    1. 자료와 처리 순서

    할 일을 적어 둔 목록에서도 무엇을 먼저 꺼낼지는 목적에 따라 달라진다. 문서 편집을 취소할 때는 가장 최근 변경부터 되돌리고, 접수한 일을 순서대로 처리할 때는 먼저 들어온 일부터 꺼낸다. 번호를 아는 항목을 바로 읽고 싶은 경우도 있다. 자료구조는 이런 작업에 맞게 여러 값을 모으고 연결하는 방식이다. 알고리즘은 그 자료에서 원하는 결과를 얻기 위해 따르는 처리 절차다. 같은 값들을 저장해도 구조와 절차를 어떻게 고르느냐에 따라 가능한 작업과 드는 비용이 달라진다.

    자료구조를 배울 때는 두 질문을 구별하면 편하다. ‘어느 순서로 넣고 꺼낼 것인가’는 사용 규칙의 질문이고, ‘메모리 안에서 값을 어떻게 보관할 것인가’는 구현의 질문이다. 마지막에 넣은 것을 먼저 꺼내는 스택과 먼저 넣은 것을 먼저 꺼내는 큐는 주로 첫 질문에 답한다. 연속된 칸이나 항목 사이의 연결로 자료를 담는 방식은 두 번째 질문에 답한다. 스택·큐·리스트가 언제나 서로 다른 저장 장치를 뜻하는 것은 아니다.

    이 글에서는 순서가 있는 자료를 담는 리스트에서 출발해 스택과 큐의 연산을 비교하고, 찾기와 정렬의 비용으로 이어 간다. 예시는 가상 문서 이력과 번호 목록이다. 코드의 출력은 아래에 명시한 Python 실행에서 확인한 값이며, 도식과 비용 비교는 원리를 설명하는 모형이다. 실제 서비스의 처리 시간이나 장비 성능을 측정한 결과는 아니다.

    2. 리스트와 저장 방식

    리스트는 항목에 앞뒤 순서가 있는 모음이다. 항목이 몇 번째에 있는지를 나타내는 번호를 인덱스라고 한다. 프로그래밍 언어에서는 첫 항목을 0번으로 세는 경우가 많다. 이때 번호 순서가 있다는 말은 값이 크기순으로 정렬되어 있다는 뜻이 아니다. 번호 목록 [31, 12, 23]도 리스트이고, 그 안의 0번 항목은 31이다.

    리스트를 구현하는 대표적인 방식 하나는 배열이다. 배열은 같은 크기의 저장 칸을 연속해서 확보한다. 시작 위치와 한 칸의 크기를 알면 특정 번호의 칸을 계산해 찾아갈 수 있다. 반면 중간에 새 항목을 끼워 넣으면서 순서를 유지하려면 뒤쪽 항목들을 옮겨 빈칸을 만들어야 한다. 크기를 늘릴 수 있는 배열 기반 리스트도 용량이 부족하면 더 큰 공간을 마련하는 작업이 필요하다. Java의 ArrayList는 이런 방식의 구현이며, 번호로 읽기는 상수 시간, 끝에 추가는 분할 상환 상수 시간으로 설명된다. 이 비용 용어는 뒤에서 풀어 본다.[1]

    다른 방식은 연결 리스트다. 값과 다음 항목을 가리키는 연결 정보를 한 덩어리로 묶는데, 이 덩어리를 노드라고 부른다. 한쪽 방향의 연결만 있으면 단일 연결 리스트, 앞과 뒤의 연결이 모두 있으면 이중 연결 리스트다. 다음 그림의 화살표는 처리 시간의 흐름이 아니라 다음 노드를 가리키는 연결이다.

    연결 리스트에서 12 뒤에 새 노드를 넣으려면 해당 위치의 연결을 고친다. 다만 ‘12가 든 노드를 이미 알고 있다’는 조건이 중요하다. 처음부터 12를 찾아가야 한다면 연결을 따라 방문하는 비용이 먼저 든다. 단일 연결 리스트에서 어떤 노드를 지울 때는 보통 그 앞 노드도 알아야 연결을 고칠 수 있다. Java의 LinkedList 역시 번호로 요청한 항목에 접근할 때 가까운 끝에서부터 이동한다.[2] 따라서 연결 리스트를 쓰면 모든 삽입과 삭제가 무조건 빨라진다고 외우기보다, 위치를 찾는 비용과 연결을 고치는 비용을 나누어 생각해야 한다.

    배열 기반 구조는 번호로 자주 읽거나 전체를 차례로 훑는 목록에 편리하다. 연결 구조는 이미 위치를 잡은 상태에서 연결을 자주 바꾸는 작업에 유용할 수 있지만, 각 노드의 연결 정보를 저장할 공간이 더 든다. 실제 속도에는 메모리를 읽는 방식과 구현도 영향을 준다. 리스트라는 이름만 보고 비용을 결정하지 않고 사용하는 언어와 구현의 문서를 확인하는 이유다.

    3. 스택과 큐

    책상 위에 종이를 쌓고 맨 위에서 꺼내는 모습을 생각하면 스택을 이해하기 쉽다. 마지막에 넣은 항목이 먼저 나오는 후입선출, 영어로 LIFO 규칙을 따른다. 넣는 연산을 push, 맨 위 항목을 제거하면서 가져오는 연산을 pop이라고 부른다. 제거하지 않고 맨 위 값만 확인하는 연산은 흔히 peek 또는 top이라고 부른다. 비어 있는 스택에서 꺼내기를 요청했을 때 오류를 낼지 별도 값을 돌려줄지도 사용 규칙에 포함된다.

    문서의 변경 이력을 저장하고 최근 변경부터 취소하는 기능은 이 순서가 필요한 사례다. Python의 리스트는 끝에 추가하는 append와 끝에서 꺼내는 pop으로 스택처럼 사용할 수 있다.[3] 다음은 Python 3.11용 코드다. 대괄호는 리스트, 따옴표 안의 값은 문자열이며, 점 뒤의 이름은 그 리스트에 요청하는 동작을 나타낸다.

    history = ["draft", "revised"]
history.append("checked")
print(history.pop())
print(history)

    CPython 3.11.15에서 실행한 출력은 다음과 같다. 마지막에 넣은 checked가 나오고 앞선 두 이력은 남았다. 이는 꺼내기 순서를 확인하는 예이며, 실제 편집 내용을 되돌리는 기능까지 구현한 것은 아니다.

    checked
['draft', 'revised']

    큐는 먼저 들어온 항목부터 꺼내는 선입선출, 영어로 FIFO 규칙을 따른다. 뒤에 넣는 연산을 enqueue, 앞에서 제거하며 가져오는 연산을 dequeue라고 한다. 접수 순서를 유지해야 하는 작업 목록에 어울린다. 스택과 달리 넣는 쪽과 꺼내는 쪽이 서로 반대다. 다음은 A, B, C를 차례로 넣고 아직 아무것도 꺼내지 않은 상태를 비교한 것이다.

    큐도 여러 방식으로 구현할 수 있다. 배열 기반 리스트의 맨 앞 항목을 지우고 나머지를 앞으로 옮기는 방식은 대기 항목이 많을수록 이동량이 늘어난다. Python 문서가 큐에 collections.deque를 권하는 이유도 이 차이다. deque는 양쪽 끝에서 넣고 꺼내도록 만든 자료구조로, 양 끝 추가·삭제가 대략 O(1)인 반면 리스트의 pop(0)은 O(n)의 이동 비용을 갖는다.[4] 배열의 앞뒤 위치를 따로 기록해 칸을 재사용하는 원형 큐도 가능하다. 이때는 빈 상태와 가득 찬 상태를 구별하고, 가득 찼을 때 기다릴지 거절할지 규칙을 정해야 한다.

    FIFO는 다음 항목을 선택하는 규칙이지, 용량 초과 때 무엇을 버릴지까지 정하는 규칙은 아니다. 기존 QoS의 FIFO·우선순위 비교 (이번 검토본 미수록)에서는 전송 대기를, 연결 풀 (이번 검토본 미수록)에서는 자원 대여와 반환·대기를 다룬다. 여기서는 그 사례를 복제하지 않고 큐의 연산과 구현 비용을 구별한다.

    4. 입력 크기와 비용

    알고리즘을 비교할 때는 먼저 무엇이 늘어나는지 정한다. 목록에 들어 있는 항목 수를 n이라고 하면 n이 입력 크기다. 시간 복잡도는 입력 크기에 따라 필요한 연산량이 어떻게 증가하는지 나타낸다. 공간 복잡도는 필요한 저장 공간의 증가를 다룬다. 추가 작업 공간만 말하는지 입력 저장까지 포함하는지도 함께 밝혀야 한다.

    빅오 표기 O는 입력이 커질 때 비용 증가의 상한을 표현하는 방법이다. 여기서는 주요 증가 양상을 비교하는 데 쓴다. O(1)은 항목 수가 늘어도 필요한 단계가 일정한 범위에 머무는 상수 시간, O(n)은 항목 수에 비례해 증가하는 선형 시간이다. O(log n)은 후보를 계속 절반으로 줄이는 탐색처럼 증가가 완만한 경우이고, O(n²)은 각 항목마다 다른 항목들을 다시 훑는 경우에 나타날 수 있다. O(1)이 ‘한 번의 기계 명령’이나 ‘항상 1초’를 뜻하지는 않는다.

    같은 연산에도 최선·평균·최악의 경우가 있다. 첫 항목에서 목표를 찾는 경우와 끝까지 못 찾는 경우를 같은 수치로 다루면 비교가 흐려진다. 또 분할 상환 비용은 여러 연산의 총비용을 나누어 보는 개념이다. 배열의 끝에 추가하다가 가끔 전체를 더 큰 공간으로 옮기더라도, 긴 추가 연산열 전체로 보면 한 번당 상수 수준일 수 있다. 이는 입력 분포를 가정한 평균 비용과 다르고, 어느 한 번의 추가도 오래 걸리지 않는다는 보장이 아니다.

    대표 구현의 비용 모형 — 값 하나의 비교·접근을 일정 비용으로 가정
    작업비용조건과 이유
    작업배열 기반 리스트의 번호로 읽기비용O(1)조건과 이유유효한 번호의 저장 위치를 계산한다.
    작업순서를 유지하는 배열 중간 삽입비용최악 O(n)조건과 이유뒤쪽 항목들을 옮겨야 한다.
    작업단일 연결 리스트의 특정 번호 찾기비용최악 O(n)조건과 이유앞에서부터 연결을 따라간다.
    작업위치를 아는 노드 뒤에 연결 삽입비용O(1)조건과 이유새 노드가 준비된 상태에서 연결만 변경한다. 위치 탐색·할당은 별도다.

    이 표는 각 절차에서 몇 칸을 옮기거나 방문하는지를 세운 모형이다. 실측 시간을 대신하지 않는다. 길이가 긴 문자열을 비교하거나 저장 장치에서 자료를 읽는다면 값 하나를 다루는 비용도 달라진다. 서비스 응답 시간을 개선할 때는 이런 구조적 비교에 실제 측정을 더해야 한다.

    5. 탐색의 전제

    탐색은 원하는 값을 찾는 작업이다. 정렬되지 않은 목록이라면 앞에서부터 하나씩 비교하는 선형 탐색을 쓸 수 있다. 입력 준비가 간단하고 어느 위치에 있는 값도 찾을 수 있지만, 없다는 것을 확인하려면 끝까지 봐야 하므로 최악의 경우 O(n)이다.

    목록이 같은 비교 규칙으로 이미 정렬되어 있고 중간 항목에 바로 접근할 수 있다면 이진 탐색을 사용할 수 있다. 가운데 값보다 목표가 크면 왼쪽 후보를 버리고, 작으면 오른쪽 후보를 버리는 절차를 반복한다. 후보가 매번 대략 절반으로 줄어들어 비교 횟수는 O(log n)으로 증가한다. 그러나 정렬되지 않은 목록에 이 절차를 그대로 적용하면 버린 쪽에 목표가 있을 수 있다. 연결 리스트처럼 가운데 위치까지 이동해야 하는 구조에서는 비교 횟수가 적다고 전체 접근 비용까지 같은 것은 아니다.

    실제 라이브러리가 반환하는 값의 의미도 확인해야 한다. Python의 bisect_left는 존재 여부가 아니라 정렬 순서를 유지하며 넣을 왼쪽 삽입 위치를 돌려준다.[5] 따라서 그 위치가 목록 안에 있는지, 그곳의 값이 목표와 같은지를 추가로 비교한다. 다음 코드는 앞 그림과 목표는 같지만, 라이브러리 내부가 그림과 똑같은 가운데 선택 순서를 사용한다고 주장하는 예는 아니다.

    from bisect import bisect_left

codes = [12, 18, 23, 31, 47, 52, 68, 75]
for target in (52, 50):
    pos = bisect_left(codes, target)
    found = pos < len(codes) and codes[pos] == target
    print(target, pos, found)

    CPython 3.11.15 실행 출력은 아래와 같다. 52와 50 모두 삽입 위치는 5지만 50은 그 자리에 존재하지 않는다. and는 앞 조건이 거짓이면 뒤 비교를 실행하지 않으므로 목록 끝을 넘는 위치를 읽는 것도 피한다.

    52 5 True
50 5 False

    찾는 단계가 빠르더라도 정렬된 배열에 실제로 값을 끼워 넣으려면 뒤 항목들을 옮길 수 있다. Python 문서도 insort의 O(log n) 탐색보다 O(n) 삽입이 전체 비용을 지배한다고 설명한다. 자주 바뀌는 자료에 드는 유지비까지 포함해야 하는 이유다. 데이터베이스 인덱스 (이번 검토본 미수록)는 조회와 유지비의 절충을 다른 맥락에서 다룬다. 여기의 리스트 탐색을 데이터베이스 실행 계획과 같은 동작으로 취급하지는 않는다.

    6. 정렬과 선택 기준

    정렬은 값을 정한 기준에 따라 다시 배열하는 작업이다. 번호순 목록을 만든 뒤 여러 번 이진 탐색을 할 수 있고, 화면에 이름순으로 보여 주거나 같은 분류의 항목을 모으는 데도 쓴다. 무엇으로 비교할지를 먼저 정해야 한다. 숫자 자체를 비교할지 문자열로 비교할지, 같은 값이 여러 개일 때 원래 순서를 유지할지가 결과를 바꾼다.

    삽입 정렬은 앞쪽을 정렬된 부분으로 유지하면서 다음 값을 알맞은 위치에 끼워 넣는 방식이다. 순서를 거꾸로 받은 경우에는 각 단계마다 앞 항목들을 많이 옮겨 전체 이동이 O(n²)으로 증가한다. 이미 정렬된 입력에서는 이를 확인하는 정도로 끝나는 구현이 가능하다. 병합 정렬은 목록을 작은 부분으로 나누어 각각 정렬한 뒤, 두 정렬 목록의 앞쪽 값을 비교하며 합친다. 단계마다 전체 항목을 처리하고 나누는 단계 수가 O(log n)이므로 전형적인 구현의 시간은 O(n log n)이다. 배열을 별도 공간에 합치는 구현은 보통 O(n)의 추가 공간이 필요하다. 이 설명은 알고리즘의 단계 수를 분석한 것으로 특정 Python 함수의 내부 구현을 뜻하지 않는다.

    같은 정렬 기준값을 가진 항목들의 기존 순서를 유지하는 성질을 안정성이라고 한다. 접수 순서대로 있던 항목을 담당 부서별로 묶으면서 같은 부서 안에서는 접수 순서를 남기고 싶다면 안정 정렬이 도움이 된다. Python의 sorted와 리스트의 sort는 안정 정렬을 제공한다. 전자는 새 리스트를 만들고 후자는 기존 리스트를 바꾸므로 원래 순서가 필요한지도 선택 기준이다.[6]

    자료구조와 알고리즘 선택은 결국 많이 하는 작업을 묻는 일이다. 최근 작업부터 되돌리면 스택, 먼저 접수한 것부터 처리하면 큐, 번호로 읽고 중간 내용을 편집하면 리스트의 구현을 비교한다. 한 번만 찾을 작은 자료를 먼저 정렬할 필요는 없을 수 있고, 변경이 드문 목록에서 반복해서 찾는다면 정렬 준비 비용을 여러 조회에 나누어 부담할 수 있다. 저장 공간, 변경 빈도, 순서 보존, 빈 입력과 중복값 처리까지 확인한 뒤 표준 라이브러리의 보장 범위를 읽으면 선택의 이유를 설명할 수 있다.

    7. 함께 읽기

    코드의 변수·조건·함수를 처음 접한다면 프로그래밍 언어와 기본 문법을 먼저 읽을 수 있다. 자료구조가 다른 분야와 어떻게 이어지는지는 컴퓨터공학의 분류 (이번 검토본 미수록)에서 살펴본다. 이 글은 스택·큐·리스트와 탐색·정렬의 선택을 다루며 통신 장비의 큐 설정, 네트워크·암호 알고리즘 전체, 실제 DB 작업을 다루지 않는다.
