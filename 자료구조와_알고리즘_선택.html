    1. 자료구조와 알고리즘

    최근 편집을 취소하는 기능과 먼저 접수한 신청부터 처리하는 기능에 같은 목록을 써도 될까? 값을 담을 수 있다는 점에서는 가능하지만, 다음에 꺼낼 항목은 달라야 한다. 자료구조는 여러 값을 보관하고 연결하는 방식이고, 알고리즘은 그 자료를 처리해 결과를 얻는 절차다. 저장 방식과 처리 절차를 함께 선택해야 필요한 순서를 지키면서 찾기·추가·삭제 비용도 설명할 수 있다.

    모든 작업을 ‘목록에 넣고 앞에서 찾기’로 처리하면 구현은 단순하다. 그러나 항목이 많아질수록 반복 탐색과 칸 이동이 부담이 된다. 반대로 조회를 빠르게 하려고 미리 정렬하면 새 항목을 넣을 때 순서를 유지하는 일이 생긴다. 좋은 선택은 언제나 빠른 구조를 찾는 것이 아니라, 자주 하는 작업에 맞춰 준비 비용과 사용 비용을 나누는 것이다.

    먼저 저장 구현과 사용 규칙을 구별하자. 연속된 칸에 담는 배열과 연결을 따라가는 리스트는 보관 방법의 차이다. 마지막 것을 먼저 꺼내는 스택과 먼저 들어온 것을 먼저 꺼내는 큐는 꺼내기 규칙의 차이다. 배열로 스택을 만들 수도 있으므로 네 이름을 서로 배타적인 상자처럼 외우면 실제 구현을 이해하기 어렵다.

    2. 자료의 저장과 접근

    자료를 읽는 순서와 자료를 놓는 위치는 같지 않을 수 있다. 아래의 두 구현은 모두 31, 12, 23이라는 순서를 제공하지만, 그 순서의 두 번째 항목에 도달하는 방법은 다르다.

    2.1 배열과 연결 리스트

    리스트는 앞뒤 순서가 있는 항목 모음이다. 몇 번째 항목인지 나타내는 번호가 인덱스이며, 많은 언어에서 첫 번호는 0이다. 따라서 [31, 12, 23]의 1번 항목은 12다. 순서가 있다는 말은 값이 크기순으로 정렬되어 있다는 뜻은 아니다.

    배열은 같은 크기의 저장 칸들을 연속해서 확보한다. 시작 위치에서 번호만큼 떨어진 칸을 계산할 수 있어 앞 항목을 차례로 읽지 않아도 된다. 그러나 순서를 유지하며 가운데에 값을 끼우려면 뒤 칸들을 옮겨야 한다. 크기를 늘리는 배열 기반 리스트도 빈 용량을 다 쓰면 더 큰 공간을 마련할 수 있다. Java의 ArrayList는 번호 접근과 끝 추가의 비용을 구별해 명시한다.[1]

    연결 리스트는 값과 다음 항목의 위치를 한 덩어리인 노드로 묶는다. 단일 연결 리스트는 다음 방향, 이중 연결 리스트는 이전과 다음 방향을 함께 기록한다. 그림의 화살표는 실행 순서가 아니라 다음 노드를 가리킨다.

    12 뒤에 19를 넣는다면 배열은 23을 뒤로 옮기고 빈칸에 19를 쓴다. 연결 방식은 새 19 노드가 23을 가리키게 하고 12의 다음 연결을 19로 바꾼다. 여기서 연결을 바꾸는 작업이 짧다는 설명은 12 노드의 위치를 이미 알고 새 노드도 준비했다는 조건에 의존한다. 처음부터 12를 찾아야 한다면 순회 비용과 노드 할당 비용이 따로 든다. 단일 연결에서 삭제하려면 보통 앞 노드의 연결도 알아야 한다. Java LinkedList도 번호 접근은 가까운 끝에서부터 이동한다.[2]

    번호 읽기가 많으면 배열 기반 구현이 유리한 출발점이다. 연결을 바꾸는 작업이 많더라도 위치 탐색이 함께 필요한지 먼저 살펴야 한다. 연결 정보의 추가 공간, 메모리를 읽는 방식, 구현 차이까지 실제 속도에 영향을 주므로 ‘연결이면 삽입이 항상 빠르다’는 결론은 성립하지 않는다.

    2.2 스택과 큐

    스택은 마지막에 넣은 항목부터 꺼내는 후입선출(LIFO) 규칙이다. 추가는 push, 제거하며 가져오기는 pop, 제거하지 않는 확인은 흔히 peek 또는 top이라고 부른다. 최근 편집부터 취소해야 할 때 이 순서가 맞는다. 빈 스택에서 꺼내면 어떤 오류나 결과를 줄지도 계약의 일부다.

    Python 리스트의 append는 끝에 추가하고 인수 없는 pop은 끝에서 꺼낸다. 대괄호는 목록, 따옴표는 문자열, 점 뒤의 이름은 목록에 요청할 동작이다.[3] 다음 CPython 3.11.15 예제에서 마지막에 넣은 checked를 먼저 꺼내면 두 이전 이력만 남는다.

    history = ["draft", "revised"]
history.append("checked")
print(history.pop())
print(history)
    checked
['draft', 'revised']

    큐는 먼저 들어온 항목부터 꺼내는 선입선출(FIFO) 규칙이다. 뒤에 넣는 enqueue와 앞에서 꺼내는 dequeue를 구별한다. 접수 순서를 지킬 때는 최근 항목이 먼저 나오는 스택보다 큐가 맞다. A, B, C를 넣고 아직 꺼내지 않았다면 다음 값은 다음처럼 갈린다.

    배열 기반 목록의 맨 앞을 지우고 나머지를 당기는 구현은 매번 이동이 생긴다. 양 끝에서 넣고 꺼내도록 만든 Python collections.deque는 큐 구현의 대안이다. 문서는 양 끝 연산은 대략 일정한 비용, 리스트의 pop(0)은 항목 수에 비례하는 이동 비용으로 구별한다.[4] 배열의 앞뒤 위치를 기록하고 칸을 돌려 쓰는 원형 큐도 만들 수 있다.

    용량이 정해진 큐는 빈 상태와 가득 찬 상태를 구별해야 한다. 가득 차면 기다릴지, 새 요청을 거절할지, 기존 항목을 버릴지는 별도 정책이다. FIFO는 다음 항목을 고르는 순서만 정한다. 이를 용량 초과 폐기 정책이나 연결 풀의 대여·반환 규칙까지 정하는 약속으로 확장하면 안 된다.

    3. 연산 비용과 탐색

    작은 목록에서는 두 방법의 차이가 보이지 않을 수 있다. 항목 수가 늘어날 때 방문하거나 옮겨야 할 칸 수를 비교하면 구조의 차이를 더 분명히 볼 수 있다.

    3.1 시간·공간 복잡도

    입력 크기인 항목 수를 n이라고 하자. 시간 복잡도는 n에 따라 필요한 연산량이 늘어나는 정도, 공간 복잡도는 저장 공간의 증가를 다룬다. 공간을 말할 때는 입력 자체를 포함하는지, 추가 작업 공간만 세는지도 밝혀야 한다.

    빅오 표기는 큰 입력에서 비용 증가의 상한을 나타낸다. O(1)은 입력 수와 무관하게 일정한 범위의 단계, O(n)은 항목 수에 비례하는 정도의 단계다. 후보를 절반씩 줄이면 O(log n), 항목마다 앞 항목들을 다시 훑거나 옮기면 최악 O(n²)이 될 수 있다. 이 표기는 초 단위 측정값이 아니며 O(1)이 기계 명령 한 개를 뜻하지도 않는다.

    대표 구현의 비용 모형 — 값 하나의 비교·접근을 일정 비용으로 가정
    작업비용조건과 이유
    작업배열 기반 리스트의 번호로 읽기비용O(1)조건과 이유유효한 번호의 저장 위치를 계산한다.
    작업순서를 유지하는 배열 중간 삽입비용최악 O(n)조건과 이유뒤쪽 항목들을 옮겨야 한다.
    작업단일 연결 리스트의 특정 번호 찾기비용최악 O(n)조건과 이유앞에서부터 연결을 따라간다.
    작업위치를 아는 노드 뒤에 연결 삽입비용O(1)조건과 이유새 노드가 준비된 상태에서 연결만 변경한다. 위치 탐색·할당은 별도다.

    같은 탐색도 첫 항목에서 찾는 최선과 끝까지 못 찾는 최악이 다르다. 평균 비용을 말하려면 입력 분포를 정해야 한다. 분할 상환은 그와 달리 연속된 여러 연산의 총비용을 나눠 보는 분석이다. 배열 기반 리스트의 끝 추가가 가끔 큰 복사를 하더라도 전체 추가열의 총비용이 선형이면 한 번당 분할 상환 상수 비용이다. 이는 어느 한 번도 오래 걸리지 않는다는 보장이 아니다.

    표는 값 하나를 비교하거나 접근하는 비용을 일정하게 두는 모형이다. 긴 문자열 비교나 저장 장치 읽기가 포함되면 한 단계의 실제 비용도 바뀐다. 이 분석으로 후보를 좁힌 뒤 실제 환경에서 측정해야 응답 시간이 개선됐다고 말할 수 있다.

    3.2 선형 탐색과 이진 탐색

    선형 탐색은 앞에서부터 하나씩 비교한다. 정렬 준비 없이 시작할 수 있지만 목표가 없다는 사실을 알려면 끝까지 읽어야 하므로 최악 O(n)이다. 한 번만 찾을 작은 목록에는 준비 비용이 없는 이 방법이 합리적일 수 있다.

    이진 탐색은 같은 비교 기준으로 정렬된 목록의 가운데 값과 목표를 비교하고 필요 없는 절반을 버린다. 아래 모형에서 52는 31보다 크므로 왼쪽 후보를 버리고, 남은 구간의 가운데에서 찾는다. 중간 칸에 바로 접근할 수 있을 때 비교 횟수는 O(log n)이다. 정렬되지 않았으면 버린 구간에 목표가 있을 수 있고, 연결 리스트처럼 중간까지 이동해야 한다면 비교 횟수와 전체 접근 비용은 달라진다.

    Python bisect_left는 ‘찾음’이 아니라 정렬 순서를 유지할 왼쪽 삽입 위치를 반환한다.[5] 그 위치가 목록 안인지 확인한 뒤 실제 값도 비교해야 한다. 아래 코드의 가운데 선택 세부는 앞의 설명용 모형과 구별한다.

    from bisect import bisect_left

codes = [12, 18, 23, 31, 47, 52, 68, 75]
for target in (52, 50):
    pos = bisect_left(codes, target)
    found = pos < len(codes) and codes[pos] == target
    print(target, pos, found)
    52 5 True
50 5 False

    CPython 3.11.15에서 52와 50의 삽입 위치는 모두 5였다. 그러나 5번 값은 52이므로 50의 존재 여부는 False다. and는 앞 조건이 거짓이면 뒤 조건을 평가하지 않아, 목표가 최댓값보다 커 위치가 목록 끝을 가리켜도 범위 밖 항목을 읽지 않는다. 빈 목록에도 같은 보호가 적용된다.

    찾는 비용이 줄어도 실제 삽입에는 뒤 항목 이동이 남는다. insort의 전체 비용이 O(n) 삽입에 지배되는 이유다. 조회가 빠르다는 이유만으로 변경 비용까지 작다고 결론 내리지 않는다. 데이터베이스의 인덱스도 유지비가 있지만, 이 리스트 예제가 데이터베이스 실행 계획 자체를 구현한 것은 아니다.

    4. 정렬과 선택 기준

    정렬은 비교 기준에 맞춰 항목의 순서를 다시 만드는 작업이다. 이진 탐색의 준비뿐 아니라 이름순 표시와 분류별 묶음에도 쓰인다. 숫자 12를 수로 볼지 문자열로 볼지부터 정해야 결과의 의미가 일관된다.

    4.1 정렬 과정과 안정성

    삽입 정렬은 앞쪽을 정렬한 상태로 유지하며 다음 값을 끼워 넣는다. [31, 12, 23]에서 12를 처리할 때 31을 오른쪽으로 옮겨 [12, 31, 23]을 만든다. 다음 23을 처리할 때 31을 한 칸 옮겨 [12, 23, 31]로 만든다. 역순 입력에서는 각 단계마다 앞부분을 길게 옮겨 최악 O(n²)이 된다. 이미 정렬됐다면 이동 없이 순서를 확인해 선형 시간에 끝내는 구현이 가능하다.

    병합 정렬은 작은 부분들을 정렬하고 다시 합친다. 같은 세 값에서 왼쪽 [31]과 오른쪽 [12, 23]이 정렬됐다고 하자. 앞값 31과 12를 비교해 12를, 이어 31과 23을 비교해 23을 넣고 남은 31을 붙인다. 결과는 같지만 값을 끼우기 위해 이미 쌓은 결과를 뒤로 미는 대신 두 부분의 앞에서 골라 간다. 전형적인 구현은 분할 단계가 O(log n)이고 각 단계에서 전체 항목을 다뤄 O(n log n) 시간이 든다. 배열 병합에는 보통 O(n)의 추가 공간이 필요하다. 이것은 절차 분석이며 Python 정렬 함수의 내부 구현 설명은 아니다.

    같은 비교값을 가진 항목의 기존 순서를 지키는 성질은 안정성이다. 접수순 목록을 부서별로 묶되 같은 부서 안의 접수순은 남기고 싶을 때 유용하다. Python의 sorted와 list.sort는 안정 정렬을 제공한다. 전자는 새 리스트, 후자는 기존 리스트를 바꾼다는 차이도 있다.[6] 삽입 정렬은 같은 값 앞을 넘지 않게, 병합은 같은 값이면 왼쪽을 먼저 고르게 구현해야 그 성질을 유지할 수 있다.

    4.2 조회와 변경의 절충

    반복 조회가 많고 변경이 드물다면 정렬 준비 비용을 여러 조회에 나눌 수 있다. 반대로 계속 들어오는 자료를 한 번씩만 처리한다면 정렬보다 큐의 순서가 중요할 수 있다. 번호 접근, 중간 삽입, 최근 작업 취소 중 무엇이 핵심인지 정한 뒤 저장 공간, 중복값, 빈 입력과 오류 규칙을 비교해야 한다. 표준 라이브러리의 비용과 계약을 읽으면 ‘왜 이 구조를 골랐는가’를 설명할 수 있다.
