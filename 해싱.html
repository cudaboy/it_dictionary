    1. 입력과 요약값

    내려받은 설치 파일이 배포자가 올린 파일과 같은지 확인하려면 무엇을 비교하면 될까? 파일 이름은 그대로여도 내용이 바뀔 수 있고, 큰 파일을 사람이 처음부터 끝까지 살펴보기는 어렵다. 이때 파일의 바이트, 즉 컴퓨터가 저장하는 데이터의 단위를 일정한 계산 규칙에 넣어 짧은 비교값을 만들 수 있다. 이 연산이 해싱(Hashing)이고, 계산 규칙이 해시 함수, 나온 값이 해시값 또는 다이제스트다.

    요약값이라고 해서 문서의 줄거리나 중요한 문장을 뽑는 것은 아니다. 해시 함수는 내용의 의미를 이해하지 않고 입력 데이터를 계산한다. 예를 들어 SHA-256은 입력이 짧은 문장이든 큰 파일이든 256비트의 결과를 만든다. 비트는 0 또는 1을 나타내는 단위다. 이 결과를 사람이 옮겨 적기 좋은 16진수로 표시하면 64자리 문자열이 된다. 16진수는 0부터 9와 a부터 f까지의 기호로 수를 표현하는 방식이다. SHA-256 같은 고정 길이 해시를 중심으로 아래의 성질을 살펴본다.[2]

    해싱의 쓰임은 파일 확인에만 있지 않다. 프로그램이 자료를 빠르게 찾을 위치를 정할 때도 해시를 쓰고, 데이터가 바뀌었는지 비교할 때도 쓴다. 다만 빠른 검색을 위한 해시와 악의적인 조작에 견뎌야 하는 해시는 요구하는 성질이 다르다. 보안에 쓰려면 단순히 짧은 결과가 나온다는 사실보다 더 많은 조건을 확인해야 한다.

    2. 결정성과 충돌

    해시를 비교에 쓸 수 있는 출발점은 결정성이다. 같은 함수와 같은 설정에 정확히 같은 바이트를 넣으면 같은 값이 나온다. 계산하는 날짜나 파일 이름이 결과를 정하는 것이 아니다. 파일 내용만 해싱했다면 이름을 바꿔도 결과는 같고, 이름을 유지한 채 내용의 한 글자를 고치면 입력 바이트가 달라진다.

    여기서 ‘같은 내용’은 사람이 읽기에 비슷하다는 뜻이 아니다. 문장 끝의 줄바꿈, 공백, 문자를 바이트로 나타내는 인코딩이 다르면 해시의 입력도 달라진다. 화면에 같은 글처럼 보이는 파일의 값이 다를 때는 이러한 차이도 살펴봐야 한다. 비교 도구가 어느 범위의 데이터를 읽었고 어떤 알고리즘을 사용했는지 먼저 맞추는 이유다.

    반대 방향의 추론에는 주의가 필요하다. 같은 입력은 같은 해시를 만들지만, 같은 해시라고 해서 서로 다른 입력의 가능성이 수학적으로 사라지는 것은 아니다. 고정 길이 결과의 가짓수는 한정되어 있고 가능한 입력은 그보다 훨씬 많다. 서로 다른 입력이 같은 결과로 이어지는 경우를 충돌이라고 한다. 따라서 해시값을 모든 데이터에 절대로 중복되지 않는 번호로 이해하면 안 된다.

    해시가 다르면, 같은 알고리즘과 정상적인 계산을 전제로 두 입력이 다르다는 결론을 내릴 수 있다. 같을 때의 신뢰 수준은 사용한 함수가 충돌을 찾기 얼마나 어렵게 하는지, 비교 기준을 어디서 얻었는지에 달려 있다. 이 두 조건을 구분하면 ‘값이 같다’와 ‘안전한 파일이다’를 성급하게 같은 말로 취급하지 않게 된다.

    3. 암호학적 해시

    암호학적 해시는 누군가 일부러 결과를 속이려 할 때도 사용하도록 설계한 해시다. SHA-256이 그 예다. 중요한 성질은 충돌이 아예 없다는 것이 아니라, 다음과 같은 입력을 현실적인 계산 자원으로 찾아내기 어렵도록 만드는 것이다.[3]

    역상 저항성
    어떤 해시값이 주어졌을 때, 그 값이 나오는 입력을 찾기 어렵다는 성질이다. 요약값에서 입력을 거꾸로 알아내려는 시도에 대응한다.
    제2역상 저항성
    특정 파일 하나가 이미 주어졌을 때, 그 파일과 같은 해시를 내는 다른 파일을 찾기 어렵다는 성질이다. 승인된 파일을 다른 내용으로 바꿔치기하는 상황과 연결된다.
    충돌 저항성
    공격자가 두 입력을 모두 고를 수 있어도, 서로 다른 두 입력을 같은 해시로 맞추기 어렵다는 성질이다. 특정 파일의 대체물을 찾는 문제와 구별한다.

    이러한 성질은 해시를 암호화 (이번 검토본 미수록)와 같게 만들지 않는다. 암호화는 적절한 키로 원문을 되찾는 복호화를 전제로 하지만, 해시는 원문을 복원하는 저장 형식이 아니다. 또한 인코딩은 데이터를 다른 표현으로 바꾸는 작업이다. 해시를 16진수로 표시하는 것은 이미 계산한 결과의 표현만 바꾸며, 원문을 숨기는 보안을 추가하지 않는다.

    ‘복호화 기능이 없다’와 ‘입력을 추측할 수 없다’도 다르다. 후보 입력을 만들어 같은 해시 함수를 적용하고 결과를 비교할 수 있기 때문이다. 가능한 입력이 매우 적거나 쉽게 예상된다면 이 방법이 통할 수 있다. 한편 MD5와 SHA-1에는 알려진 충돌 취약점이 있으므로, 이름에 해시가 들어간다고 모두 같은 보안 수준이라고 보지 않는다.[4]

    4. 파일 바이트의 비교

    도서 목록 파일에 book-001,SQL 한 줄이 있고 마지막에 줄바꿈이 있다고 하자. 아래 코드는 이 파일의 내용에 해당하는 바이트열, 같은 복사본, 책 이름에 2가 추가된 변경본을 비교한다. 실제 파일을 읽거나 내려받지는 않고, 합성 파일 내용을 메모리에 두어 같은 계산을 수행한다. Python에서 문자열 앞의 b는 바이트열을, \n은 줄바꿈을 나타낸다.

    SHA-256 비교 코드

    import hashlib
original = b"book-001,SQL\n"
copy = b"book-001,SQL\n"
changed = b"book-001,SQL 2\n"
def digest(data):
    return hashlib.sha256(data).hexdigest()
print("same:", digest(original) == digest(copy))
print("changed:", digest(original) == digest(changed))
print("hex length:", len(digest(original)))

    hashlib.sha256(data)는 입력의 SHA-256 결과를 계산하고, hexdigest()는 이를 16진수 문자열로 돌려준다. ==는 두 값이 같은지를 검사한다. 따라서 첫 비교는 원본과 복사본, 두 번째 비교는 원본과 변경본을 대상으로 한다. 이 API의 입력과 출력 형식은 Python 공식 문서에서 확인할 수 있다.[5]

    실제 실행 결과

    same: True
changed: False
hex length: 64

    위 코드를 Python 3.11.15 표준 라이브러리로 실행한 결과다. 동일 복사본은 같은 값을 만들었고, 이번 변경본은 다른 값을 만들었다. 64라는 길이는 원본 파일의 길이가 아니라 SHA-256 결과를 16진수로 표시한 길이다. 이 실행은 모든 가능한 입력에 충돌이 없다는 증명도, 실제 배포 파일의 안전성 검사도 아니다.

    실제 파일을 비교할 때는 파일을 바이트 그대로 읽어 같은 해시를 계산한다. 줄바꿈을 자동 변환하는 텍스트 처리나 일부 구간만 읽는 처리 때문에 비교 대상이 달라지지 않도록 한다. 파일 해시는 내용 차이를 알려 줄 뿐 어느 글자가 바뀌었는지까지 알려 주지는 않는다. 원인을 찾으려면 파일 비교 도구나 배포 기록을 추가로 확인해야 한다.

    5. 기준값의 신뢰

    앞의 실험은 내가 만든 원본과 복사본을 비교했다. 다운로드 상황에서는 원본을 직접 갖고 있지 않을 수 있다. 이때 배포자가 제공한 기준 해시와 받은 파일의 해시를 비교한다. 데이터가 기대한 상태에서 바뀌지 않았는지 확인하는 것을 무결성 확인이라고 한다. 비교가 의미 있으려면 계산값뿐 아니라 기준값의 출처도 믿을 수 있어야 한다.

    공격자가 파일과 그 옆의 해시 문자열을 모두 바꿀 수 있다면, 바뀐 파일의 해시를 다시 적어 두는 것만으로 비교를 통과시킬 수 있다. 따라서 파일 옆에 긴 문자열이 있다는 사실만으로 신뢰가 생기지 않는다. 공식 배포 경로를 확인하거나, 신뢰할 수 있는 배포자의 키로 서명된 해시 목록을 검증하는 절차가 필요하다. 전자서명은 서명자의 키를 사용해 만든 정보를 검증하는 방식이며, 이때도 검증에 쓰는 키가 실제 배포자의 것인지 확인해야 한다.

    Ubuntu의 공식 다운로드 검증 안내는 해시 목록의 서명을 확인하는 단계와 ISO 파일의 SHA-256을 비교하는 단계를 나눈다. 이는 ‘기준을 믿을 근거’와 ‘받은 파일이 그 기준에 맞는가’가 서로 다른 질문임을 보여 준다. 여기서는 그 절차를 설명의 근거로 인용하며 실제 ISO 다운로드나 서명 검증을 수행한 것은 아니다.[6]

    6. 용도와 한계

    해시는 큰 파일의 비교값을 작게 전달하고, 저장된 내용의 변경을 탐지하며, 프로그램에서 자료를 분류하거나 찾는 데 쓰인다. 파일 비교에는 계산이 빠른 성질이 유리하다. 반대로 비밀번호 저장은 유출된 저장값을 가지고 후보를 반복 대입하는 비용을 높이는 것이 중요하다. 같은 ‘해싱’이라는 이름을 써도 최적화하려는 목표가 다르다.

    빠른 SHA-256 한 번만으로 안전한 비밀번호 저장을 구성하지 않는다. 그 목적에는 계산 비용을 조정하는 전용 방식이 필요하다. 저장값 생성과 로그인 확인의 자세한 흐름은 비밀번호 해싱 (이번 검토본 미수록)에서 이어 읽는다.[1] 파일 해시와 비밀번호 해싱의 목적 차이

    해시가 기준과 일치해도 프로그램에 취약점이 없거나 파일 내용 자체가 무해하다는 결론까지 나오지는 않는다. 믿을 수 있는 배포자가 만든 파일에도 문제가 있을 수 있다. 해시 비교는 정해진 입력의 일치를 확인하는 도구로 쓰고, 배포자의 신뢰·서명·보안 검토는 각각 필요한 절차로 구별한다.

    7. 함께 읽기

    프로그램과 데이터의 배경은 소프트웨어 (이번 검토본 미수록), 원문 복원과 키의 역할은 암호화 (이번 검토본 미수록), 로그인용 저장값은 비밀번호 해싱 (이번 검토본 미수록)에서 다룬다. 사용자의 신원을 확인하는 전체 목적은 인증 (이번 검토본 미수록)과 연결된다.
