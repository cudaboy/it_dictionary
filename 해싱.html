    1. 해싱과 해시값

    파일 이름이 같으면 내용도 같을까? 이름을 바꾸지 않고 내용을 수정할 수 있으므로 이름만으로는 판단할 수 없다. 파일을 이루는 바이트, 즉 컴퓨터가 저장하는 데이터 단위를 계산 규칙에 넣어 비교값을 만들면 내용 변화 확인에 도움이 된다. 이 계산을 해싱, 규칙을 해시 함수, 결과를 해시값 또는 다이제스트라고 한다. 해싱은 검색할 위치를 고르는 데도 쓰이지만, 보안용 파일 비교와는 요구하는 성질이 다르다.

    해시값은 글의 줄거리처럼 중요한 의미를 골라낸 요약이 아니다. 입력 바이트에 계산을 적용한 결과다. SHA-256은 입력 길이가 달라도 256비트의 결과를 만든다. 비트는 0 또는 1을 나타내며, 이 결과를 0~9와 a~f로 수를 적는 16진수로 표현하면 64자리다. 사람에게 보이는 긴 문자열의 길이가 원본 파일의 크기를 말해 주지는 않는다. 모든 해시가 같은 길이를 쓰는 것은 아니며 아래 고정 길이 설명은 SHA-256 같은 함수에 해당한다.[1]

    빠른 검색과 파일 비교는 모두 입력을 계산값에 대응시키지만 그 다음 행동이 다르다. 검색에서는 계산값으로 후보를 좁힌 뒤 실제 키를 확인한다. 파일 확인에서는 기준 해시와 비교하여 내용이 같은지 판단할 근거를 얻는다. 누군가 고의로 다른 파일을 같은 값에 맞추려는 상황까지 고려한다면 암호학적 성질과 기준의 출처를 함께 확인해야 한다.

    2. 해시 함수의 특성

    2.1 결정성과 충돌

    같은 함수와 설정에 같은 바이트를 넣으면 같은 결과가 나온다. 이 결정성 때문에 두 곳에서 따로 계산한 값을 비교할 수 있다. 파일 내용만 입력했다면 파일 이름이나 계산 날짜를 바꾸어도 해시는 그대로다. 반대로 이름을 유지한 채 내용의 한 글자를 바꾸면 입력은 달라진다.

    사람 눈에 같은 문장과 바이트가 같은 데이터는 다르다. 끝의 줄바꿈이나 공백, 문자를 바이트로 표현하는 인코딩이 달라지면 입력도 달라진다. 파일 비교 전에 알고리즘과 읽은 범위를 맞춰야 하는 이유다. 한 도구가 줄바꿈을 변환한 텍스트를 계산하고 다른 도구가 원래 바이트를 계산하면 서로 다른 대상을 비교하게 된다.

    같은 입력이면 같은 결과지만 그 역이 언제나 성립하지는 않는다. 고정 길이 결과의 가짓수보다 가능한 입력이 많으므로 서로 다른 입력이 같은 값으로 모일 수 있다. 이를 충돌이라고 한다. 해시를 모든 데이터에 하나씩 붙는 절대적인 고유번호로 사용할 수 없는 이유다.

    동일 알고리즘으로 정상 계산했는데 해시가 다르면 입력도 다르다. 해시가 같을 때는 충돌 가능성과 사용 목적을 따져야 한다. 해시 테이블은 충돌을 처리하여 서로 다른 키를 보관하고, 보안용 파일 확인은 의도적인 바꿔치기가 어렵도록 암호학적 해시를 선택한다. 어느 경우든 계산값의 일치를 파일의 무해함과 같은 뜻으로 읽지 않는다.

    2.2 암호학적 해시

    암호학적 해시는 우연한 차이뿐 아니라 고의적인 조작도 고려해 설계한다. SHA-256이 그 예다. 목표는 충돌의 수학적 존재를 없애는 것이 아니라 다음 문제들을 현실적인 계산 자원으로 풀기 어렵게 하는 것이다. 어떤 정보가 먼저 주어지는지에 따라 세 성질을 구별한다.[2]

    역상 저항성
    어떤 해시값이 주어졌을 때, 그 값이 나오는 입력을 찾기 어렵다는 성질이다. 요약값에서 입력을 거꾸로 알아내려는 시도에 대응한다.
    제2역상 저항성
    특정 파일 하나가 이미 주어졌을 때, 그 파일과 같은 해시를 내는 다른 파일을 찾기 어렵다는 성질이다. 승인된 파일을 다른 내용으로 바꿔치기하는 상황과 연결된다.
    충돌 저항성
    공격자가 두 입력을 모두 고를 수 있어도, 서로 다른 두 입력을 같은 해시로 맞추기 어렵다는 성질이다. 특정 파일의 대체물을 찾는 문제와 구별한다.

    이 성질들은 해시를 암호화로 만들지는 않는다. 암호화는 적절한 키로 원문을 되찾는 복호화를 전제로 하지만 해시는 원문 복원용 저장 형식이 아니다. 인코딩은 표현을 바꾸는 작업이다. 계산된 해시를 16진수로 표시해도 결과의 표현만 달라질 뿐 별도의 비밀 보호가 추가되지는 않는다.

    복호화 기능이 없어도 입력 후보를 추측하여 같은 함수에 넣고 결과를 대조할 수 있다. 가능한 입력이 적거나 쉽게 예상된다면 이 반복 대입이 효과적일 수 있다. 또한 MD5와 SHA-1에는 알려진 충돌 취약점이 있다. 파일 비교 도구에 알고리즘 이름이 있다는 사실만으로 보안 목적에 적합하다고 판단하지 않는다.[3]

    3. 파일 바이트 비교

    한 줄짜리 도서 목록의 원본·복사본·변경본을 비교해 보자. 원본은 book-001,SQL 뒤에 줄바꿈이 있고 변경본은 책 이름 뒤에 2가 추가된다. 코드는 파일을 열지 않고 해당 내용의 메모리 바이트열을 입력한다. Python의 b 접두사는 바이트열, \n은 줄바꿈을 나타낸다. 함수를 가져오는 import, 이름에 값을 붙이는 =, 함수를 정의하는 def를 따라 입력과 계산을 구별하면 된다.

    3.1 SHA-256 비교 코드

    import hashlib
original = b"book-001,SQL\n"
copy = b"book-001,SQL\n"
changed = b"book-001,SQL 2\n"
def digest(data):
    return hashlib.sha256(data).hexdigest()
print("same:", digest(original) == digest(copy))
print("changed:", digest(original) == digest(changed))
print("hex length:", len(digest(original)))

    digest(data)는 전달받은 바이트의 SHA-256을 계산한 뒤 hexdigest()로 16진수 문자열을 반환한다. ==는 값의 같음을 검사한다. 첫 줄의 비교 대상은 원본과 복사본이고 다음 줄은 원본과 변경본이다. len은 반환된 문자열 길이를 센다. 같은 함수를 세 입력에 적용하므로 비교 조건이 맞춰진다.[4]

    3.2 실행 결과

    same: True
changed: False
hex length: 64

    Python 3.11.15 표준 라이브러리로 실행하면 동일 복사본은 True, 이번 변경본은 False가 나온다. 마지막 64는 입력 길이가 아니라 16진수 해시의 길이다. 이 실행은 이 세 바이트열의 결과를 확인한 것이며 서로 다른 모든 입력에서 충돌이 없음을 증명한 것은 아니다.

    동일한 비교를 실제 파일에 적용하려면 바이트를 그대로 읽는다. 텍스트 모드의 줄바꿈 변환이나 일부 구간만 읽는 처리로 입력이 달라지지 않게 해야 한다. 값이 달라졌다는 결과만으로 수정 위치까지 알 수는 없다. 어느 글자가 바뀌었는지 알아내려면 원본과 변경본을 직접 비교하는 도구가 추가로 필요하다.

    4. 기준값과 활용 조건

    4.1 기준값의 신뢰

    직접 만든 원본을 가진 실험과 달리 다운로드에서는 원본 파일을 갖고 있지 않을 수 있다. 이때 배포자의 기준 해시와 받은 파일의 계산값을 비교한다. 데이터가 기대한 상태에서 바뀌지 않았는지 확인하는 것이 무결성 확인이다. 아래 그림에서 파일을 계산하는 경로와 기준값의 출처를 확인하는 경로를 나눈 이유가 여기에 있다.

    파일과 해시 문자열을 같은 공격자가 모두 바꿀 수 있다면 바뀐 파일의 해시를 다시 적어 비교를 통과시킬 수 있다. 긴 문자열만 첨부되어 있다고 출처가 검증되는 것은 아니다. 공식 배포 경로를 확인하거나 신뢰할 수 있는 배포자 키로 서명된 해시 목록을 검증해야 한다. 전자서명은 서명자의 키로 만든 정보를 검증하는 방식이며 검증에 사용하는 키가 실제 배포자의 것인지도 확인해야 한다.

    Ubuntu의 공식 안내는 해시 목록의 서명 확인과 ISO 파일의 SHA-256 비교를 별도 단계로 제시한다. 앞 단계는 기준을 믿을 근거를 마련하고, 뒤 단계는 받은 파일이 그 기준에 맞는지 확인한다. 파일 비교가 성공했다는 이유로 서명 검증까지 수행했다고 말할 수 없는 까닭이다.[5]

    4.2 용도와 한계

    검색용 해싱에서는 키, 즉 찾으려는 자료를 구별하는 값을 해시로 계산해 후보 저장 위치를 고른다. 예를 들어 사물함 목록에서 이름 ‘민서’와 ‘지훈’이 같은 후보 칸에 배정되었다면, 그 칸의 목록에서 실제 이름을 비교해 맞는 기록을 찾을 수 있다. 이처럼 한 칸에 여러 항목을 두는 충돌 처리 방식이 있다. 후보를 좁히는 이득이 있지만 충돌이 많아지면 추가 비교가 늘고, 항목 수가 늘면 저장 공간을 확장하고 위치를 다시 계산하는 비용도 든다. 충돌을 처리해 정답을 찾는 문제는 공격자가 같은 암호학적 해시를 만들기 어렵게 하는 문제와 다르다.

    파일 해시는 큰 자료의 비교값을 작게 전달하는 데 유리하지만 계산하려면 입력 바이트를 읽어야 한다. 비밀번호 저장에서는 유출된 값에 후보를 계속 대입하는 비용을 높이는 것이 중요하다. 그래서 빠른 SHA-256 한 번만으로 안전한 비밀번호 저장을 구성하지 않고 비용을 조정할 수 있는 전용 방식을 사용한다. 파일 해시와 비밀번호 해싱의 목적 차이[6]

    해시 일치는 정해진 입력에 대한 비교 결과다. 배포자가 믿을 만한지, 내용에 취약점이 있는지, 실행해도 무해한지까지 자동 판정하지 않는다. 파일 확인·검색·비밀번호 저장은 모두 해싱을 쓰지만 필요한 속도와 보안 조건이 다르므로 목적부터 정하고 함수를 선택해야 한다.
