    1. 사용자 인터페이스

    신청 화면이 보기 좋은데도 사용자가 접수를 끝내지 못한다면 무엇부터 바꿔야 할까? “내용 확인”을 누른 사람이 이미 신청이 끝났다고 믿는다면 버튼의 색보다 확인과 확정의 차이를 먼저 드러내야 한다. 사용자 인터페이스(UI)는 사람이 시스템에 의사를 전달하고 결과를 받는 접점이다. 글·메뉴·버튼·입력칸뿐 아니라 선택 뒤 어떤 반응이 오는지도 포함한다.

    사용자 인터페이스 설계는 사용자가 하려는 일을 정보의 배치와 조작의 흐름으로 옮기는 일이다. 신청이라면 수업 찾기, 자리 확인, 정보 입력, 최종 확정, 결과 확인이 이어져야 한다. 각 화면을 따로 예쁘게 만들어도 다음 행동이나 성공 여부를 알 수 없으면 작업은 끊긴다. 화면 안의 구성과 화면 사이의 연결을 함께 정하는 이유다.

    서비스를 이용하며 느끼는 인식과 경험의 더 넓은 범위를 사용자 경험(UX)이라고 한다. 접수 화면은 쉬웠지만 이후 안내가 오지 않아 수업에 참석하지 못했다면 화면 밖의 과정까지 살펴야 한다. UI는 UX에 영향을 주는 중요한 부분이지만 모든 업무 문제를 화면 배치만으로 해결할 수 있는 것은 아니다.

    2. 사용자와 이용 조건

    2.1 작업과 화면 상태

    “누구나 편리하게”라는 목표만으로는 어떤 화면을 만들지 판단하기 어렵다. 처음 방문한 신청자가 휴대전화로 수업을 고르는 상황과, 담당자가 키보드로 신청 목록을 반복 검토하는 상황은 필요한 정보와 조작이 다르다. 사용자, 끝내려는 작업, 이용 조건을 함께 정해야 설계의 비교 기준이 생긴다.

    작업을 입력·선택·결과로 풀어 보면 누락된 상태를 찾기 쉽다. 신청자는 수업을 선택하고 연락처를 입력한다. 시스템은 입력 오류와 접수 결과를 알려 준다. “마감 수업은 신청할 수 없다”는 요구는 목록의 마감 표시만이 아니라 최종 접수 실패 안내에도 연결된다. 입력하는 동안 다른 신청으로 자리가 소진될 수 있기 때문이다.

    내용이 없는 빈 상태, 응답을 기다리는 로딩 상태, 처리 성공 상태, 수정이 필요한 오류 상태를 구별한다. 빈 신청 목록에는 기록이 없다는 사실과 수업을 찾는 길이 필요하고, 잘못된 입력에는 수정할 항목이 필요하다. 응답이 늦어 아직 접수 여부를 모르는 상태는 성공도 실패도 아니다. 확인 중이라는 안내와 결과를 다시 확인할 방법을 정하면 사용자가 같은 신청을 무작정 반복할 가능성을 줄일 수 있다.

    2.2 일관성과 접근성

    같은 행동을 화면마다 “접수”, “등록”, “예약”으로 바꾸어 부르면 사용자는 서로 다른 기능으로 이해할 수 있다. 프로젝트가 지킬 공통 규칙인 UI 표준과 적용을 돕는 설명인 UI 지침을 마련해 용어·버튼·오류 표시를 맞춘다. 조직마다 명칭의 범위는 다르므로 필수 규칙, 권고, 예외 승인 절차를 문서에 구별해 두는 것이 중요하다.

    접근성은 다양한 감각·운동·인지 조건의 사람이 정보와 기능을 이용할 수 있는 성질이다. W3C의 WCAG는 웹 콘텐츠의 접근성을 확인할 수 있는 성공 기준을 제공한다. 미적 취향을 정하는 스타일 안내와는 목적이 다르다.[1]

    먼저 마우스 없이 수업 선택부터 확정까지 진행해 본다. 키보드 기준 2.1.1은 개별 키 입력의 특정 타이밍 없이 기능을 키보드 인터페이스로 조작할 수 있게 하는 방향이다. 자유곡선 그리기처럼 입력 경로 자체가 기능에 본질적인 경우에는 예외가 있지만, 수업 선택은 경로가 아니라 선택한 항목이 결과다. 원래 마우스로 만들었다는 이유만으로 키보드 대안을 생략할 수는 없다.

    다음은 초점, 곧 현재 키보드 조작 대상의 표시다. Tab으로 이동할 때 어느 버튼에 있는지 보이는지(2.4.7), 이동 순서가 화면의 의미와 조작을 유지하는지(2.4.3)를 확인한다. 수업 항목을 고른 다음 관련 확인 버튼으로 이동해야 하는 흐름이라면, 뜻과 무관하게 화면 여러 곳을 오가는 순서는 이해를 방해할 수 있다.

    이메일 오류도 사용자의 다음 행동에서 생각한다. 붉은 테두리만 두면 색을 구별하기 어려운 사람은 무엇이 달라졌는지 모를 수 있으므로 색 외 단서를 둔다(1.4.1). 시스템이 입력 오류를 자동 검출했다면 잘못된 항목을 식별하고 오류 내용을 글로 설명한다(3.3.1). 이런 조건들을 일부 반영한 것과 서비스 전체의 WCAG 적합성은 별개다. 적용 버전과 목표 수준, 검사할 화면·상태를 정해 전체 절차를 검토해야 한다.

    3. 신청 흐름과 화면 명세

    3.1 메뉴와 화면 이동

    메뉴 구조는 기능과 정보를 찾아갈 분류이고, 화면 흐름은 행동과 처리 결과에 따른 진행이다. “수업 찾기”, “내 신청”, “이용 안내”라는 메뉴는 목적지를 알려 준다. 그중 신청이라는 작업은 아래처럼 입력·수정·확정을 거쳐야 한다. 여러 입력칸과 선택 항목을 한 작업의 양식으로 묶은 것을 폼이라고 한다. 내부 부서명보다 사용자가 달성하려는 일에 맞춰 이름을 붙이면 찾는 부담을 줄일 수 있다.

    입력이 유효하면 확인 화면으로 가지만, 이것만으로 접수가 확정되지는 않는다. “내용 확인”은 입력 내용을 검토하는 단계이고 “신청 확정”은 실제 접수를 요청하는 행동이다. 수정할 때는 유효한 값을 유지한 폼으로 돌아가고, 최종 접수에서 마감되면 다른 수업을 찾게 한다. 결과가 미확정인 경우도 별도로 표시한다. 이 세 갈래를 구별하면 완료 화면을 언제 보여 줄지 개발자와 검토자가 같은 기준으로 읽을 수 있다.

    기능 묶음을 담당하는 부분을 하위 시스템이라고 한다. 외부 신청 화면과 내부 관리 화면이 나뉘어 있어도 같은 신청 상태를 서로 모순되게 표시해서는 안 된다. 신청자에게 보여 줄 접수 결과와 담당자에게 필요한 내부 메모는 구별하고, 내부 기능의 접근 통제는 단순히 메뉴를 숨기는 방식에만 맡기지 않는다.

    3.2 입력과 피드백

    폼은 한 작업에 필요한 입력과 선택을 묶은 양식이다. 많은 항목을 받을수록 좋은 것이 아니다. 신청에 필요하지 않은 정보까지 요구하면 사용자의 부담과 관리할 정보가 함께 늘어난다. W3C의 폼 지침은 필요한 정보만 묻는 간단한 양식과 명확한 이름표·지침·결과 안내를 강조한다.[2]

    입력칸의 이름표인 레이블은 “연락받을 이메일”처럼 용도를 드러내고 해당 입력칸과 연결한다. 입력을 시작하면 사라지는 예시 문구는 레이블을 대신하기 어렵다. 필수 여부와 형식 조건은 입력 전에 알 수 있게 두고, 관련 선택지는 같은 질문 아래 묶는다. 안내를 찾기 위해 다른 화면을 오가게 하지 않는 것이 핵심이다.

    피드백은 입력이나 행동에 대한 시스템의 반응이다. “처리 실패”만 알리는 대신 수정할 항목과 방법을 알려 주고, 문제가 없는 다른 값은 가능한 한 남긴다. 완료 화면에는 확정된 결과와 다음 행동을 제시한다. 화면 검사는 입력을 쉽게 돕지만 요청의 신뢰성을 보장하지 않는다. 서버에서도 값의 형식과 업무상 의미를 검증해야 한다.

    3.3 와이어프레임과 스토리보드

    와이어프레임은 화면의 배치와 정보 우선순위를 단순하게 표현한 설계도다. 장식보다 필요한 항목과 읽는 순서를 먼저 검토한다. 아래 신청 폼에서는 선택한 수업을 확인한 뒤 이름과 연락처를 입력하고 내용을 확인하도록 배치했다. 오류 문구의 위치도 입력칸 곁에 두어 무엇을 고칠지 연결한다.

    오류 예문은 언제나 노출하는 문구가 아니라, 이메일이 비어 있는데 내용 확인을 요청했을 때처럼 조건에 따라 표시할 안내다. 이런 조건과 동작을 적지 않은 그림만 전달하면 사람마다 빈칸 처리나 버튼 결과를 다르게 구현할 수 있다.

    스토리보드는 화면 그림에 번호·목적·표시 조건·입력·행동·이동 규칙을 붙여 동작을 명세하는 자료다. 신청 폼을 F1, 확인 화면을 C1, 완료 화면을 D1이라고 부르면 “F1에서 유효한 입력으로 내용 확인 → C1”, “C1에서 수정 → 값을 유지한 F1”, “C1에서 확정 요청 성공 → D1”로 연결할 수 있다. 번호는 설계 대화의 식별자이지 사용자에게 외우게 하는 용어가 아니다.

    “신청이 확정되면 접수번호와 수업명을 보여 준다”는 요구에 R1이라는 번호를 붙이고 완료 화면 D1에 연결해 두면, 요구 변경 때 수정할 화면과 확인 항목을 찾기 쉽다. 화면 문구와 흐름을 서로 다른 자료에서 관리하더라도 승인 버전을 맞춘다. 아직 결정되지 않은 정책을 보기 좋은 화면으로 덮어 두기보다 결정할 질문으로 드러내야 구현자의 추측을 줄일 수 있다.

    4. 시제품과 평가

    프로토타입은 설계 대안을 시험하는 시제품이다. 종이 화면을 차례로 보여 주거나 클릭 경로를 연결하거나 필요한 동작만 구현할 수 있다. 목적은 완제품처럼 보이게 하는 것보다 큰 구현 비용을 들이기 전에 잘못 이해한 부분을 찾는 데 있다.[3]

    4.1 작업 성공과 사용성

    메뉴 이름을 알아보는지 확인하려면 스케치도 도움이 된다. 반면 키보드 초점이나 좁은 화면의 읽기 흐름을 검사하려면 해당 동작을 표현한 시제품이 필요하다. 질문을 먼저 정하면 불필요한 구현은 줄이면서도 검토에 필요한 현실성은 확보할 수 있다.

    사용성은 정해진 사용자와 사용 상황에서 목표를 정확하고 완전하게 달성하는 효과성, 그 결과에 비해 들인 시간·노력인 효율성, 이용 과정과 결과에 대한 만족을 함께 살핀다.[4] 처음 온 신청자가 휴대전화로 수업 접수를 끝내는 작업이라면, 성공 여부뿐 아니라 되돌아감·오류·소요 시간과 느낀 어려움을 함께 관찰할 수 있다.

    참여자에게 “원하는 수업에 신청하고 접수 결과를 확인해 주세요”라는 작업을 제시하고 성공 조건을 미리 정한다. 진행자가 곧바로 길을 알려 주면 실제 사용의 어려움이 가려질 수 있다. 행동과 발언을 먼저 기록하고 그 원인에 대한 검토자의 해석은 구별한다.

    “내용 확인” 뒤 참여자가 작업을 끝냈다고 말한다면, 확인 화면의 제목을 “신청 내용 검토”로 분명히 하고 확정 행동의 위치와 단계 안내를 함께 검토할 수 있다. 수정본에서는 설명 없이 최종 확정까지 진행하고 접수 결과를 식별하는지를 다시 관찰한다. 이 관찰 기준은 개선 여부를 판정하는 방법이지 이미 혼동이 감소했다는 측정 결과가 아니다. 실제 서비스의 보안·성능·접근성은 구현 뒤에도 검사해야 한다.

    4.2 감성공학과 선호

    작업을 끝낼 수 있다는 것과 화면이 차분하거나 친근하게 느껴진다는 것은 다른 질문이다. 감성공학은 사용자의 느낌과 인상을 조사해 설계 요소와 연결하려는 접근이다. 디자이너 한 사람의 취향을 사용자 전체의 선호로 대신하지 않고 반응을 관찰한다.[5]

    같은 기능과 안내를 유지한 두 화면에서 정보 밀도나 글자 간격을 달리하고, 대상 사용자에게 “차분하다–산만하다” 같은 표현으로 평가하게 할 수 있다. 어떤 요소를 달리했는지 기록해야 인상과 설계 사이 관계를 해석할 수 있다. 색·문구·배치를 한꺼번에 바꾸면 무엇이 차이를 만들었는지 구별하기 어렵다.

    선호가 높은 색이라도 글을 구별하기 어렵다면 접근성 문제가 남고, 차분한 배치라도 확정 버튼을 못 찾으면 작업 성공에 문제가 남는다. 사용자 집단과 문화·상황에 따라서도 인상은 달라진다. 감성 평가는 사용성·접근성을 대체하지 않고 서로 다른 질문에 대한 판단을 보완한다.

    5. 활용과 한계

    이 설계 방식은 신청·구매처럼 가끔 하는 작업과 내부 조회처럼 반복하는 작업 모두에 쓰인다. 요구, 화면 상태, 이동 규칙을 먼저 연결하면 개발자에게 넘길 모호함이 줄고, 시제품을 이용하면 구현을 크게 바꾸기 전에 이해 문제를 찾을 수 있다.

    대신 명세와 시제품을 만드는 시간, 사용자 검토, 구현과 문서의 변경을 맞추는 비용이 든다. 화면만 바꿔서 잘못된 접수 정책이나 서버의 동시 처리 결함을 고칠 수는 없다. 사용자가 이해하는 결과와 시스템이 실제 확정한 결과를 일치시키는 일이 설계와 구현 사이의 핵심 연결이다.
