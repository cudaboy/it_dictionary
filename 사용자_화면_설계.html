    작업을 담는 화면

    온라인으로 체험 수업을 신청하려는 사람에게는 예쁜 첫 화면보다 먼저 해결해야 할 질문이 있다. 원하는 수업을 어디서 찾는지, 신청할 자리가 있는지, 어떤 정보를 입력해야 하는지, 마지막 버튼을 누른 뒤 접수가 끝났는지를 알아야 한다. 신청 기능 자체가 있어도 이런 단서가 없으면 사용자는 작업을 중단하거나 같은 신청을 다시 보낼 수 있다.

    사용자 인터페이스(UI, User Interface)는 사람이 시스템에 의사를 전달하고 그 결과를 받아 보는 접점이다. 화면의 글·메뉴·버튼·입력칸뿐 아니라 선택 뒤의 반응도 포함한다. 화면 설계는 사용자의 목적을 이 접점의 구조와 동작으로 바꾸는 일이다. 무엇을 먼저 보여 주고, 어떤 선택을 받으며, 성공하거나 실패했을 때 무엇을 알려 줄지를 정한다. 화면 하나의 모양과 여러 화면 사이의 연결을 함께 다룬다.

    UI를 이용하면서 사람이 느끼고 경험하는 더 넓은 범위를 사용자 경험(UX, User Experience)이라고 한다. 신청 화면은 이해하기 쉬운데 완료 뒤 안내를 받지 못한다면 경험 전체는 좋지 않을 수 있다. 화면 설계는 사용자 경험을 만드는 중요한 부분이지만 서비스의 모든 문제를 화면 배치로 해결할 수는 없다. 이 문서에서는 가상의 체험 교실을 예로 들되, 조회·신청·설정 등 여러 작업에 공통되는 설계 과정을 설명한다. 화면과 조건은 교육용이며 실제 서비스의 복제가 아니다.

    사용자와 작업

    먼저 누가 어떤 상황에서 무엇을 끝내려 하는지 확인한다. 처음 신청하는 사람과 매일 신청 목록을 확인하는 담당자는 필요한 정보와 익숙한 용어가 다르다. 휴대전화로 잠깐 접속하는 사람과 키보드로 여러 건을 검토하는 사람도 조작 조건이 다르다. “누구나 편하게 쓴다”보다 “처음 방문한 신청자가 수업을 골라 접수 결과를 확인한다”처럼 작업을 구체화해야 화면을 검토할 수 있다.

    요구사항을 화면과 연결할 때에는 입력·선택·결과를 나누어 본다. 신청자는 수업을 고르고 필요한 정보를 제공한다. 시스템은 입력에 문제가 있는지 알려 주고, 접수 결과를 제시한다. “마감된 수업에는 신청할 수 없다”는 업무 조건이 있다면 목록의 마감 표시, 상세 화면의 설명, 최종 접수가 실패했을 때의 안내에 모두 영향을 준다. 기능의 근거와 규칙을 확인하는 방법은 요구사항과 분석 모델에서 이어진다.

    화면을 열었을 때 아무 항목도 없는 빈 상태, 결과를 기다리는 로딩 상태, 처리가 끝난 성공 상태, 사용자가 수정하거나 다시 시도해야 하는 오류 상태도 설계 대상이다. 정상 결과만 그려 놓으면 개발 과정에서 안내가 제각각 만들어지기 쉽다. 빈 목록에는 “신청 내역이 없습니다”와 가능한 다음 행동을, 오류에는 원인과 복구 방법을 적어 둔다. 아직 접수 결과를 알 수 없는 상태를 실패나 성공으로 단정하지 않는 것도 중요하다.

    표준과 지침

    여러 화면에서 같은 일이 같은 방식으로 동작하면 사용자는 한 번 배운 조작을 다시 쓸 수 있다. 이를 위해 적용할 규칙을 정한다. UI 표준은 프로젝트에서 공통으로 지키기로 정한 기준이고, UI 지침은 상황에 맞게 그 기준을 적용하도록 돕는 설명이다. 예를 들어 버튼 이름과 오류 표시 방식을 통일하는 규칙, 긴 입력 양식을 나누는 권고를 둘 수 있다. 문서마다 두 말을 쓰는 범위가 다를 수 있으므로 필수 규칙과 권고, 예외 승인 방식을 명확하게 구분한다.

    외부 표준을 참고할 때에는 무엇에 관한 표준인지도 알아야 한다. W3C의 WCAG(Web Content Accessibility Guidelines)는 장애가 있는 사람도 웹 콘텐츠를 이용할 수 있도록 하는 접근성 기준이다. 여기서 접근성은 다양한 감각·운동·인지 조건에서도 정보를 이해하고 기능을 조작할 수 있는 성질을 말한다. WCAG는 화면의 모든 미적 선택을 정하는 스타일 설명서가 아니라 확인 가능한 성공 기준을 제공한다.[1]

    체험 수업 신청 화면을 검토한다면 마우스를 내려놓고 수업 선택부터 신청 확정까지 진행해 볼 수 있다. 버튼이 키보드로 눌리는지만 볼 것이 아니라, 특정 순간에 키를 맞춰 누르거나 정해진 속도로 연속 입력해야만 작업이 끝나는지도 살핀다. 이런 시간 맞추기를 신청 기능의 전제로 두지 않는 것이 WCAG 2.2의 키보드 기준(2.1.1)을 이 사례에 적용하는 방향이다. 자유곡선을 그리는 작업은 선이 지나간 경로 자체가 결과의 일부인 반면, 수업 선택은 선택된 항목이 결과다. 따라서 경로 입력이 기능에 본질적인 경우의 예외를 모든 포인터 조작에 넓혀 적용해서는 안 된다. 문자 입력이나 수업 선택에 마우스를 썼다는 이유만으로 예외가 되지도 않는다. 다음으로 Tab 키를 눌렀을 때 현재 조작 대상인 초점을 눈으로 찾을 수 있는지 확인한다(2.4.7). 예를 들어 항목을 고른 다음 그 항목의 확인 버튼으로 이동하는 순서가 작업 이해에 중요하다면, 화면의 의미와 실제 조작을 유지하는 탐색 순서가 필요하다(2.4.3). 오류 안내도 신청자의 다음 행동에서 출발해 설계한다. 이메일 입력칸의 붉은 테두리만 보고 수정 이유를 추측하게 하지 말고, 색을 보지 않아도 알 수 있는 단서를 둔다(1.4.1). 시스템이 입력 오류를 자동 검출한 상황이라면 어느 항목에서 무엇이 잘못됐는지를 글로 알려 주어야 한다(3.3.1). 이는 모든 업무 오류를 자동으로 찾아낸다는 보장이 아니다. 여기서는 검출된 이메일 오류 옆에 설명을 놓아 수정 위치와 이유를 연결하는 사례를 든 것이다. 이 문단은 신청 작업에 대한 독자 해설이며, 표준의 정확한 적용 범위는 원문에서 확인한다.[1]

    실제 적용 문서에는 참고한 표준의 버전과 목표 수준을 적고, 어떤 화면과 상태를 검사할지 정한다. 예시 몇 개를 반영했다고 서비스 전체가 표준에 적합하다고 선언할 수는 없다. 프로젝트의 공통 버튼·입력칸 등 반복 요소를 모아 관리하면 일관성을 유지하는 데 도움이 되지만, 그 요소를 조합한 전체 작업의 이해 가능성도 따로 살펴야 한다.

    메뉴와 화면 흐름

    메뉴 구조는 사용자가 기능과 정보를 찾아가는 분류다. 개발팀의 담당 부서명이나 내부 처리 단계보다 사용자의 목적에 맞는 이름을 쓴다. 체험 교실이라면 “수업 찾기”, “내 신청”, “이용 안내”가 출발점이 될 수 있다. 같은 뜻을 “접수”, “예약”, “등록”으로 번갈아 부르면 서로 다른 기능으로 오해할 수 있으므로 업무상 차이가 없다면 이름을 통일한다.

    화면 흐름은 사용자의 행동과 시스템 결과에 따라 어느 화면이나 상태로 이어지는지를 표현한다. 메뉴는 찾아갈 장소를 보여 주고, 흐름은 작업의 진행을 보여 준다는 차이가 있다. 신청 과정에서는 앞으로 진행하는 길뿐 아니라 뒤로 가기, 수정, 취소, 실패 뒤의 재시도 경로도 함께 정한다. 사용자가 이전 화면으로 돌아갔을 때 입력한 값이 남는지도 이 단계의 결정이다.

    이 흐름에서는 폼 입력이 맞다는 것과 실제 신청이 확정되었다는 것을 구분한다. 입력 중에는 자리가 있었더라도 마지막 접수 때 상황이 바뀔 수 있기 때문이다. 화면의 “확인” 버튼과 “신청 확정” 버튼도 결과가 다르므로 서로 다른 이름을 붙였다. 버튼 글은 사용자가 누른 뒤 생길 일을 예측하는 단서다.

    기능 묶음을 담당하는 부분을 하위 시스템이라고 한다. 외부 신청 화면과 내부 접수 관리 화면이 따로 있다면 같은 신청 상태를 서로 다르게 해석하지 않도록 연결 규칙을 정한다. 신청자에게는 “접수 완료”, 담당자에게는 그에 대응하는 신청 건과 처리 상태가 보이게 한다. 담당자만 필요한 내부 메모를 외부 화면에 그대로 노출하지 않는 것처럼, 대상별로 보여 줄 정보와 가능한 행동도 나눈다. 내부 화면이라는 이유로 접근 통제를 화면 숨기기에만 맡겨서는 안 된다.

    입력과 피드백

    폼은 한 작업을 위해 관련 입력칸과 선택 항목을 모아 놓은 양식이다. 종이 신청서처럼 항목을 많이 놓는 것이 목적이 아니라, 작업에 필요한 정보를 정확히 받는 것이 목적이다. W3C의 폼 안내도 불필요하거나 지나친 정보를 요구하지 말고 짧고 단순한 양식을 만들도록 권한다. 이름표, 입력 방법, 관련 항목의 묶음, 결과 알림이 함께 있어야 사용자가 양식을 이해할 수 있다.[2]

    입력칸의 의미를 나타내는 글을 레이블이라고 한다. “연락받을 이메일”처럼 용도를 드러내고 입력칸과 연결한다. 입력을 시작하면 사라지는 예시 문구만으로 이름표를 대신하면 무엇을 적던 칸인지 다시 확인하기 어렵다. 필수 항목은 입력 전에 알리고, 형식 조건이나 예시는 해당 항목 곁에 둔다. 관련된 선택 항목은 하나의 질문 아래 묶어 읽을 수 있게 한다.

    이 그림처럼 배치와 정보의 우선순위를 단순하게 그린 것을 와이어프레임이라고 한다. 색이나 장식보다 필요한 항목이 있는지, 순서가 자연스러운지 검토하는 데 쓴다. 위 예에서는 오류 안내가 어느 항목에 붙는지까지 정했지만, 모든 오류를 항상 보여 주는 뜻은 아니다. 미입력인 채 확인을 요청하는 등 안내가 필요한 조건을 함께 명시해야 한다.

    입력 뒤 시스템이 보내는 반응을 피드백이라고 한다. 잘못된 항목을 알려 줄 때는 “실패했습니다”만 표시하기보다 무엇을 고쳐야 하는지 안내하고, 유효한 다른 입력은 가능한 한 유지한다. 완료 화면에는 결과와 이후 할 일을 보여 준다. 다만 화면의 입력 안내와 검사는 사용 편의를 위한 부분이다. 서버에서 값의 형식과 의미를 확인하는 구현은 입력값 검증 (이번 검토본 미수록)에서 다루며, 화면을 거쳤다는 사실로 유효한 요청이라고 믿어서는 안 된다.

    스토리보드

    그림만 전달하면 개발자와 검토자가 “이 버튼은 무엇을 하는가”, “어느 조건에 이 문구가 뜨는가”를 다시 추측해야 한다. 스토리보드는 화면의 모양에 화면 번호, 목적, 표시 조건, 입력 항목, 행동과 이동 규칙 등을 붙여 전체 동작을 설명하는 설계 자료다. 와이어프레임이 화면의 뼈대를 보여 준다면 스토리보드는 그 화면을 언제 어떻게 쓰는지까지 설명한다. 조직마다 서식은 달라도 같은 행동을 같은 결과로 해석할 수 있어야 한다.

    신청 폼을 F1, 확인 화면을 C1, 완료 화면을 D1이라고 부르면 “F1에서 내용 확인을 선택하고 입력에 문제가 없으면 C1로 간다”처럼 연결을 정확히 적을 수 있다. C1에는 선택한 수업과 입력 요약을 보여 주며 수정 버튼은 값을 유지한 F1로 돌아간다고 기록한다. D1은 실제 접수가 성공했다는 결과를 받은 때만 보여 준다. 화면 번호는 이런 대화와 변경 검토를 위한 식별자이지 사용자에게 외우게 할 이름이 아니다.

    스토리보드에는 화면과 관련된 요구 번호도 연결한다. “접수번호와 수업명 표시” 요구가 바뀌면 완료 화면 설명과 확인 항목을 함께 찾을 수 있다. 화면 문구·제약·흐름을 서로 다른 문서에 적더라도 승인한 버전이 맞아야 한다. 정해지지 않은 규칙은 임의의 동작으로 숨기지 말고 결정할 질문으로 남긴다.

    프로토타입과 검토

    프로토타입은 설계 생각을 시험해 보기 위해 만든 시제품이다. 종이 화면을 바꿔 보여 주는 방식, 클릭하면 다음 화면으로 넘어가는 모형, 일부 동작을 코드로 만든 시제품이 모두 가능하다. GOV.UK의 설계 지침은 이런 시제품으로 여러 대안을 빠르게 탐색하고, 본격 구현에 앞서 사용자와 팀의 이해를 확인하도록 설명한다.[3]

    얼마나 실제처럼 만들지는 확인할 질문에 맞춘다. 메뉴 이름을 이해하는지 보려면 간단한 스케치로 시작할 수 있다. 입력 순서나 키보드 조작, 좁은 화면에서의 읽기와 같은 상호작용을 보려면 그 동작을 표현할 수 있는 시제품이 필요하다. 클릭 경로를 연결하는 설계 도구는 화면 이동과 반복 요소의 공유를 돕지만, 도구 선택이나 화면의 정교함 자체가 검토의 성공 기준은 아니다.

    사용성은 특정 사용자가 특정 사용 상황에서 목표를 얼마나 정확하고 완전하게 달성하는지(효과성), 그 결과에 비해 시간과 노력을 얼마나 들이는지(효율성), 사용 과정과 결과에 얼마나 만족하는지(만족)를 함께 보는 개념이다.[5] 이 신청 화면에서는 처음 방문한 신청자가 휴대전화로 수업을 골라 접수 결과를 확인하는 상황처럼 사용자·목표·사용 조건을 정하고, 접수 완료 여부뿐 아니라 걸린 시간·되돌림·오류와 사용 후 느낀 어려움·만족도 함께 살핀다. 사용성은 감성 선호나 접근성과 겹치는 부분이 있지만 같은 개념은 아니다. 화면이 마음에 드는지, 작업을 효과적이고 효율적으로 끝내며 만족하는지, 장애가 있는 사람도 이용할 수 있는지는 연결해서 살피되 구별할 질문이다.

    검토에서는 “이 화면이 마음에 드나요?”만 묻지 않고 “원하는 수업에 신청하고 접수가 끝났는지 확인해 주세요”처럼 작업을 제시한다. 먼저 성공 조건과 관찰할 내용을 정하고, 참여자가 어디서 멈추고 어떤 이름을 오해하는지 기록한다. 진행자가 바로 답을 알려 주면 혼자 사용할 때의 어려움을 놓칠 수 있다. 사용자의 행동과 발언, 검토자의 해석을 나누어 기록한 뒤 UI·UX 담당자와 개발자가 수정 이유를 검토한다.

    예를 들어 참여자가 “내용 확인”을 누른 뒤 신청이 끝났다고 생각했다면 버튼 문구뿐 아니라 다음 화면의 제목, 확정 버튼의 위치, 단계 안내를 함께 보아야 한다. 수정본으로 같은 작업을 다시 확인하여 혼동이 줄었는지 판단한다. 이는 가능한 검토 상황을 설명한 것이며 실제 사용자 시험 결과를 보고하는 사례는 아니다. 프로토타입으로 이해하기 쉬운 흐름을 찾았더라도 실제 서비스의 보안·성능·접근성 검사는 구현 후 따로 필요하다.

    느낌과 감성공학

    같은 정보를 제공하는 화면도 복잡하거나 차분하게 느껴질 수 있다. 감성공학은 이런 사용자의 느낌과 인상을 조사하고 설계 요소와 연결하려는 접근이다. 디자이너 개인의 취향을 곧바로 모든 사용자의 선호로 간주하는 것과 다르다. 일본감성공학회가 발행한 웹 디자인 연구는 사용자의 감성 반응을 측정하여 디자인에 반영하는 모델을 다룬다.[4]

    입문 수준에서는 “어떤 느낌을 주고 싶은가”를 관찰 가능한 비교 질문으로 바꾸는 데서 시작할 수 있다. 같은 기능과 안내 내용을 유지한 두 화면을 준비하고, 대상 사용자에게 “차분하다–산만하다”, “친근하다–낯설다” 같은 표현이 얼마나 어울리는지 물어보는 식이다. 글자 간격·정보 밀도·색·표현 방식 중 무엇을 달리했는지도 기록해야 느낌과 설계 요소의 관계를 검토할 수 있다. 여러 요소를 동시에 바꾸면 무엇 때문에 평가가 달라졌는지 분리하기 어렵다.

    느낌의 평가는 작업 성공과 구별한다. 차분하다는 평가를 얻었더라도 중요한 버튼을 찾지 못하면 사용성에 문제가 있고, 마음에 드는 색이라도 글을 구별하기 어렵다면 접근성을 해칠 수 있다. 사용 집단과 문화, 작업 상황이 다르면 인상도 달라질 수 있으므로 한 번의 선호 조사로 보편적인 정답을 만들지 않는다. 감성 평가를 작업 관찰과 함께 사용하면 보기 좋은가와 일을 끝낼 수 있는가를 균형 있게 검토할 수 있다.

    설계의 활용과 경계

    화면 설계는 신청·조회·구매처럼 사용자가 직접 작업을 끝내는 서비스뿐 아니라 담당자가 반복 업무를 처리하는 내부 프로그램에도 쓰인다. 요구와 흐름을 먼저 맞추고 시제품으로 확인하면 구현 뒤의 큰 수정을 줄일 수 있다. 대신 문서와 시제품이 실제 구현에서 멀어지지 않도록 변경을 함께 관리해야 하며, 화면만으로 업무 정책이나 서버 처리의 결함을 해결할 수는 없다.

    기본적인 프로그램 역할은 소프트웨어 (이번 검토본 미수록), 값이 유효한지 확인하는 구현은 입력값 검증 (이번 검토본 미수록)으로 연결한다. 여기서는 셸·GUI 조작법, 실제 서비스 복제, 특정 UI 도구의 설치·운용, 장비·배선·운영 상세를 다루지 않는다. 시험 기준의 화면 설계 항목은 학습 범위의 근거이며 이 글의 시제품 설명은 실기 수행 전체를 검증한 결과가 아니다.
