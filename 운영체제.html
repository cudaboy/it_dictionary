    1. 공동 사용의 기반 ↑ 목차

    문서를 편집하면서 음악을 듣고 파일을 내려받을 때, 각각의 프로그램은 같은 컴퓨터의 계산 장치와 메모리, 저장장치를 함께 쓴다. 어느 프로그램에 계산 시간을 줄지, 다른 프로그램의 자료를 함부로 바꿀 수 있는지, 파일을 어느 장치에서 읽을지는 누군가 조정해야 한다. 운영체제는 프로그램이 실행될 기반을 제공하고 이런 자원 사용을 관리하는 시스템 소프트웨어다. CPU는 명령을 계산·실행하는 장치이고, 메모리는 실행 중인 명령과 자료를 두는 작업 공간이며, 저장장치는 전원이 꺼진 뒤에도 보관할 파일을 담는다.

    운영체제 덕분에 문서 편집기는 저장장치의 전기 신호를 직접 다루기보다 ‘이 파일을 열어 달라’고 요청할 수 있다. 동시에 운영체제는 그 요청을 누가 했는지 확인하고, 다른 프로그램이 쓰는 자원과 충돌하지 않도록 처리한다. 프로그램에 공통된 사용 방법을 제공하는 일과 자원을 나누고 보호하는 일이 함께 있는 것이다. 화면의 창이나 바탕화면은 운영체제를 사용하는 한 방식이며, 화면 없이 요청을 처리하는 서버에도 운영체제가 필요하다.

    이 문서는 여러 프로그램이 한 컴퓨터를 공유하는 원리를 다룬다. 뒤의 구현 예는 Linux 계열이며, 모든 운영체제가 같은 명령이나 내부 구조를 쓰는 것은 아니다. 운영체제와 응용프로그램의 분류는 소프트웨어 (이번 검토본 미수록)에서 더 넓게 살펴볼 수 있다.

    2. 응용과 커널 ↑ 목차

    운영체제의 중심에서 자원 접근을 관리하는 부분을 커널이라고 한다. 문서 편집기나 웹 브라우저 같은 응용프로그램은 보통 제한된 실행 영역인 사용자 공간에서 동작한다. 커널은 하드웨어와 메모리 보호 기능을 제어하는 권한을 갖고, 프로그램의 요청을 정해진 입구로 받는다. 이 입구가 시스템 호출이다. 응용프로그램은 흔히 공통 기능을 모아 둔 라이브러리를 거쳐 파일 열기나 읽기 같은 시스템 호출을 사용한다.

    예를 들어 편집기가 문서를 읽을 때는 파일 이름을 전달하고 읽을 권한이 있는지 검사받는다. 커널 안의 파일 처리 기능은 파일의 위치를 찾고 필요한 자료를 돌려준다. 장치 고유의 제어를 맡는 드라이버는 저장장치·네트워크 장치 등과 실제로 통신하는 부분이다. 이렇게 역할을 나누면 응용프로그램마다 모든 장치의 제어 방법을 다시 구현할 필요가 줄어든다. Linux의 VFS는 서로 다른 파일시스템을 공통된 파일 접근 방식으로 연결하는 커널 계층이다.[1]

    ‘Linux’라는 말은 커널을 가리키기도 하고 일상적으로는 이를 사용하는 운영체제 전체를 가리키기도 한다. 실제 사용 가능한 배포판에는 커널 외에도 명령 도구, 라이브러리, 서비스, 설치·갱신 도구 등이 들어간다. GNU 도구와 Linux 커널을 결합한 체계를 GNU/Linux라고 부른다. 따라서 커널 버전만 알아서는 설치된 모든 프로그램이나 배포판의 구성을 알 수 없다.[2]

    3. 실행 시간의 배분 ↑ 목차

    디스크에 저장된 프로그램과 지금 실행 중인 프로그램은 구별해야 한다. 실행 중인 프로그램을 운영체제가 관리하는 단위를 프로세스라고 한다. 프로세스에는 실행에 필요한 메모리와 열린 파일, 실행 주체 등의 정보가 연결된다. 같은 편집기를 두 번 실행하면 같은 프로그램 파일을 사용하면서도 서로 다른 실행 상태를 가질 수 있다. 하나의 프로세스 안에 실행 흐름을 여러 개 둘 수도 있는데, 이 흐름을 스레드라고 한다.

    계산 장치가 한 번에 처리할 수 있는 일은 한정되어 있다. 커널의 스케줄러는 실행할 준비가 된 작업 가운데 다음에 CPU를 사용할 작업을 고른다. 여기서 작업은 Linux에서 스케줄링되는 스레드 같은 실행 단위를 뜻한다. 하나의 논리 CPU에서는 작업들이 시간을 나누어 진행하고, 여러 논리 CPU가 있으면 여러 작업이 실제로 동시에 실행될 수도 있다. 작업을 바꿀 때는 이전 작업의 실행 위치와 상태를 보존하고 다음 작업의 상태를 복원한다. 이런 전환에도 비용이 든다.[3]

    음악 재생과 파일 다운로드를 함께 한다고 가정해 보자. 다운로드 작업이 네트워크 응답을 기다리는 동안에는 계속 계산만 할 이유가 없다. 기다리는 작업 대신 실행할 준비가 된 음악 처리나 다른 작업에 CPU를 줄 수 있다. 준비된 작업이 아주 많아지면 차례를 기다리는 시간이 늘고 반응이 늦어질 수 있다. 이 사례는 스케줄링의 필요성을 설명하는 가정이며, 실제 측정한 실행 순서나 일정한 시간 배분을 뜻하지 않는다.

    운영체제는 여러 작업을 진행시키지만 모든 작업을 무조건 같은 비율로 실행하지는 않는다. 우선순위와 정책, 실행 가능한 CPU, 자원 제한 등이 영향을 준다. ‘프로그램이 켜져 있다’와 ‘지금 CPU에서 실행 중이다’가 다르다는 점을 이해하면, 응답이 느릴 때 계산이 몰린 것인지 다른 자원을 기다리는 것인지 구별할 출발점을 얻는다. 구체적인 상태와 식별자는 프로세스 (이번 검토본 미수록)에서 이어 다룬다.

    4. 메모리의 분리와 공유 ↑ 목차

    여러 프로그램이 같은 메모리 칩을 쓴다고 해서 모든 자료를 서로 자유롭게 읽고 쓸 수 있으면, 편집기의 오류 하나가 다른 프로그램의 내용을 망가뜨릴 수 있다. 일반적인 데스크톱·서버 운영체제는 각 프로세스에 별도의 가상 주소 공간을 제공한다. 주소 공간은 프로그램이 메모리 위치를 번호로 가리킬 수 있는 범위다. 프로그램이 보는 가상 주소와 실제 메모리 위치 사이의 연결을 커널과 하드웨어가 관리한다.

    이 주소 변환과 접근 허가를 돕는 하드웨어를 MMU(메모리 관리 장치)라고 한다. 같은 숫자의 주소라도 프로세스가 다르면 다른 실제 자료를 가리킬 수 있다. 허용되지 않은 위치에 접근하면 정상적인 읽기·쓰기로 처리되지 않고 오류를 일으킬 수 있다. 반대로 협업이 필요하면 운영체제가 허용한 공유 메모리처럼 일부 영역을 함께 쓰게 할 수도 있다. 분리와 공유는 서로 반대되는 우연한 현상이 아니라 통제할 대상이다.[4]

    가상 메모리가 있다고 실제 RAM이 무한해지는 것은 아니다. 운영체제는 필요 없는 캐시를 줄이거나, 구성이 허용하면 일부 자료를 저장장치로 옮겨 RAM을 확보할 수 있다. 이 저장장치 보조 공간을 스왑이라고 한다. 저장장치 접근은 RAM 접근보다 느릴 수 있어 이런 이동이 잦아지면 프로그램 반응이 나빠진다. Linux에서는 메모리를 충분히 확보하지 못할 때 일부 작업을 종료하는 상황도 생길 수 있다. 주소의 분리, 물리 메모리 사용, 스왑의 관계는 가상 메모리 (이번 검토본 미수록)에서 더 자세히 설명한다.

    5. 파일·장치와 실행 권한 ↑ 목차

    입출력(I/O)은 파일에서 자료를 읽거나 화면·네트워크·저장장치로 내보내는 일이다. 파일은 이름으로 자료를 보관하고 찾는 단위이고, 디렉토리는 파일과 하위 디렉토리의 이름을 조직한다. 파일시스템은 이런 이름과 내용, 속성 등을 관리하는 방식이다. 응용프로그램은 공통된 파일 접근 기능을 사용하고, 커널은 실제 파일시스템과 장치에 맞는 처리를 연결한다. 이 구조는 저장장치를 바꾸더라도 응용프로그램의 기본적인 읽기 요청을 유지하는 데 도움이 된다.

    읽고 쓰는 속도 차이를 줄이기 위해 운영체제는 최근 파일 자료를 메모리에 보관하는 캐시를 사용한다. 쓰기 요청도 먼저 메모리에 반영한 뒤 장치로 내보낼 수 있다. 따라서 응용프로그램의 쓰기 함수가 성공했다는 사실과 전원 장애 뒤에도 데이터가 남는다는 보장은 같은 질문이 아니다. 중요한 자료의 보존은 응용프로그램의 저장 방식, 운영체제의 동기화 요청, 저장장치의 동작을 함께 따져야 한다. 파일 이름과 저장 공간 구조는 파일시스템 (이번 검토본 미수록)에서 이어 읽을 수 있다.

    파일을 열 수 있는지는 요청한 프로세스의 신원과 권한에도 달려 있다. Linux에서는 사용자와 그룹을 식별하는 번호 및 파일의 소유권·허가 비트 등이 판단에 쓰인다. 일반 사용자의 프로그램은 자신에게 허용된 범위에서 일하고, 시스템 전체 설정을 바꾸는 작업에는 더 높은 권한이 필요할 수 있다. 관리 계정인 root는 전통적으로 매우 넓은 권한을 가지며, Linux는 특정 특권을 나누어 부여하는 기능도 제공한다. 일부 실행 파일은 특별한 설정에 따라 실행 시 권한이 달라질 수 있으므로 ‘실행한 사람과 항상 똑같은 권한’이라고 단정하면 안 된다.[5]

    이 사용자 권한과 앞서 설명한 사용자 공간·커널 공간은 다른 구분이다. root로 실행한 응용프로그램도 보통 사용자 공간에서 동작하며 필요한 일을 시스템 호출로 요청한다. 권한이 부족하다는 오류를 보았다고 즉시 관리 권한으로 다시 실행하기보다, 어느 파일에 어떤 동작이 필요한지 확인해야 한다. 허용 범위를 좁게 유지하면 실수나 프로그램 결함의 피해도 줄일 수 있다.

    6. 조회로 확인하는 범위 ↑ 목차

    시스템 정보를 읽는 명령도 서로 다른 질문에 답한다. uname -s는 커널 이름, uname -r은 커널 릴리스, id -u는 실행 주체의 유효 사용자 번호를 나타낸다. 이는 명령의 의미를 비교한 것이며 특정 컴퓨터의 관측값이나 실행 절차를 제시한 것이 아니다.[6]

    커널 이름은 운영체제 전체의 구성 목록이 아니며, 사용자 번호는 메모리 보호나 저장장치의 정상 여부를 보여 주지 않는다. 한 가지 조회 결과가 시스템의 모든 상태를 대표하지 않는다는 점이 중요하다. 명령과 인수, 출력의 구별은 셸과 명령행 (이번 검토본 미수록)에서 이어 다룬다.

    7. 활용과 관리의 경계 ↑ 목차

    개인용 컴퓨터에서는 여러 응용프로그램을 편리하게 함께 실행하는 기반이 되고, 서버에서는 여러 사용자의 요청과 서비스를 지속적으로 처리하는 기반이 된다. 응용 개발자는 공통된 파일·통신 기능을 사용하고, 운영 담당자는 프로세스·메모리·입출력·권한이라는 갈래로 문제를 나누어 조사할 수 있다. 운영체제의 역할을 알면 ‘컴퓨터가 느리다’를 CPU 대기, 메모리 부족, 장치 대기처럼 더 구체적인 질문으로 바꿀 수 있다.

    다만 자원 관리 기능이 있어도 자원의 총량은 유한하고, 커널이나 드라이버의 결함은 여러 프로그램에 영향을 줄 수 있다. 파일 접근을 통제한다고 사용자가 승인한 잘못된 변경까지 막는 것은 아니며, 캐시나 메모리 분리가 백업을 대신하지도 않는다. 운영체제 선택과 운영에서는 필요한 장치·응용프로그램과의 호환성, 지원과 갱신, 최소한의 권한, 복구 방법을 함께 준비해야 한다. 이 문서의 목적은 그 판단에 앞서 역할을 구별하는 것이며 커널 설정이나 설치 절차를 대신하는 관리 매뉴얼은 아니다.
