    1. 운영체제와 자원 관리

    문서를 편집하면서 음악을 듣고 파일을 내려받을 수 있는 이유는 무엇일까? 각 프로그램이 컴퓨터의 자원을 제멋대로 독점하지 않도록 나누고, 요청을 처리할 공통 통로가 있기 때문이다. 운영체제는 프로그램이 실행될 기반을 제공하며 계산 장치·메모리·파일 같은 자원을 관리하는 시스템 소프트웨어다.

    CPU는 명령을 계산하고 실행하는 장치이고, 메모리는 실행 중인 명령과 자료의 작업 공간이며, 저장장치는 전원이 꺼진 뒤에도 파일을 보관하는 장치다. 편집기와 재생기는 이런 자원을 함께 쓰지만 서로의 자료를 마음대로 바꾸어서는 안 된다. 운영체제는 누구에게 실행 기회를 줄지, 어느 자료에 접근을 허용할지를 관리한다.

    공통 기능이 없다면 편집기마다 저장장치를 다루는 방식을 구현하고 장치가 바뀔 때마다 수정해야 한다. 운영체제가 파일 열기·읽기 같은 통로를 제공하면 응용프로그램은 작업 목적에 집중할 수 있다. 자원을 편리하게 쓰는 방법과 자원을 나누고 보호하는 규칙이 함께 있는 셈이다. 창과 바탕화면은 이용 방식 중 하나이며 화면 없이 서비스를 제공하는 서버에도 운영체제가 쓰인다. 아래 구현 설명은 Linux 계열을 예로 들며 다른 운영체제의 명령과 내부 구성은 다를 수 있다.

    2. 요청과 보호의 경계

    2.1 응용·시스템 호출·커널

    운영체제의 핵심에서 자원 접근을 관리하는 부분이 커널이다. 편집기나 브라우저 같은 응용프로그램은 보통 제한된 실행 영역인 사용자 공간에서 동작한다. 커널은 하드웨어와 메모리 보호 기능을 제어하며 정해진 입구로 요청을 받는다. 그 입구가 시스템 호출이다. 응용은 흔히 공통 기능을 묶은 라이브러리를 거쳐 파일 열기나 읽기를 요청한다.

    편집기가 문서를 열면 커널은 파일과 접근 권한을 확인하고 내용을 읽을 경로를 찾는다. Linux의 VFS는 여러 파일시스템을 공통 파일 접근 방식에 연결하는 커널 계층이다. 장치마다 다른 제어를 담당하는 소프트웨어인 드라이버가 실제 장치와의 통신을 맡는다. 응용프로그램은 모든 저장장치의 제어 방식을 따로 알 필요가 줄어든다.[1]

    한번 읽은 자료를 메모리에 두고 다시 쓰는 저장 영역을 캐시라고 한다. 아래 그림에서 요청은 편집기에서 장치 쪽으로 내려가지만, 필요한 자료가 캐시에 있으면 장치 읽기를 생략할 수 있다. 응용이 받은 결과는 반대 방향으로 돌아온다.

    응용마다 장치 제어를 반복하지 않아도 된다는 것은 공통 기반에 함께 의존한다는 뜻이기도 하다. 커널이나 그 안에서 동작하는 드라이버에 결함이 생기면 영향이 한 응용에만 머물지 않을 수 있다. 역할 분담의 이점과 보호 경계의 범위를 함께 보는 이유다.

    2.2 커널과 배포판

    Linux는 엄밀하게 커널을 가리키지만 일상에서는 이를 사용하는 운영체제 전체를 뜻하기도 한다. 실제로 설치하는 배포판에는 커널뿐 아니라 라이브러리, 명령 도구, 서비스와 설치·갱신 수단이 함께 들어간다. GNU 도구와 Linux 커널을 결합한 체계를 GNU/Linux라고 부른다.[2]

    따라서 커널 이름이 같아도 사용할 수 있는 프로그램과 기본 설정까지 같은 것은 아니다. 어떤 명령이 없다는 문제는 커널의 이름만으로 해결할 수 없고 배포판과 설치 구성을 확인해야 한다. 커널 정보 조회가 답하는 범위를 구별하면 불필요하게 시스템 전체를 같은 것으로 취급하지 않게 된다.

    3. 실행 자원의 분배

    프로그램들이 요청할 통로를 공유하려면 계산 시간, 메모리, 파일 접근을 각각 조절해야 한다. 프로그램이 느릴 때도 어느 자원에서 멈추었는지에 따라 이유가 달라진다.

    3.1 프로세스·스레드·스케줄링

    저장장치에 놓인 프로그램 파일과 실행 중인 프로그램은 다르다. 실행 중인 프로그램을 운영체제가 관리하는 단위가 프로세스다. 실행에 필요한 메모리, 열린 파일, 신원 등의 정보가 연결된다. 같은 편집기를 여러 번 실행하면 같은 프로그램을 바탕으로도 서로 다른 상태를 가질 수 있다. 한 프로세스 안의 개별 실행 흐름은 스레드라고 한다.

    스케줄러는 실행할 준비가 된 작업 중 다음에 CPU를 쓸 작업을 고른다. Linux에서는 스레드 같은 실행 단위가 대상이다. 하나의 논리 CPU에서는 작업들이 시간을 나누어 쓰고, 여러 논리 CPU에서는 여러 작업이 실제로 동시에 실행될 수 있다. 실행 위치와 상태를 보존했다가 다른 작업의 상태를 복원하는 전환에도 시간이 든다.[3]

    실행은 지금 CPU에서 처리 중인 상태, 준비는 CPU를 받으면 진행할 수 있는 상태, 대기는 입출력 완료 같은 사건을 기다리는 상태로 구별할 수 있다. 음악 처리 작업이 준비되어 있고 다운로드가 네트워크 응답을 기다리는 경우를 따라가 보자.

    1. 다운로드 작업이 실행하다가 아직 도착하지 않은 자료를 기다리며 대기에 들어간다.
    2. 스케줄러가 준비된 음악 처리 작업을 선택하면 CPU는 음악 처리에 쓰인다. 기다리는 다운로드가 그동안 계속 CPU를 차지할 필요는 없다.
    3. 자료가 도착해 기다리던 조건이 충족되면 다운로드 작업은 다시 실행할 준비가 된다.
    4. 스케줄러가 다운로드를 선택한 때 남은 처리를 이어 간다. 자료가 도착한 순간 반드시 즉시 실행된다는 뜻은 아니다.

    이렇게 대기 시간을 다른 일에 활용할 수 있지만 모든 작업이 같은 비율로 실행되는 것은 아니다. 정책·우선순위·실행 가능한 CPU·자원 제한이 영향을 준다. 준비된 작업이 많으면 차례를 기다리는 시간이 늘 수 있다. Linux의 CPU 분배 정책 중 하나인 CFS에 관한 설명을 현재 모든 Linux 정책에 일반화하지 않고, “실행 가능 여부와 실행 순서가 다르다”는 기본 구분을 먼저 이해하는 것이 중요하다.

    3.2 메모리의 분리와 공유

    편집기의 잘못된 메모리 접근이 재생기의 자료까지 고치지 않도록 일반적인 데스크톱·서버 운영체제는 프로세스마다 가상 주소 공간을 제공한다. 주소 공간은 프로그램이 위치 번호로 가리킬 수 있는 메모리의 범위다. 프로그램이 보는 가상 주소와 실제 메모리 위치의 연결을 커널과 하드웨어가 관리하므로, 같은 번호라도 프로세스가 다르면 다른 자료를 가리킬 수 있다.

    주소 변환과 접근 보호를 돕는 하드웨어가 MMU, 메모리 관리 장치다. 이 설명은 MMU가 있는 일반적인 데스크톱·서버를 전제로 한다. 허가되지 않은 접근은 정상 읽기·쓰기로 처리되지 않고 오류가 될 수 있다. 반대로 협력이 필요한 프로세스에는 허용된 공유 메모리를 제공할 수 있다. 분리와 공유 모두 통제된 연결의 결과다.[4]

    RAM은 실행 중인 자료가 놓이는 물리적 주기억장치다. 가상 주소가 넓어도 실제 RAM이 무한히 늘지는 않는다. 운영체제는 다시 읽을 수 있는 캐시를 회수하거나, 구성이 허용하면 일부 자료를 저장장치의 보조 공간인 스왑으로 옮긴다. 나중에 그 자료가 필요하면 다시 가져와야 하므로 이동이 잦으면 반응이 느려질 수 있다. 충분한 메모리를 확보하지 못하면 Linux가 일부 작업을 종료하는 상황도 가능하다.

    3.3 파일·장치와 권한

    입출력(I/O)은 파일이나 장치에서 자료를 읽거나 내보내는 일이다. 파일은 이름으로 자료를 다루는 단위이고 디렉토리는 파일과 하위 디렉토리의 이름을 조직한다. 이런 이름·내용·속성을 관리하는 방식이 파일시스템이다. 응용의 공통 읽기 요청을 커널이 실제 파일시스템과 장치의 처리에 연결한다.

    속도 차이를 줄이기 위해 파일 자료를 메모리에 캐시할 수 있다. 쓰기도 먼저 메모리에 반영하고 이후 저장장치로 보낼 수 있다. 따라서 쓰기 함수가 성공했다는 사실과 전원 장애 뒤에도 내용이 남는다는 내구성 보장은 다르다. 중요한 기록을 보존하려면 응용의 저장 절차, 운영체제의 동기화 요청, 저장장치 동작을 함께 고려해야 한다.

    접근 허용은 요청한 프로세스의 신원과 권한에 따라 달라진다. Linux에서는 사용자·그룹 번호와 파일 소유권·허가 비트 등이 판단에 쓰인다. 관리 계정인 root는 전통적으로 넓은 권한을 갖고, 특정 특권을 나누어 부여하는 기능도 있다. 특별히 설정된 실행 파일은 실행 시 권한이 달라질 수 있으므로 실행자의 권한을 언제나 그대로 갖는다고 단정하지 않는다.[5]

    사용자 권한과 사용자 공간·커널 공간은 서로 다른 축이다. root로 실행한 응용도 보통 사용자 공간에서 시스템 호출을 요청한다. 권한 부족 오류가 생겼다면 먼저 필요한 파일과 동작을 확인해야 한다. 즉시 관리 권한을 주기보다 허용 범위를 필요한 만큼 유지하는 편이 실수나 결함의 피해를 줄인다.

    4. 상태 확인과 활용

    4.1 커널·사용자 정보 조회

    관찰할 질문을 정하면 명령 출력의 의미도 분명해진다. uname -s는 커널 이름을, uname -r은 커널 릴리스를, id -u는 실행 주체의 유효 사용자 번호를 알려 준다. 앞의 둘은 어떤 커널에서 실행되는지, 마지막은 어떤 사용자 신원으로 판단되는지에 관한 조회다.[6]

    이 결과만으로 배포판의 모든 구성, 프로세스의 CPU 대기, 메모리 부족이나 파일의 내구성을 알 수는 없다. 커널 릴리스를 알았다고 특정 스케줄링 정책과 설정까지 확인한 것도 아니다. 출력 하나를 시스템 전체의 건강 상태로 확대하지 않고, 실행·메모리·입출력·권한 중 어떤 질문을 더 확인해야 하는지 구별하는 데 쓴다.

    4.2 활용과 한계

    운영체제는 개인용 컴퓨터에서는 여러 응용의 동시 이용을, 서버에서는 여러 요청의 지속적인 처리를 뒷받침한다. 응용 개발자는 공통 파일·통신 기능을 이용하고 문제를 조사하는 사람은 자원별로 원인을 좁힐 수 있다. 다운로드 대기와 CPU 경쟁을 구별하면 단순히 “프로그램을 더 빨리 실행하자”는 대책이 언제 도움이 되지 않는지도 이해할 수 있다.

    관리 기능은 자원 총량을 늘리거나 모든 실패를 없애지 않는다. 작업 전환과 주소 관리에는 비용이 있고, 캐시나 메모리 분리는 백업을 대신하지 않는다. 접근 통제도 사용자가 허용한 잘못된 변경까지 막지는 못한다. 필요한 응용·장치와의 호환성, 지원·갱신, 최소 권한과 복구 수단을 함께 준비해야 공통 기반의 이점을 안정적으로 사용할 수 있다.
