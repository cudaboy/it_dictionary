    1. 브라우저와 서버

    상품 목록이 브라우저에 나타나려면 누가 무엇을 보내야 할까? 브라우저가 목록을 요청하면 서버가 결과와 자료를 돌려준다. 이때 요청 대상, 원하는 작업, 처리 결과, 자료 형식을 공통 규칙으로 표현하는 약속이 HTTP(Hypertext Transfer Protocol)다. 통신 당사자가 함께 따르는 규칙을 프로토콜이라고 한다. 한쪽은 숫자 200을 가격으로, 다른 쪽은 성공 표시로 읽는 식이라면 같은 데이터를 받아도 뜻이 맞지 않는다. HTTP는 이런 기본 의미를 통일하여 서로 다른 프로그램이 통신하게 한다.

    요청하는 역할이 클라이언트, 요청을 처리하고 응답하는 역할이 서버다. 웹을 이용할 때 브라우저는 클라이언트로 동작한다. 서버는 미리 저장한 문서를 보내거나 상품 정보를 조회해 새 내용을 만들 수 있다. 문서·이미지·상품 정보처럼 요청의 대상이 되는 것을 자원이라 부른다. HTTP는 자원을 읽는 작업뿐 아니라 검색, 게시글 등록, 파일 업로드와 프로그램 사이의 데이터 교환에도 쓰인다. 공통 통신 규칙은 공유하지만 상품 가격이나 주문 가능 여부 같은 업무 규칙은 해당 서비스가 정한다.[1]

    https:// 주소는 통신 내용을 암호화하고 인증서를 통해 상대 서버의 신원을 확인하는 HTTPS 접근을 뜻한다. HTML과 다른 문서 형식이라는 뜻은 아니다. HTTP/1.1·HTTP/2·HTTP/3은 같은 요청·응답 의미를 서로 다른 전송 방식으로 구현한다. 두 프로그램 사이의 데이터 전달을 맡는 전송 프로토콜에는 TCP와 QUIC이 있으며 HTTP/3은 QUIC을 사용한다. 따라서 HTTP 전체를 TCP 기반이라고 한정할 수 없다. 통신이 보호되어도 서버가 잘못된 상품 가격을 보내는 문제까지 해결되지는 않는다.[2]

    2. URL과 요청 대상

    원하는 상품 목록은 어떻게 지정할까? URL은 자원의 위치와 접근 방식을 적는 주소다. 아래 주소에는 서비스에 접속할 정보, 공책 목록을 고르는 조건, 받은 문서에서 이동할 위치가 함께 들어 있다. 이들을 구분해야 서버가 처리할 조건과 브라우저가 처리할 위치를 혼동하지 않는다.[3]

    이 주소로 문서를 새로 요청하면 대상에 /products?category=notebook이 들어간다. #delivery는 요청 대상에서 빠지고, 브라우저가 받은 문서의 delivery 위치를 찾는 데 사용한다. 그러므로 서버가 배송 안내로 이동하라는 프래그먼트를 자동으로 전달받는 것은 아니다. 페이지 프로그램이 프래그먼트 값을 읽어 다른 요청에 넣는다면 그것은 프로그램이 추가한 동작이다.

    경로가 같아도 쿼리나 로그인 상태가 다르면 응답 내용은 달라질 수 있다. URL은 고정된 바이트의 파일 이름이 아니라 요청할 자원을 가리키기 때문이다. 또한 쿼리는 주소창과 방문 기록, 서버 로그 등에 남을 수 있다. 전송에 HTTPS를 사용하더라도 비밀번호를 쿼리에 넣지 않는 이유다.

    3. 요청과 응답의 구성

    대상을 정했다면 할 일과 전달할 자료를 적는다. 메서드는 요청할 작업의 의미, 헤더는 처리에 필요한 부가정보, 본문은 전달하는 데이터다. GET은 대상의 표현을 가져오는 요청이고, POST는 보낸 내용을 대상의 규칙에 따라 처리하라는 요청이다. 공책 목록 조회에는 GET을, 주문 제출에는 POST를 사용할 수 있다. 응답은 처리 결과를 나타내는 상태 코드와 헤더, 필요한 경우 본문을 돌려준다.[4]

    아래 교환에서 브라우저는 공책 목록을 요청하고 서버는 HTML 문서를 답한다. HTML은 제목·문단·링크 등 문서 구조를 표현하는 언어다. 요청의 Accept는 클라이언트가 수용할 자료 형식을 알리고, 응답의 Content-Type은 실제 본문의 자료 형식을 알린다. 희망한 형식과 실제 받은 형식을 각각 확인하는 셈이다.

    본문을 받은 뒤에는 브라우저의 해석이 이어진다. HTML은 문서 구조로, 색·배치 같은 모양을 기술하는 CSS는 표시 규칙으로, 동작을 작성하는 언어인 JavaScript는 허용되는 경우 실행할 프로그램으로 처리한다. 위 응답의 Content-Type은 HTML이라는 해석 단서를 준다. 그러나 외부에서 받은 값을 글자로 넣을지 HTML로 다시 해석할지는 페이지 프로그램의 삽입 방식과 보안 검사에도 달려 있다. 서버가 전송했다는 사실만으로 안전한 화면 출력이 끝난 것은 아니다.[5]

    주문 제출에서는 상품 식별자와 수량을 POST 본문에 넣고 요청의 Content-Type으로 그 형식을 알릴 수 있다. 반면 목록을 거르는 조건은 앞의 GET처럼 URL 쿼리에 담는 방식이 일반적이다. GET 본문에는 일반적으로 정의된 의미가 없으므로 서버와 중간 구성요소가 이를 검색 조건으로 처리할 것이라고 기대해서는 안 된다.

    GET의 의미는 조회이므로 주문 확정·삭제 같은 의도적인 상태 변경에 사용하지 않는다. 다만 조회를 처리하며 접속 로그를 남기는 부수 효과까지 금지한다는 뜻은 아니다. POST를 선택해도 값이 올바른지, 사용자가 그 작업을 해도 되는지는 서버가 따로 검사해야 한다. 메서드는 업무 의도를 표현하고, HTTPS는 전송을 보호하며, 권한 검사는 허용 여부를 판단한다.

    4. 특성

    4.1 상태 코드와 리다이렉트

    상태 코드는 서버의 처리 결과를 세 자리 숫자로 분류한다. 200 OK는 성공, 404 Not Found는 대상의 현재 표현을 찾지 못했거나 존재를 공개하지 않는 경우, 500 Internal Server Error는 예상하지 못한 서버 측 조건으로 처리를 못 한 경우다. 첫 숫자로 보면 1xx는 진행 안내, 2xx는 성공, 3xx는 추가 동작, 4xx는 요청 측 문제로 분류된 응답, 5xx는 서버 오류다. 코드만으로 구체 원인을 모두 알 수는 없으므로 설명 본문과 서버 기록도 함께 확인한다.[6]

    주문을 제출한 뒤 영수증으로 이동할 때 서버가 화면을 직접 밀어 보내는 것일까? 리다이렉트는 클라이언트에게 다른 주소를 요청하도록 안내하는 응답이다. 주문 POST에 303 See Other와 Location: /orders/receipt가 오면 브라우저는 영수증 주소에 GET을 새로 보낼 수 있다. Location은 이동 주소를 담는 헤더이며 이 예의 상대 주소는 현재 주소를 기준으로 해석한다. 주문 처리와 영수증 조회가 두 번의 교환으로 나뉘는 것이 핵심이다.

    리다이렉트 번호가 달라지면 후속 요청의 규칙도 달라진다. 307과 308을 따라 자동 이동할 때는 메서드를 유지하므로 POST가 언제나 GET으로 바뀌는 것은 아니다. 한편 304 Not Modified는 다른 주소로 이동하는 지시가 아니라 조건부 조회에서 기존 저장본을 재사용하라는 응답이다. HEAD는 GET과 같은 조회의 응답 정보를 본문 없이 받는 메서드다. HEAD 응답, 보낼 본문이 없는 성공을 나타내는 204 No Content, 304 응답에는 본문이 없다.

    4.2 무상태성과 쿠키·세션

    페이지 하나에도 여러 번의 교환이 생긴다. HTML을 받은 브라우저는 그 문서가 참조하는 이미지·CSS·JavaScript를 별도로 요청할 수 있고, 버튼을 누른 뒤 프로그램이 필요한 데이터만 추가로 가져올 수도 있다. 이전 응답을 저장해 재사용하는 캐시는 이 과정에서 같은 자료를 다시 받는 비용을 줄인다.

    여러 요청이 이어져도 HTTP 요청의 의미는 앞선 요청을 알아야만 해석할 수 있는 방식으로 정의되지 않는다. 이 성질이 무상태성이다. 그렇다면 로그인한 사람을 다음 요청에서 어떻게 알아볼까? 서비스가 요청 사이에 공유할 상태와 그 상태를 찾는 표식을 별도로 마련한다. 쿠키에 세션 식별자를 담는 방식은 그 한 예다.[7]

    쿠키는 브라우저가 저장한 뒤 조건에 맞는 요청에 첨부하는 이름·값 데이터다. 서버 세션은 로그인 여부나 장바구니 같은 문맥을 여러 요청에 걸쳐 서버에서 관리하는 방식이다. 서버 세션을 쓰면 실제 회원 정보는 서버에 두고 그 기록을 찾는 식별자만 쿠키로 전달할 수 있다. 쿠키는 전달할 표식이고 세션은 그 표식으로 찾는 상태인 셈이다. 화면 언어를 저장하는 쿠키는 서버 세션 없이도 사용할 수 있다.

    응답의 Set-Cookie는 저장할 값과 조건을 지정하고, 다음 요청의 Cookie는 저장된 이름·값을 전달한다. 예시의 Path=/는 호스트의 모든 경로를 범위로 삼는다. Domain을 생략했으므로 쿠키는 설정한 호스트 shop.example.com에만 해당한다. 허용되는 상위 도메인을 Domain으로 지정하면 하위 호스트까지 범위가 넓어진다. 다만 쿠키는 포트별로 격리되지 않고 Path도 프로그램 사이의 안전한 격리 경계가 아니다.[8]

    각 속성은 서로 다른 조건을 더한다. Secure는 이 HTTPS 사례에서 암호화된 요청에만 쿠키를 보내도록 한다. HttpOnly는 JavaScript의 쿠키 직접 읽기·변경을 제한하지만 스크립트가 일으킨 요청의 쿠키 첨부까지 막지는 않는다. SameSite는 요청이 시작된 사이트 문맥에 따른 조건이다. 4.3 출처와 브라우저 보안의 사이트 구분과 함께 읽어야 한다. 만료 여부, 개인정보 보호 정책, 프로그램의 인증정보 포함 설정도 전송 여부에 영향을 준다.

    쿠키가 남아 있는 기간과 서버가 로그인을 인정하는 기간은 같은 것이 아니다. Max-Age나 Expires가 없으면 브라우저 세션 동안 유지하는 세션 쿠키가 되지만, 이는 서버 세션의 다른 이름이 아니다. 브라우저가 세션 복원 때 쿠키를 되살릴 수도 있다. 따라서 창을 닫는 동작만 로그아웃 조건으로 삼지 않고 서버에서도 세션의 만료와 종료를 관리해야 한다.

    4.3 출처와 브라우저 보안

    이 기준을 실제 요청에 적용할 때는 세 질문을 순서대로 나눈다. 첫째, 어떤 주소로 어떤 요청을 보내는가? 둘째, 그 주소와 요청 조건에 맞는 쿠키가 있는가? 셋째, 응답이 왔을 때 요청한 페이지의 프로그램이 내용을 읽어도 되는가? 앞의 두 질문에 답했다고 세 번째 답까지 정해지는 것은 아니다.

    브라우저가 서로 다른 서비스의 문서와 데이터를 구별할 때 쓰는 기준 중 하나가 출처(origin)다. 여기서 다루는 HTTP·HTTPS URL의 출처는 스킴·호스트·포트의 조합이다. 경로·쿼리·프래그먼트는 출처에 포함되지 않는다. 생략한 포트는 해당 스킴의 기본 포트로 비교한다. 그래서 https://shop.example.com과 https://shop.example.com:443은 같은 출처다.[9]

    반면 쿠키의 SameSite 판단에 쓰는 사이트(site)는 일반적인 도메인 이름의 URL에서 스킴과 등록 가능한 도메인을 기준으로 묶는다. 등록 가능한 도메인은 com이나 co.uk처럼 공개적으로 구분된 도메인 접미사 바로 앞의 이름까지 포함한 부분이다. 따라서 shop.example.com과 api.example.com에서는 example.com이 기준이 된다. 단순히 점 뒤의 두 조각을 고르는 규칙은 아니며, 포트도 사이트 비교에는 포함하지 않는다. 이처럼 스킴을 포함한 비교를 schemeful same-site라고 한다.[10]

    브라우저의 동일 출처 정책은 한 출처의 문서나 프로그램이 다른 출처의 정보를 읽고 조작하는 일을 제한한다. 이를 ‘다른 출처로는 어떤 요청도 보낼 수 없다’는 뜻으로 이해하면 안 된다. 다른 출처의 링크로 이동하거나 양식을 제출하는 동작, 이미지를 넣는 동작은 각각의 규칙 아래에서 가능하다. 요청이 서버에 도착하는 것과 그 응답을 요청한 페이지의 JavaScript가 읽을 수 있는 것은 별개의 판단이다.

    CORS(교차 출처 자원 공유)는 서버가 응답 헤더로 허용할 출처 등을 알리고 브라우저가 이를 확인하는 방식이다. 페이지 프로그램이 다른 출처의 응답을 읽을 수 있도록 허용 범위를 정하는 데 쓰인다. 일부 요청은 먼저 OPTIONS 메서드로 허용 여부를 확인하는 사전 요청을 보내고, 그 확인이 통과해야 실제 요청을 보낸다. 반면 사전 확인 없이 보내지는 요청도 있으므로 CORS 오류가 났다는 사실만으로 서버에 요청이 도착하지 않았다고 단정할 수 없다. CORS는 사용자의 신원이나 업무 권한을 서버에서 확인하는 절차를 대신하지 않는다.[11]

    쿠키의 SameSite=Strict는 같은 사이트 문맥의 요청으로 전송을 제한한다. 명시적인 SameSite=Lax는 같은 사이트 요청 외에 다른 사이트에서 오는 최상위 화면 이동 중 GET 같은 안전한 메서드도 허용한다. 여기서 ‘안전한 메서드’는 조회처럼 상태 변경을 요청하지 않는다는 HTTP 의미이지 보안 검사가 불필요하다는 뜻이 아니다. SameSite=None은 교차 사이트 전송도 허용하는 설정이며 Secure가 함께 필요하다. 어느 설정이든 Domain·Path 같은 나머지 조건과 브라우저 정책은 여전히 적용된다. SameSite를 생략한 경우의 기본 동작을 모든 브라우저에서 동일하다고 가정하지 않는다.

    예를 들어 같은 사이트인 api.example.com이라도 4.2의 호스트 전용 쿠키는 shop.example.com에만 해당하므로 API 호스트로 보내지 않는다. 또한 출처가 다른 프로그램 요청은 인증정보 포함 설정과 CORS 조건도 별도로 검토해야 한다. 같은 사이트인지, 쿠키가 실리는지, 응답을 읽을 수 있는지는 같은 질문이 아니다. 쿠키가 자동으로 실리는 요청이라도 이용자가 의도한 요청인지는 별도로 확인해야 한다.

    예를 들어 https://shop.example.com의 페이지가 https://api.example.com/products를 단순 GET으로 조회한다고 하자. 사전 요청이 필요하지 않은 조건이라면 요청은 서버에 도달할 수 있다. 그러나 4.2의 호스트 전용 sid 쿠키는 API 호스트의 쿠키가 아니므로 실리지 않는다. API가 올바른 CORS 허용 헤더를 보내지 않으면 페이지 프로그램은 응답 내용을 읽지 못한다. 다른 호스트의 응답 공유를 허용하는 것과 회원 인증을 확인하는 것은 별도 작업이다.

    5. 활용과 한계

    화면이 보이지 않는 문제를 HTTP 관점에서 나누면 확인할 지점이 선명해진다. 브라우저 개발자 도구의 네트워크 목록에서 URL·메서드·상태·헤더를 확인한다. 목록 문서는 200으로 받았어도 이미지 요청이 실패할 수 있고, 자료는 도착했지만 JavaScript 실행이나 교차 출처 읽기에서 막힐 수 있다. 응답 자체를 못 받은 통신 실패와 서버가 500으로 답한 경우도 서로 다르다.

    프로그램이 데이터나 기능을 요청하는 접점인 API도 HTTP를 이용한다. 사람이 읽는 HTML 대신 이름·값 구조로 데이터를 표현하는 JSON을 응답할 수 있다. 공통 규칙 덕분에 클라이언트와 서버를 독립적으로 만들기 쉽고 캐시·중간 전달 서버로 반복 전송을 줄일 수 있다. 대신 여러 자원을 요청하는 왕복 비용과 캐시의 갱신 조건을 관리해야 하며, 회원별 자료를 다른 사람에게 재사용하지 않도록 범위를 정해야 한다.

    성공 상태는 서버가 해당 요청에 대해 알린 결과이지 업무 전체의 정확성을 인증하는 표시가 아니다. HTTPS를 사용해도 입력 검증·권한 판단·안전한 화면 출력은 남는다. 서버가 사용자 대신 URL에 접속하는 기능에서는 처음 주소뿐 아니라 리다이렉트로 도달할 주소도 검토해야 한다. HTTP는 통신의 공통 언어를 제공하고, 그 언어로 무엇을 허용할지는 서비스가 책임진다.
