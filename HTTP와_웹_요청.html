    1. 브라우저와 서버

    브라우저 주소창에 문구점 주소를 입력하면 상품 목록이 나타난다. 브라우저는 그 목록을 스스로 알고 있는 것이 아니라, 주소가 가리키는 서비스에 자료를 요청하고 돌아온 내용을 화면으로 만든다. 이때 ‘어떤 자료를 원하는지’, ‘처리가 성공했는지’, ‘돌려주는 자료는 어떤 종류인지’를 주고받는 약속이 HTTP(Hypertext Transfer Protocol)다. 컴퓨터끼리 통신할 때 따르는 이런 약속을 프로토콜이라고 한다.

    요청을 보내는 쪽을 클라이언트, 요청을 받아 처리하고 답하는 쪽을 서버라고 한다. 웹을 볼 때는 브라우저가 클라이언트다. 서버는 저장된 문서를 그대로 보내기도 하고, 프로그램이 상품 정보를 조회해 만든 결과를 보내기도 한다. HTTP로 요청할 수 있는 문서·이미지·상품 정보 같은 대상을 자원이라고 부른다. HTTP는 페이지를 읽는 일뿐 아니라 검색, 양식 제출, 파일 업로드, 프로그램 사이의 데이터 교환에도 쓰인다.[1]

    주소가 https://로 시작하면 HTTP 내용을 주고받는 통신을 암호화하고 상대 서버의 신원을 인증서로 확인하는 HTTPS를 사용한다. 이것은 HTTP와 무관한 별도 페이지 형식이 아니라 통신 보호를 갖춘 이용 방식이다. HTTP/1.1·HTTP/2·HTTP/3은 메시지를 전송하는 방식이 다른 HTTP 버전이다. 특히 HTTP/3은 TCP가 아니라 QUIC이라는 전송 프로토콜을 사용하므로 HTTP 전체를 ‘TCP로만 하는 통신’으로 이해하면 안 된다.[2]

    2. URL과 요청 대상

    URL은 자원의 위치와 접근 방식을 나타내는 주소다. 문구점의 공책 목록을 열고 배송 안내 위치로 이동하는 주소를 다음처럼 구성할 수 있다. 각 부분의 역할을 나누어 보면 주소 전체가 서버에 그대로 전달되는 것은 아니라는 점도 보인다.[3]

    따라서 이 주소로 새 문서를 요청할 때 서버가 받는 대상에는 /products?category=notebook이 들어가지만 #delivery는 들어가지 않는다. 서버가 목록을 보내면 브라우저는 그 문서에서 delivery로 표시된 위치를 찾는다. 페이지의 프로그램이 프래그먼트를 읽어 별도 요청에 실어 보내는 동작은 이 기본 URL 처리와 구별한다.

    서버는 같은 경로라도 쿼리나 로그인 상태 등에 따라 다른 내용을 돌려줄 수 있다. URL은 ‘항상 같은 바이트가 들어 있는 파일 이름’이라기보다 요청할 자원을 가리키는 주소다. 또한 쿼리는 주소창·방문 기록·서버 로그 등에 남을 수 있으므로 비밀번호 같은 비밀값을 넣는 곳으로 삼지 않는다.

    3. 요청과 응답의 구성

    브라우저가 보내는 요청에는 무엇을 해 달라는지 나타내는 메서드, 대상 주소, 처리에 참고할 부가정보인 헤더, 필요할 때 실제로 전달할 데이터인 본문이 들어간다. 메서드 GET은 대상의 내용을 가져오라는 뜻이다. POST는 전달한 데이터를 대상의 규칙에 따라 처리해 달라는 뜻으로, 게시글 등록이나 주문 제출에 사용할 수 있다.[4]

    앞의 공책 목록을 가져오는 요청과 서버의 응답을 나란히 읽어 보자. HTML은 제목·문단·링크처럼 웹 문서의 구조를 표시하는 언어다. 요청의 Accept는 클라이언트가 받을 수 있는 자료 형식을 알리고, 응답의 Content-Type은 실제 보내는 자료 형식을 알린다.

    응답이 도착하면 브라우저는 받은 바이트를 이용 목적에 맞게 해석한다. HTML 문서를 탐색하면 제목·문단 등의 구조를 만들어 화면을 구성하고, CSS는 모양에 적용하며, 허용된 JavaScript는 프로그램으로 실행한다. 서버가 데이터를 보냈다는 사실과 브라우저가 그것을 단순 글자로 표시할지 코드로 해석할지는 서로 다른 단계다. Content-Type과 브라우저의 보안 검사, 그리고 페이지 프로그램이 데이터를 어디에 넣는지가 중요하다.[5]

    양식에서 주문을 제출할 때는 POST 요청의 본문에 상품 식별자와 수량 등을 실을 수 있다. 본문 형식은 그 요청의 Content-Type으로 나타낸다. 반면 일반적인 GET 조회 조건은 위 예처럼 URL의 쿼리로 전달한다. GET 본문에는 일반적으로 정의된 의미가 없으므로 GET을 ‘본문에 검색 조건을 넣는 요청’으로 가정하지 않는다.

    GET은 조회를 요청하는 메서드이므로 주문 확정이나 삭제처럼 사용자가 의도한 상태 변경을 GET에 맡기지 않는다. 접속 로그 기록 같은 부수 작업까지 없다는 뜻은 아니다. POST라는 이름 자체가 입력 검증이나 암호화를 대신하지도 않는다. 서버는 전달된 값과 권한을 확인해야 하며, 전송 보호에는 HTTPS가 필요하다.

    4. 특성

    4.1 상태 코드와 리다이렉트

    응답의 상태 코드는 요청을 어떻게 처리했는지 나타내는 세 자리 숫자다. 앞의 200 OK는 성공이며, 404 Not Found는 대상의 현재 내용을 찾지 못했거나 그 존재를 공개하지 않는 경우에 쓰인다. 500 Internal Server Error는 서버가 예상하지 못한 조건 때문에 요청을 처리하지 못한 경우다. 큰 분류로는 1xx가 진행 안내, 2xx가 성공, 3xx가 추가 동작 안내, 4xx가 요청 측 문제로 분류된 응답, 5xx가 서버 측 오류다. 실제 원인은 코드뿐 아니라 설명 본문과 서버 기록을 함께 봐야 한다.[6]

    서버가 다른 주소로 다시 요청하도록 안내하는 것을 리다이렉트라고 한다. 예를 들어 주문 제출을 처리한 뒤 서버가 303 See Other와 Location: /orders/receipt를 보내면, 브라우저는 그 주소에 GET 요청을 하여 영수증 화면을 가져올 수 있다. Location은 이동할 주소를 담은 응답 헤더이고, 여기의 /orders/receipt는 현재 주소를 기준으로 해석하는 상대 주소다. 최초 POST와 영수증 GET은 서로 다른 요청이다.

    다른 리다이렉트 코드가 모두 같은 방식으로 동작하는 것은 아니다. 307·308로 자동 이동할 때는 요청 메서드를 유지한다. 따라서 POST 뒤의 모든 리다이렉트를 GET으로 바꾼다고 이해하면 안 된다. 또 3xx인 304 Not Modified는 다른 URL로 이동하라는 뜻이 아니라 조건부 조회 결과 기존 저장본을 재사용하라는 응답이다. 본문 없이 GET과 같은 조회의 응답 정보를 받는 HEAD 메서드도 있다. HEAD에 대한 응답, 성공했지만 보낼 본문이 없다는 204 No Content 응답, 304 응답에는 본문이 없다.

    4.2 무상태성과 쿠키·세션

    한 페이지를 여는 일도 보통은 요청 하나로 끝나지 않는다. 브라우저는 HTML을 읽다가 필요한 이미지, 모양을 정하는 CSS, 동작을 수행하는 JavaScript 프로그램을 각각 요청할 수 있다. 사용자가 버튼을 누르면 프로그램이 추가 요청을 보내 화면 일부만 바꾸기도 한다. 이전 응답을 저장해 재사용하는 캐시가 있다면 어떤 자료는 다시 내려받지 않아도 된다.

    이처럼 요청은 이어지지만 HTTP 자체는 이전 요청을 알아야만 다음 요청의 의미를 해석할 수 있는 구조가 아니다. 이를 무상태라고 한다. 문구점이 ‘이 브라우저는 방금 로그인한 회원의 브라우저’라는 정보를 이어 가려면 응용프로그램이 요청들을 연결하는 방법을 마련해야 한다. 흔한 방법은 쿠키에 세션 식별자를 넣는 것이다.[7]

    쿠키는 브라우저에 저장했다가 조건에 맞는 요청에 함께 보내는 작은 이름·값 데이터다. 서버 세션은 여러 요청에 걸쳐 유지할 로그인 상태나 장바구니 같은 문맥을 서버 쪽에서 관리하는 방식이다. 서버 세션 방식에서는 서버가 세션 기록을 만들고, 그 기록을 찾을 식별자만 쿠키로 보낼 수 있다. 쿠키는 전달 수단이고 세션 기록은 서버가 관리하는 상태이므로 둘은 같은 물건이 아니다. 화면 언어를 저장하는 쿠키처럼 서버 세션과 무관한 쿠키도 있다.

    Set-Cookie는 저장할 쿠키와 그 조건을 알리는 응답 헤더이고, Cookie는 저장해 둔 이름·값을 보내는 요청 헤더다. 위의 Path=/는 해당 호스트의 모든 경로를 전송 범위로 지정한다. Domain을 생략했으므로 호스트는 쿠키를 설정한 shop.example.com으로 제한된다. 허용되는 상위 도메인을 Domain에 지정하면 하위 호스트까지 범위가 넓어진다. 쿠키는 포트별로 격리되지 않으며, Path도 서로 다른 프로그램을 안전하게 격리하는 보안 경계는 아니다.[8]

    Secure는 이 HTTPS 예에서 암호화된 요청에만 쿠키를 보내도록 제한한다. HttpOnly는 페이지의 JavaScript가 쿠키 값을 직접 읽거나 바꾸지 못하게 하지만, JavaScript가 일으킨 요청에 쿠키가 실리는 것까지 막지는 않는다. SameSite는 요청이 어느 사이트 문맥에서 시작됐는지에 따른 전송 조건이며, 그 기준은 4.3 출처와 브라우저 보안에서 구별한다. 전송 여부에는 쿠키 만료, 브라우저의 개인정보 보호 정책, 프로그램이 요청할 때 정한 인증정보 포함 설정도 영향을 준다.

    쿠키의 수명과 서버 세션의 수명도 별개다. Max-Age·Expires로 쿠키의 유지 시간을 지정할 수 있고, 둘 다 없으면 브라우저 세션 동안 유지하는 ‘세션 쿠키’가 된다. 이 말은 서버 세션 그 자체라는 뜻이 아니다. 브라우저의 세션 복원 기능으로 쿠키가 복원될 수도 있으므로 창을 닫는 것만으로 서버의 로그아웃이 완료됐다고 보지 않는다. 서버는 별도로 세션 만료·종료를 판단해야 한다. 구체적인 생성·갱신·종료 정책은 세션 관리 (이번 검토본 미수록)에서 이어 읽는다.

    4.3 출처와 브라우저 보안

    브라우저가 서로 다른 서비스의 문서와 데이터를 구별할 때 쓰는 기준 중 하나가 출처(origin)다. 여기서 다루는 HTTP·HTTPS URL의 출처는 스킴·호스트·포트의 조합이다. 경로·쿼리·프래그먼트는 출처에 포함되지 않는다. 생략한 포트는 해당 스킴의 기본 포트로 비교한다. 그래서 https://shop.example.com과 https://shop.example.com:443은 같은 출처다.[9]

    반면 쿠키의 SameSite 판단에 쓰는 사이트(site)는 일반적인 도메인 이름의 URL에서 스킴과 등록 가능한 도메인을 기준으로 묶는다. 등록 가능한 도메인은 com이나 co.uk처럼 공개적으로 구분된 도메인 접미사 바로 앞의 이름까지 포함한 부분이다. 따라서 shop.example.com과 api.example.com에서는 example.com이 기준이 된다. 단순히 점 뒤의 두 조각을 고르는 규칙은 아니며, 포트도 사이트 비교에는 포함하지 않는다. 이처럼 스킴을 포함한 비교를 schemeful same-site라고 한다.[10]

    브라우저의 동일 출처 정책은 한 출처의 문서나 프로그램이 다른 출처의 정보를 읽고 조작하는 일을 제한한다. 이를 ‘다른 출처로는 어떤 요청도 보낼 수 없다’는 뜻으로 이해하면 안 된다. 다른 출처의 링크로 이동하거나 양식을 제출하는 동작, 이미지를 넣는 동작은 각각의 규칙 아래에서 가능하다. 요청이 서버에 도착하는 것과 그 응답을 요청한 페이지의 JavaScript가 읽을 수 있는 것은 별개의 판단이다.

    CORS(교차 출처 자원 공유)는 서버가 응답 헤더로 허용할 출처 등을 알리고 브라우저가 이를 확인하는 방식이다. 페이지 프로그램이 다른 출처의 응답을 읽을 수 있도록 허용 범위를 정하는 데 쓰인다. 일부 요청은 먼저 OPTIONS 메서드로 허용 여부를 확인하는 사전 요청을 보내고, 그 확인이 통과해야 실제 요청을 보낸다. 반면 사전 확인 없이 보내지는 요청도 있으므로 CORS 오류가 났다는 사실만으로 서버에 요청이 도착하지 않았다고 단정할 수 없다. CORS는 사용자의 신원이나 업무 권한을 서버에서 확인하는 절차를 대신하지 않는다.[11]

    쿠키의 SameSite=Strict는 같은 사이트 문맥의 요청으로 전송을 제한한다. 명시적인 SameSite=Lax는 같은 사이트 요청 외에 다른 사이트에서 오는 최상위 화면 이동 중 GET 같은 안전한 메서드도 허용한다. 여기서 ‘안전한 메서드’는 조회처럼 상태 변경을 요청하지 않는다는 HTTP 의미이지 보안 검사가 불필요하다는 뜻이 아니다. SameSite=None은 교차 사이트 전송도 허용하는 설정이며 Secure가 함께 필요하다. 어느 설정이든 Domain·Path 같은 나머지 조건과 브라우저 정책은 여전히 적용된다. SameSite를 생략한 경우의 기본 동작을 모든 브라우저에서 동일하다고 가정하지 않는다.

    예를 들어 같은 사이트인 api.example.com이라도 4.2의 호스트 전용 쿠키는 shop.example.com에만 해당하므로 API 호스트로 보내지 않는다. 또한 출처가 다른 프로그램 요청은 인증정보 포함 설정과 CORS 조건도 별도로 검토해야 한다. 같은 사이트인지, 쿠키가 실리는지, 응답을 읽을 수 있는지는 같은 질문이 아니다. 쿠키가 자동으로 실리는 요청의 정당성 문제는 CSRF (이번 검토본 미수록)로 연결된다.

    5. 활용과 한계

    HTTP를 알면 ‘화면이 안 나온다’는 증상을 주소, 요청, 응답, 화면 해석 단계로 나누어 볼 수 있다. 브라우저 개발자 도구의 네트워크 목록에서는 요청한 URL과 메서드, 응답 상태와 헤더를 살펴볼 수 있다. 목록 페이지는 200으로 왔지만 이미지 요청만 실패할 수도 있고, 문서는 도착했지만 프로그램 실행이나 교차 출처 읽기 단계에서 막힐 수도 있다. 응답을 받지 못한 통신 실패와 서버가 500으로 답한 실패도 구별된다.

    웹페이지뿐 아니라 프로그램이 필요한 데이터나 기능을 요청하는 접점인 API에도 HTTP가 널리 쓰인다. 이 경우 응답 본문은 HTML 대신 이름·값으로 데이터를 표현하는 JSON 같은 형식일 수 있다. 서버 프로그램이 요청을 받아 업무 처리를 수행하는 구조는 WAS (이번 검토본 미수록)에서 이어 볼 수 있다. 캐시와 중간 전달 서버를 활용하면 같은 자료의 반복 전송을 줄일 수 있지만, 사용자별 자료를 누구에게 재사용해도 되는지는 별도로 정해야 한다.

    HTTP 상태는 통신 상대가 알린 처리 결과이지 업무 전체의 정확성을 보증하는 증명서는 아니다. HTTPS도 통신 중 내용을 보호하는 역할이지 서버의 입력 검증, 사용자의 권한 판단, 안전한 화면 출력을 자동으로 완성하는 기능은 아니다. 요청을 이해한 다음에는 목적에 따라 인증 (이번 검토본 미수록), 인가 (이번 검토본 미수록), 입력값 검증 (이번 검토본 미수록)을 연결해 읽는다. 서버가 대신 URL에 접속하는 기능의 주소·리다이렉트 검토는 SSRF (이번 검토본 미수록)에서 다룬다. 통신 경로 자체가 궁금하다면 네트워크 (이번 검토본 미수록)와 TCP·UDP와 전송 계층 포트 (이번 검토본 미수록)가 다음 문서다.
