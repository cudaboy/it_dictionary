    1. 객체지향 프로그래밍

    할 일 관리 프로그램에는 제목과 완료 여부를 보관하는 기능, 일을 완료하는 기능, 화면에 목록을 보여 주는 기능이 필요하다. 처음에는 목록 하나와 처리 함수 몇 개로 충분하다. 그런데 취소한 일은 완료할 수 없다는 규칙이 추가되고, 여러 화면에서 같은 일을 수정하게 되면 질문이 달라진다. ‘어떤 순서로 처리할까?’뿐 아니라 ‘이 일의 상태를 누가 바꾸며, 그때 지킬 규칙은 어디에 둘까?’도 정해야 한다.

    객체지향 프로그래밍(Object-Oriented Programming, OOP)은 프로그램을 상태와 행동을 가진 객체들의 협력으로 구성하는 방식이다. 할 일 객체가 자신의 완료·취소 규칙을 맡고, 화면 객체가 입력과 표시를 맡도록 역할을 나눌 수 있다. 한 객체가 다른 객체의 공개된 동작을 요청하면서 전체 기능을 완성한다. 관련 값과 함수를 단순히 같은 파일에 모으는 데서 더 나아가, 어떤 대상이 무엇을 책임지고 어디까지 사용할 수 있는지 경계를 세우는 것이 핵심이다.[1]

    객체가 반드시 현실의 물건을 본떠야 하는 것은 아니다. 편집기의 문서와 선택 영역, 게임의 캐릭터와 이동 규칙, 연결의 사용 상태, 요금 계산 정책도 객체가 될 수 있다. 객체의 이름이 현실과 비슷한지보다 프로그램의 변화와 규칙을 이해하기 좋은 단위인지가 중요하다. 모든 명사를 클래스로 만들거나 모든 함수를 메서드로 옮긴다고 좋은 객체 설계가 되는 것은 아니다.

    객체지향의 목적은 변경의 영향을 줄이고, 상태가 유효한지 확인할 곳을 분명하게 만드는 데 있다. 완료 규칙을 할 일 객체에 모으면 화면이 늘어도 각 화면에 규칙을 복사할 필요가 줄어든다. 다만 이 이점은 호출자가 정해진 통로를 사용하고 객체들의 책임이 적절히 나뉘었을 때 생긴다. 클래스 문법 자체가 유지보수성과 안전성을 보장하지는 않는다.

    2. 절차 중심과 객체 중심

    절차 중심 접근은 해야 할 일을 함수와 실행 순서로 나누어 표현한다. 할 일을 읽고, 조건을 검사하고, 값을 바꾸고, 결과를 출력하는 흐름이 앞에 드러난다. 객체 중심 접근은 그 흐름에 참여하는 대상과 각 대상의 책임을 먼저 드러낸다. ‘완료 함수에 기록을 넘긴다’와 ‘할 일 객체에 완료를 요청한다’의 차이가 출발점이다. 두 방식 모두 함수 호출, 조건문, 반복문을 사용하므로 객체지향이 실행 순서를 없애는 것은 아니다.

    기존 프로그램이 할 일 기록을 함수에 전달하고 모든 변경을 공통 함수로 모았다면, 절차 중심 방식에서도 규칙을 한곳에서 지킬 수 있다. 반대로 객체를 써도 여러 화면이 객체의 필드에 직접 대입하면 규칙은 다시 흩어진다. 비교할 것은 ‘함수는 나쁘고 클래스는 좋다’가 아니라, 새 요구가 들어올 때 같은 판단을 몇 군데 고쳐야 하는지와 내부 표현을 누가 알아야 하는지다.

    도식에서 사라진 검사는 삭제된 것이 아니라 할 일 객체로 이동했다. 화면은 사용자의 입력을 받고 성공이나 거부를 표시하는 책임을 계속 갖는다. 같은 개선을 공통 함수와 비공개 모듈 데이터로 구현할 수도 있다. 객체는 여러 할 일 각각의 상태와 그 상태를 다루는 동작을 함께 전달해야 할 때 자연스러운 단위가 된다.

    실제 프로그램은 두 관점을 섞는 경우가 많다. 파일을 읽어 항목으로 나누는 순차 처리는 함수로 두고, 여러 요청 사이에서 상태가 유지되는 작업은 객체로 관리할 수 있다. 객체의 메서드 안에서도 입력을 받아 결과만 계산하는 함수를 호출할 수 있다. 한 번 실행하고 끝나는 짧은 변환 작업이나 같은 계산을 많은 값에 적용하는 작업은 함수와 자료구조만으로 더 명료할 수 있다.

    3. 상태·행동·정체성

    상태는 어떤 시점에 객체가 가진 값이다. 할 일의 제목과 진행 상태가 여기에 해당한다. 행동은 객체가 제공하는 동작이다. 완료 요청은 진행 상태를 바꾸며, 현재 상태 조회는 값을 바꾸지 않고 알려 준다. 행동이 항상 상태 변경을 뜻하는 것은 아니고, 계산 정책처럼 호출 사이에 보관할 상태가 거의 없는 객체도 있다.

    정체성은 값이 같더라도 어느 개별 객체인지를 구별하는 성질이다. 제목과 진행 상태가 모두 같은 두 할 일도 사용자가 따로 등록한 항목이라면 서로 다른 대상이다. 한 항목의 제목을 수정했다고 다른 항목까지 바뀌어서는 안 된다. 반대로 목록 화면과 상세 화면이 같은 할 일 객체를 가리킨다면, 한쪽에서 완료한 상태를 다른 쪽에서도 보게 된다. ‘값이 같은가’와 ‘같은 객체인가’를 구별해야 이 차이를 설명할 수 있다.[2]

    객체를 가리키는 연결을 참조라고 한다. 변수 이름을 하나 더 붙이거나 인수로 전달했다고 항상 객체가 복제되지는 않는다. Python에서 객체를 다른 변수에 대입하는 것은 같은 객체에 이름을 추가하는 경우이며, 독립 복사가 필요하면 그 의도를 따로 구현해야 한다. 또한 업무에서 쓰는 항목 번호와 실행 중 객체의 정체성은 구별된다. 파일에서 같은 항목을 두 번 읽어 별도 객체를 만들 수도 있으므로, 같은 업무 대상을 합칠지는 항목 번호 등 별도의 기준으로 정한다.

    4. 클래스와 객체

    클래스는 어떤 상태와 동작을 가진 객체를 만들지 정의하는 틀이고, 그 정의로 만든 개별 객체가 인스턴스다. 할 일 클래스는 제목·진행 상태와 완료·취소 동작을 정의한다. 오늘의 검토 작업과 내일의 정리 작업은 같은 클래스로 만든 서로 다른 인스턴스가 될 수 있다. 클래스는 공통 정의이고 객체는 실행 중의 개별 대상이라는 구분이 중요하다.[2]

    객체에 보관하는 값은 필드 또는 속성, 객체에 속한 함수는 메서드라고 부른다. 객체 생성 때는 사용할 수 있는 초기 상태를 마련해야 한다. Python의 __init__은 새 인스턴스를 초기화하는 메서드이고, 메서드 첫 매개변수의 관례적인 이름인 self는 지금 동작할 객체를 받는다. 같은 메서드를 호출해도 어느 객체로 호출했는지에 따라 다루는 상태가 달라진다.

    공통 정의를 쓴다는 말은 상태까지 모두 공유한다는 뜻이 아니다. 행사별 잔여 표나 할 일별 진행 상태는 각 인스턴스에 둔다. Python에서 변경 가능한 목록을 클래스 변수로 두면 여러 인스턴스가 그 목록을 함께 보게 될 수 있다. 공유가 필요한 데이터인지, 객체마다 따로 가져야 하는 데이터인지 먼저 구별해야 한다. 클래스 문법과 접근 제한의 세부는 언어마다 다르며, 클래스 기반 방식만이 객체를 구성하는 유일한 방식은 아니다.

    5. 책임과 협력

    책임은 객체가 알아야 하거나 수행해야 하는 일이다. 할 일 객체는 현재 진행 상태를 알고 유효한 상태 변경을 수행한다. 화면은 사용자 요청을 받아 결과를 표시한다. 저장 담당 객체는 기록을 파일이나 저장소에 보관한다. 이름이 ‘할 일’이라는 이유만으로 화면 출력, 파일 경로 선택, 오류 창 표시까지 할 일 객체에 넣으면 서로 다른 변경이 한곳에 모인다.

    협력은 객체들이 각자의 책임을 수행하기 위해 다른 객체에 요청하고 결과를 받는 관계다. 호출자가 사용할 수 있는 메서드와 그 의미를 인터페이스, 즉 사용 약속이라고 한다. complete()라는 이름만 정하는 것으로는 부족하다. 완료된 일을 다시 완료하면 어떻게 되는지, 취소한 일은 어떤 오류로 거부하는지, 거부되었을 때 상태가 유지되는지도 약속에 포함된다.

    전체 순서를 조정하는 역할은 여러 객체의 내부 값을 직접 고치는 대신 공개 동작을 호출한다. 할 일 객체는 어떤 화면에서 요청했는지 몰라도 완료 규칙을 시험할 수 있고, 화면은 그 상태를 저장하는 파일 형식이 바뀌어도 영향을 덜 받는다. 이런 분리는 관련 있는 일을 한곳에 모으고, 서로 다른 이유로 바뀌는 일을 분리하려는 판단이다.[3]

    책임을 나눈 뒤에도 객체들은 계약에 의존한다. 메서드의 입력이나 결과 의미를 바꾸면 협력자도 수정해야 할 수 있다. 지나치게 작은 객체를 많이 만들어 요청을 여러 단계 거치게 하면 전체 흐름을 찾기 어려워진다. 중요한 것은 객체 수가 아니라 규칙의 위치와 호출 관계를 설명할 수 있는지다.

    6. 추상화와 캡슐화

    추상화는 목적에 필요한 특징과 동작을 골라 모델로 표현하는 일이다. 할 일 관리에 필요한 제목·진행 상태·완료 요청은 남기고, 완료 버튼의 색상이나 저장 파일의 바이트 배치는 할 일의 핵심 모델에서 제외한다. 무엇을 같은 종류로 보고 어떤 동작을 제공할지 정하는 것이다. ‘상세한 내용을 생략한다’에서 끝나는 것이 아니라, 생략해도 사용자가 필요한 일을 할 수 있는 표현을 선택한다.[4]

    캡슐화는 관련 상태와 행동을 경계 안에 묶고, 바깥에서 사용할 통로를 정하는 일이다. 정보 은닉은 바깥에서 알 필요 없는 내부 표현과 바뀔 수 있는 설계 결정을 감추는 원칙이다. 추상화가 ‘완료를 요청할 수 있는 할 일’이라는 사용 모델을 고른다면, 캡슐화는 그 요청을 통해 상태가 바뀌도록 경계를 구성한다. 내부 상태를 문자열로 저장하다 숫자로 바꾸어도 외부 계약이 유지되면 호출자는 그 변경을 몰라도 된다.[3]

    상태가 항상 만족해야 할 조건을 불변 조건이라고 한다. 매표소의 ‘잔여 수량은 0 이상’이나 할 일의 ‘진행 중·완료·취소 중 하나의 상태를 가진다’가 그 예다. 여기에 ‘취소한 일은 완료로 전환하지 않는다’처럼 이전 상태와 다음 상태 사이의 전환 규칙도 정할 수 있다. 필드를 숨긴 뒤 아무 값이나 대입하는 메서드를 제공하면 이런 규칙은 보호되지 않는다. 의미 있는 동작이 조건을 확인한 뒤 변경하도록 설계해야 한다.

    접근 제한은 이 설계를 돕지만 언어별 강도가 다르다. Python의 밑줄 하나로 시작하는 _state는 내부용이라는 관례이며 외부 접근을 강제로 막지 않는다. 밑줄 두 개로 시작하는 일부 이름의 변환도 주로 하위 클래스와의 이름 충돌을 피하기 위한 것이지 보안 장벽이 아니다. Java의 private와 같은 접근 통제로 설명해서는 안 된다.[2]

    내부 목록을 그대로 반환하면 호출자가 그 목록을 바꾸어 메서드의 검사를 우회할 수 있다. 필요한 값만 돌려주거나 복사본·불변 표현을 제공할지 검토한다. 공개 동작이 민감한 값을 오류 메시지로 내보내는지도 살펴야 한다. 캡슐화는 잘못된 변경을 줄이는 설계 수단이며, 사용자 인증·권한 검사나 프로세스 격리의 대체물은 아니다.

    7. 객체의 상태 전환

    다음 할 일은 생성 시 진행 중으로 시작한다. 완료된 일을 다시 완료하는 것은 허용하고, 완료된 일의 취소와 취소한 일의 완료는 거부한다. 제목을 정리하는 계산은 별도 함수로 두고 상태가 유지되는 대상은 객체로 두었다. 함수와 객체가 한 프로그램에서 공존하는 작은 예다.

    return text.strip()

class Task:
    def __init__(self, title):
        self._title = normalize_title(title)
        self._state = "open"

    @property
    def state(self):
        return self._state

    def complete(self):
        if self._state == "cancelled":
            raise ValueError("cancelled task")
        self._state = "done"

    def cancel(self):
        if self._state == "done":
            raise ValueError("completed task")
        self._state = "cancelled"

a = Task(" review ")
b = Task(" review ")
detail_view = a
print(a is b, a is detail_view)
detail_view.complete()
print(a.state, b.state)
b.cancel()
try:
    b.complete()
except ValueError as error:
    print(str(error), b.state)

    a와 b는 값이 같은 제목으로 생성했지만 다른 객체이고, detail_view와 a는 같은 객체를 가리킨다. Python의 is는 같은 객체인지 검사한다. @property는 상태 조회를 a.state처럼 읽게 한다. 대입용 동작을 정의하지 않은 읽기 속성이지만 내부의 _state까지 외부에서 접근할 수 없게 만든 것은 아니다.[5]

    이 코드를 CPython 3.11.15로 실행한 표준 출력은 다음과 같다.

    False True
done open
cancelled task cancelled

    첫 줄은 두 개별 객체와 하나의 공유 참조를 구별한다. 두 번째 줄에서는 상세 화면을 뜻하는 변수로 완료를 요청했지만 a가 가리키는 상태도 완료로 보이고, 별도 객체 b는 진행 중이다. 마지막 줄은 취소한 일의 완료 요청을 거부하고 취소 상태를 유지했다는 관측이다. 이 결과가 검증하는 범위는 메서드를 통한 순차적인 상태 전환이며, 동시에 들어오는 요청이나 저장 실패 복구는 아니다.

    8. 상속·다형성·합성

    상속은 기존 클래스의 정의를 바탕으로 새 클래스를 만드는 관계다. 기존 클래스는 부모 또는 기반 클래스, 새 클래스는 자식 또는 파생 클래스라고 한다. 자식은 공통 동작을 물려받고 일부 동작을 새로 정의할 수 있다. 부모의 메서드를 자식이 자기 구현으로 바꾸는 것이 오버라이딩이다. 예를 들어 공통 가격 정책 아래 일반 정책과 회원 정책을 두고 금액 계산을 각각 구현할 수 있다.[2]

    다형성은 같은 사용 약속으로 서로 다른 구현을 다루는 성질이다. 매표소가 선택된 정책에 ‘수량에 대한 금액’을 요청하면 일반 정책은 일반 금액을, 회원 정책은 회원 금액을 계산한다. 매표소는 정책 종류마다 조건문을 작성하지 않고 같은 요청을 보낸다. 따라서 상속은 정의 사이의 관계이고 다형성은 공통 약속을 통해 여러 구현을 사용하는 방식이다. 둘을 같은 뜻으로 외우면 상속 없이도 가능한 협력을 놓치게 된다.

    Java에서는 인터페이스 선언을 구현하는 방법으로 약속을 나타낼 수 있다. Python에서는 같은 부모를 명시적으로 상속하지 않아도 필요한 메서드를 제공하는 객체와 협력할 수 있다. 단, 메서드 이름과 인수만 맞아서는 부족하다. 가격 정책이라면 정수 수량을 받아 약속한 단위의 금액을 돌려주고, 매표소의 잔여 수량을 임의로 바꾸지 않아야 한다. 자식 객체를 부모 대신 사용했을 때도 호출자가 기대한 결과와 오류 조건이 유지되어야 한다.

    합성은 객체가 다른 객체를 구성 요소로 가지고 그 객체에게 일을 맡기는 방식이다. 일반 매표소·회원 매표소라는 하위 클래스를 계속 만드는 대신, 매표소는 수량 관리와 판매를 맡고 보유한 정책 객체에 계산을 위임할 수 있다. 매표소는 가격 정책의 한 종류가 아니라 가격 정책을 가지고 있는 대상이다. 이 의미의 객체 합성은 객체를 조합하는 넓은 설계 방법이며, UML에서 부품의 수명까지 규정하는 좁은 합성 관계와는 구별해서 읽어야 한다.

    상속은 공통 계약과 구현을 함께 물려받는 데 유용하지만, 부모 내부 구현에 기대는 자식이 많으면 부모 변경이 넓게 번질 수 있다. ‘코드가 비슷하다’보다 ‘같은 역할로 대체해도 되는가’를 먼저 확인한다. 합성은 교체할 일을 분리하기 쉽지만 객체 생성과 연결이 늘고 어느 객체가 일을 맡았는지 따라가야 한다. 독립적으로 바뀌는 역할은 합성을 검토하고, 안정적인 대체 관계가 있는 공통 역할은 상속이나 인터페이스로 표현할 수 있다.

    가격 계산처럼 교체할 행동을 분리하는 구조를 반복되는 문제의 해법으로 정리한 것이 전략 패턴이다. OOP는 객체와 책임을 구성하는 기본 관점이고, 패턴은 그 관점을 활용해 특정 설계 문제를 해결하는 이름 붙은 방법이다.[6]

    9. 활용과 비용

    객체지향은 여러 요청 동안 상태를 유지하는 화면 구성요소, 문서 편집기, 게임 대상, 주문·예약 같은 업무 모델에 잘 맞을 수 있다. 각 대상의 상태와 허용 동작을 함께 이해할 수 있고, 공통 계약으로 다른 구현을 넣으면 구현별 시험과 교체도 쉬워진다. 실제 이득은 ‘상태 규칙이 한곳에 모였는가’, ‘새 정책을 넣을 때 안정적인 부분을 덜 수정하는가’로 확인할 수 있다.

    반면 객체끼리 서로의 내부를 많이 알거나 하나의 거대한 객체가 모든 처리를 맡으면 변경이 다시 넓게 번진다. 상속 계층이 깊어지면 실제 호출되는 구현을 찾기 어렵고, 공유되는 변경 가능 상태가 많으면 실행 순서에 따라 결과가 달라진다. 작은 계산마다 객체를 만들면 읽을 코드와 연결 과정만 늘 수 있다. 대량 데이터 처리에서는 객체 생성과 간접 호출의 비용, 메모리 배치까지 측정할 필요가 있다. 객체지향인지 여부만으로 속도가 빠르거나 느리다고 결론 내리지는 않는다.

    설계의 출발점은 상태의 수명과 바뀔 규칙을 확인하는 일이다. 짧고 독립적인 계산은 함수로 남기고, 유효한 상태를 유지해야 하는 대상은 변경 통로를 모으며, 실제로 교체해야 하는 협력자는 작은 계약으로 나눈다. 이후 요구가 달라지면 그 경계가 여전히 유용한지 다시 검토한다. 재사용은 클래스를 많이 만들었을 때가 아니라, 필요한 부분을 기존 가정과 충돌 없이 다시 사용할 수 있을 때 얻는 결과다.

    10. 자료형과 객체 설계

    관련 필드의 모양과 함수 문법은 프로그래밍 언어와 문법의 출발점이다. 필드를 묶어 사용자 정의 자료형을 만드는 일에 변경 책임과 상태 규칙을 더하면 객체 설계의 질문으로 이어진다. 구조체를 사용했다는 사실만으로 누가 값을 바꿀지까지 정해지는 것은 아니다.

    자료구조와 알고리즘은 값을 담고 꺼내고 찾는 연산과 비용을 다룬다. 내부 목록을 어떤 연산으로 구현할지와 그 목록을 외부에 그대로 공개해도 되는지는 연결되지만 다른 질문이다. 소프트웨어 아키텍처와 모듈은 더 큰 구성요소의 경계를 다룬다. 클래스와 객체의 협력은 그 경계를 코드로 표현하는 방법 중 하나다.
