    1. 상태와 행동의 묶음

    매표소에 남은 표가 있는데, 여러 처리 코드가 그 수를 제각각 바꾼다고 생각해 보자. 어떤 코드는 표가 충분한지 검사하고 다른 코드는 검사 없이 수를 줄인다면 남은 표가 음수가 될 수 있다. 남은 수량과 판매 규칙을 함께 묶고, 판매를 맡은 동작을 통해서만 정상적인 변경이 일어나게 하면 규칙을 찾고 지키기가 쉬워진다. 객체지향은 이처럼 관련된 상태와 행동을 객체로 구성하고 객체들이 협력하도록 프로그램을 설계하는 방식이다.

    상태는 지금 가지고 있는 값이며, 행동은 그 값을 사용하거나 변경하는 동작이다. 남은 표 수량은 상태, 표를 판매하고 결과를 돌려주는 일은 행동이다. 객체는 실행 중 이러한 상태와 행동을 가진 개별 대상이다. 현실의 물건만 객체가 되는 것은 아니다. 요금 정책, 파일 읽기, 비교 규칙처럼 추상적인 역할도 객체로 표현할 수 있다.

    객체지향이 모든 문제에 필요한 것은 아니다. 저장할 상태 없이 입력을 한 번 계산해 반환하는 작업이라면 함수 하나로 충분할 수 있다. 객체는 상태의 수명, 변경 규칙, 협력 관계를 한 단위로 이해할 때 특히 유용하다. 이 글은 먼저 클래스·캡슐화·상속·다형성을 설명한 뒤, 반복되는 변경 문제를 푸는 설계 패턴으로 연결한다. 매표소와 가격은 설명용 가정이며 실제 예매나 결제에는 연결하지 않는다.

    2. 클래스와 객체

    클래스는 어떤 상태와 동작을 가진 객체를 만들지 정의하는 틀이다. 같은 클래스로 만든 개별 객체를 그 클래스의 인스턴스라고 한다. ‘매표소’라는 클래스가 하나 있어도 오전 행사 매표소와 오후 행사 매표소는 서로 다른 객체가 될 수 있다. 한쪽이 표를 팔았다고 다른 쪽의 남은 표도 줄어서는 안 된다. 클래스는 공통적인 정의이고 객체는 실행 중의 개별 대상이라는 구분이 중요하다.[1]

    객체에 붙은 값은 필드 또는 속성, 객체에 속한 함수는 메서드라고 부른다. 객체를 만들 때 초기 상태를 정하는 절차도 필요하다. Python에서는 클래스 이름 뒤에 괄호를 붙여 인스턴스를 만들며, __init__ 메서드는 새 인스턴스의 상태를 초기화한다. 메서드의 첫 매개변수에 관례적으로 쓰는 self는 그 메서드가 다룰 객체 자신이다. 이는 객체를 지칭하는 이름이지 클래스 전체에 공유되는 값이 아니다.

    클래스 수준에 둔 값과 인스턴스에 둔 값은 다르다. 여러 객체가 공유하는 변경 가능한 목록을 클래스에 두면 한 객체의 수정이 다른 객체에서도 보일 수 있다. 행사별 남은 표처럼 개별 상태여야 하는 값은 각 인스턴스를 초기화할 때 마련한다. 또 이름 두 개가 같은 객체를 가리킬 수 있다. 객체를 다른 변수에 대입했다고 언제나 독립 복사본이 만들어지는 것은 아니다.[1]

    Java에서도 클래스와 인스턴스를 구분하지만 접근 제한과 타입 검사 등의 언어 규칙은 Python과 같지 않다. 하나의 언어에 class라는 단어가 있다는 사실보다, 상태를 누가 변경하고 어떤 호출 약속을 지키는지 이해하는 것이 객체지향 학습의 핵심이다.

    3. 캡슐화와 정보 은닉

    캡슐화는 관련된 상태와 동작을 경계 안에 묶고 바깥에는 사용할 통로를 제공하는 것이다. 정보 은닉은 바깥에서 알 필요가 없는 내부 표현과 변경 가능성이 큰 설계 결정을 감추는 원칙이다. 두 개념은 함께 쓰인다. 매표소 사용자는 ‘2장을 판매해 달라’고 요청하고 결과를 받으면 된다. 내부에서 수량을 어떤 이름으로 보관하는지까지 알아야 할 필요는 없다. 외부 계약을 유지하면 내부 표현을 바꾸기 쉬워진다.[2]

    이때 지켜야 할 상태 조건을 불변 조건이라고 한다. 매표소의 경우 ‘남은 표는 항상 0 이상’이 그 예다. 판매 메서드는 양의 정수 수량인지, 남은 수량을 넘지 않는지 먼저 확인하고 통과할 때만 수량을 줄인다. 값을 숨기고 모든 필드에 무조건 대입하는 메서드를 하나씩 붙이는 것만으로는 이런 조건이 지켜지지 않는다. 공개 동작 자체가 의미 있는 업무 규칙을 지켜야 한다.

    언어의 접근 제한은 이 설계를 돕는 수단이다. Python의 밑줄 하나로 시작하는 속성 이름은 외부에서 직접 쓰지 말라는 관례이며 접근을 강제로 금지하지 않는다. 밑줄 두 개로 시작하는 일부 이름의 변환도 주로 하위 클래스와의 이름 충돌을 피하기 위한 장치이지 보안 장벽이 아니다. 아래 예제의 _remaining 역시 내부용 관례다. 이를 Java의 private와 동일한 접근 통제로 설명하면 안 된다.[1]

    보안 관점에서는 내부 자료를 바깥에 그대로 노출하는 경로도 살핀다. 내부 목록의 원본 참조를 반환하면 호출자가 메서드의 검사를 거치지 않고 내용을 바꿀 수 있다. 필요한 값만 반환하거나 복사본·불변 표현을 제공하는 방법을 고려한다. 또한 공개 메서드가 민감한 값을 오류 메시지로 내보내지 않는지, 입력을 검증하기 전에 상태를 변경하지 않는지 확인한다. 캡슐화는 잘못된 변경을 줄이는 설계 수단이며 사용자 인증·권한 검사나 프로세스 격리를 대신하지 않는다.

    4. 상속과 다형성

    상속은 기존 클래스와의 관계를 선언하여 그 정의를 바탕으로 새 클래스를 만드는 방식이다. 기존 클래스를 부모 또는 기반 클래스, 새 클래스를 자식 또는 파생 클래스라고 한다. 공통 기능을 물려받고 필요한 동작을 새로 정의할 수 있다. 부모에게 있는 메서드를 자식이 같은 이름의 자기 구현으로 바꾸는 일을 오버라이딩이라고 한다. Python의 class MemberPrice(PricePolicy)라는 선언은 MemberPrice가 PricePolicy를 상속한다는 뜻이다.[1]

    다형성은 같은 사용 약속을 통해 서로 다른 구현을 다루는 성질이다. 매표소가 가격 정책에게 ‘수량에 대한 금액’을 요청하면 일반 가격 정책과 회원 가격 정책은 각자의 계산을 수행한다. 매표소는 정책의 구체적인 종류를 매번 검사해 분기하지 않아도 된다. 아래 예제에서는 실제 정책 객체의 total 메서드가 실행된다. 따라서 상속 선언은 클래스 사이의 관계이고, 다형성은 공통 호출을 서로 다른 구현에 적용하는 사용 방식이라는 차이가 있다.

    인터페이스는 이 공통 사용 약속을 뜻한다. Java의 인터페이스 선언처럼 언어 기능으로 표현할 수도 있고, Python에서는 필요한 메서드를 제공한다는 약속으로 협력할 수도 있다. Python은 명시적으로 같은 부모를 상속하지 않아도 요청한 메서드가 있으면 사용할 수 있다. 그렇다고 아무 객체나 맞는 것은 아니다. 이름과 인수뿐 아니라 결과의 뜻과 오류 조건도 맞아야 한다. 예제의 정책은 양의 정수 수량에 대해 0 이상의 정수 금액을 반환해야 한다.

    상속은 코드 몇 줄을 재사용한다는 이유만으로 고르지 않는다. 부모 대신 자식 객체를 사용했을 때 호출자가 기대한 약속이 유지되어야 한다. 가격 정책이 갑자기 문자열을 반환하거나 남은 표까지 변경한다면 같은 이름의 메서드가 있어도 이 계약에는 맞지 않는다. 부모의 내부 구현에 기대는 상속은 부모 변경의 영향을 받기 쉽다. 공통점보다 변경 이유가 다르면, 다음 절처럼 별도 객체를 가지고 협력하는 방법을 고려한다.

    5. 합성과 전략 패턴

    합성은 어떤 객체가 다른 객체를 구성 요소로 가지고 그 객체에게 일을 맡기는 방식이다. ‘회원 매표소’를 ‘일반 매표소’의 자식으로 끝없이 늘리는 대신, 매표소는 표 수량을 관리하고 가격 정책 객체는 금액을 계산하게 할 수 있다. 이때 매표소는 가격 정책의 한 종류가 아니라 가격 정책을 가지고 있는 객체다. 역할을 분리하면 가격 계산만 교체하기 쉬워진다.

    설계 패턴은 반복해서 나타나는 설계 문제에 대한 해결 구조와 그때의 이익·비용을 이름으로 정리한 것이다. 그대로 복사해 붙이는 완성 코드나 반드시 적용해야 할 규정이 아니다. 전략(Strategy) 패턴은 바뀔 수 있는 계산·처리 방식을 별도 구현으로 만들고, 사용하는 쪽이 공통 약속으로 선택한 구현에 위임하게 한다. 아래에서는 요금 계산이 전략이며, 표의 수량 관리까지 정책에 넘기지는 않는다.

    실제 API에서도 사용하는 쪽과 교체할 규칙을 분리하는 모습을 볼 수 있다. Java의 Comparator는 두 대상을 비교하는 규칙을 정렬 메서드에 전달할 수 있게 한다. 공식 API는 비교기의 역할과 지켜야 할 순서 계약을 설명한다. 이를 전략 관점으로 읽으면 ‘정렬이 진행되는 방법’과 ‘어떤 항목을 앞에 둘지’의 책임이 구별된다. 여기서는 비교 규칙 교체의 설계 의미만 다루며 정렬 알고리즘과 복잡도는 자료구조 문서의 범위다.[3]

    전략을 만들면 정책별로 시험하기 쉽고 호출자의 조건 분기를 줄일 수 있다. 대신 작은 규칙에도 여러 클래스와 생성 과정이 생겨 이해 비용이 늘 수 있다. 정책 하나가 변할 가능성도 없고 계산이 단순하다면 함수 하나가 더 명료하다. Python처럼 함수를 값으로 전달할 수 있는 언어에서는 전략을 반드시 상속 클래스들로 구현할 필요도 없다. 다음 코드는 상속·다형성·합성을 함께 관찰하기 위해 클래스를 사용한다.

    6. 매표소 예제

    일반 표는 한 장에 1000원, 회원 표는 한 장에 800원으로 가정한다. 각 매표소는 표 3장으로 시작하며 하나의 실행 흐름에서만 사용한다. PricePolicy의 기본 메서드는 실제 계산을 제공하지 않고 NotImplementedError로 미구현임을 알린다. 이는 Python의 추상 클래스 선언 기능을 쓴 것은 아니며, 자식 클래스가 구현할 공통 약속을 간단히 표현한 것이다. 두 자식은 total을 오버라이딩한다.

    class PricePolicy:
    def total(self, quantity):
        raise NotImplementedError("provide a price policy")

class StandardPrice(PricePolicy):
    def total(self, quantity):
        return 1000 * quantity

class MemberPrice(PricePolicy):
    def total(self, quantity):
        return 800 * quantity

class TicketDesk:
    def __init__(self, stock, policy):
        if type(stock) is not int or stock < 0:
            raise ValueError("invalid stock")
        self._remaining = stock
        self._policy = policy

    @property
    def remaining(self):
        return self._remaining

    def sell(self, quantity):
        if type(quantity) is not int or quantity <= 0:
            raise ValueError("invalid quantity")
        if quantity > self._remaining:
            raise ValueError("not enough tickets")
        price = self._policy.total(quantity)
        if type(price) is not int or price < 0:
            raise ValueError("invalid policy result")
        self._remaining -= quantity
        return price

morning = TicketDesk(3, StandardPrice())
afternoon = TicketDesk(3, MemberPrice())
print(morning.sell(2), morning.remaining)
print(afternoon.sell(2), afternoon.remaining)
try:
    morning.sell(2)
except ValueError as error:
    print(str(error), morning.remaining)

    morning과 afternoon은 별개의 매표소 객체를 가리킨다. 생성 때 전달한 정책 객체는 _policy에 보관된다. sell은 수량을 검증한 뒤 정책의 total을 호출하며, 정책 결과도 확인한 다음에만 남은 표를 줄인다. @property는 호출자가 remaining을 값처럼 읽게 한다. 이 예제에는 그 속성의 대입 동작을 정의하지 않았지만, 내부 이름인 _remaining까지 외부에서 접근 불가능해지는 것은 아니다.[6]

    최종 본문에서 코드를 추출하여 CPython 3.11.15로 실행한 표준 출력은 다음과 같다. print는 한 줄에 금액과 남은 수량을 공백으로 구분해 표시한다.

    2000 1

    7. 다른 패턴과 선택 기준

    패턴을 배우는 이유는 많은 이름을 설계에 붙이기 위해서가 아니라, 어디가 바뀌며 어떤 관계 때문에 수정이 번지는지 구체적으로 말하기 위해서다. 패턴은 보통 객체를 만드는 방법을 다루는 생성, 객체들을 연결하는 모양을 다루는 구조, 객체들이 일을 나누는 방법을 다루는 행위 관점으로 묶어 이해한다. 전략은 처리 방식의 교체라는 행위 문제를 다룬다.

    어댑터(Adapter)는 기존 객체의 사용 방법과 호출자가 원하는 사용 약속이 다를 때 그 사이를 맞추는 역할을 한다. 예를 들어 바이트를 읽는 기능을 문자로 읽고 싶은 곳에 그대로 전달할 수는 없다. Java의 InputStreamReader는 바이트 스트림을 받아 문자 인코딩 규칙으로 해석해 문자 읽기 기능을 제공한다. 공식 문서가 보장하는 것은 이 변환 동작이며, 이를 어댑터의 관점에서 읽으면 기존 기능을 감싸 호출 경계를 맞춘다는 점을 볼 수 있다. 문서에 나오는 ‘bridge’라는 일반 표현을 곧바로 별도의 Bridge 패턴 분류로 단정하지는 않는다.[4]

    어댑터는 내부 차이를 감추지만 의미가 다른 기능을 무조건 같게 만들지는 못한다. 문자 인코딩을 잘못 정하면 읽기 메서드가 있어도 뜻이 바뀐다. 반환 형식뿐 아니라 오류, 자원 해제, 단위와 의미까지 맞는지 확인해야 한다. 매표소에서 가격 정책은 서로 같은 계약의 계산을 교체하는 전략이고, 서로 다른 외부 요금 API를 같은 계약으로 맞추는 계층은 어댑터가 될 수 있다.

    옵서버(Observer)는 변화나 사건을 제공하는 객체에 관심 있는 객체들이 등록하고 알림을 받는 관계다. 잔여 표가 바뀌면 화면 표시와 통계 표시가 각각 갱신되는 상황을 생각할 수 있다. 제공자는 각 화면의 내부 구현 대신 공통 알림 약속을 사용한다. Microsoft의 공식 문서는 제공자·관찰자·등록·등록 해제를 설명하고, 관찰자가 구독을 끝낼 수 있는 수단도 제시한다.[5]

    옵서버를 쓰면 수신자를 추가하기 편하지만 알림이 이어지는 순서와 객체 수명을 추적하기 어려워질 수 있다. 구독을 해제하지 않아 불필요한 객체가 계속 참조되는 문제, 한 수신자의 오류가 다른 수신자에게 미치는 영향도 설계해야 한다. 옵서버라는 이름만으로 비동기·병렬 실행이나 네트워크 메시지 전달이 보장되지는 않는다. 분산 시스템의 이벤트 기반 아키텍처와 닮은 목적이 있어도 실패와 전달 조건까지 같은 것은 아니다.

    생성 문제에서는 호출자가 구체 클래스 이름을 여러 곳에 반복하지 않도록 생성 책임을 모으는 방법을 생각할 수 있다. 이를 단순히 ‘팩터리’라고 부르기도 하지만, 생성 함수 하나를 만들었다고 모든 Factory Method나 Abstract Factory 패턴의 구조를 구현한 것은 아니다. 생성 방식을 분리할 필요가 있는지부터 묻고, 실제 요구에 맞는 구조를 선택한다.

    8. 자료형에서 객체 설계로

    값을 묶어 사용자 정의 자료형을 만드는 일은 프로그래밍 언어와 기본 문법에서 다룬다. 그 글의 구조체는 관련 필드의 모양을 정의한다. 여기서는 한 단계 더 나아가 누가 값을 바꿀지, 어떤 상태 조건을 지킬지, 다른 동작을 어떻게 같은 계약으로 사용할지를 설명했다. 구조체를 사용했다는 것과 객체의 변경 책임을 설계했다는 것은 같지 않다. 이 절은 기초 문서에서 ‘객체지향과 설계 패턴’으로 넘어오는 연결 지점이다.

    자료구조와 알고리즘 선택은 값을 담고 꺼내고 찾는 연산과 비용을 맡는다. 이 글은 리스트를 어떻게 구현할지가 아니라 내부 목록을 그대로 외부에 내보내도 되는지와 같은 책임 경계를 다룬다. 소프트웨어 구조와 모듈은 더 큰 구성요소의 결합도·응집도와 아키텍처 대안을 맡는다. 클래스와 객체의 협력은 그 경계를 실제 코드로 표현하는 방법 중 하나다.

    기존 소프트웨어의 추상화와 재사용 (이번 검토본 미수록)은 여러 층에서 같은 기능을 사용하는 의미를, JDBC의 인터페이스 사용 (이번 검토본 미수록)은 연결·문장·결과 객체를 통한 실제 API 사용을 보여 준다. 객체를 사용한 코드만 보았다고 상속·다형성 원리까지 배운 것은 아니다. 소스가 실행 가능한 산출물로 이어지는 과정은 컴파일 (이번 검토본 미수록)의 범위로 남긴다.

    이 글은 패턴 목록 전체를 외우는 사전이나 대형 프레임워크 안내서가 아니다. 여기서 캡슐화는 상태와 동작의 설계 경계이며 네트워크 패킷을 다른 형식으로 감싸는 뜻과 구별한다. 배포 장비와 실제 업무 시스템 설정 없이도 어떤 상태를 보호하고 어떤 구현을 바꿀지를 설명할 수 있는 것이 이 글의 목표다.
