    1. 아키텍처와 모듈

    파일이나 서비스를 잘게 나누면 변경이 쉬워질까? 예약 화면의 문구를 바꿀 때 요금 계산을 고치지 않아도 된다면 분리의 효과가 있다. 하지만 예약 하나를 위해 여러 서비스의 계약을 동시에 수정해야 한다면 파일 수만 늘어난 셈일 수 있다. 소프트웨어 아키텍처는 주요 구성요소와 관계, 지켜야 할 제약, 그런 구조를 선택한 이유를 다룬다. 목적은 상자를 늘리는 것이 아니라 기능을 제공하면서 변경과 실패의 영향을 이해할 수 있게 하는 것이다.

    모듈은 관련된 일을 하나의 책임으로 묶고 정해진 통로로 협력하는 단위다. 이름 붙인 처리 묶음인 함수, 클래스들의 묶음, 다른 코드가 가져다 쓰는 라이브러리, 독립 실행 서비스가 설계상 모듈이 될 수 있다. 언어 문법의 모듈이나 파일 구분만으로 책임이 잘 나뉘었다고 판정하지는 않는다.

    아키텍처가 예약 화면·업무 규칙·저장 기능의 관계를 정한다면 세부 모듈 설계는 각 경계의 입력, 결과, 오류와 내부 동작을 구체화한다. 먼저 어떤 변경을 분리할지 정하고, 다음으로 그 부분들이 어떻게 협력할지 정해야 두 수준이 이어진다.

    2. 구조 선택과 품질

    구조의 이름을 먼저 고르는 대신 질문을 먼저 고른다. 저장 형식이 바뀌면 화면도 바뀌는가, 저장 실패 뒤 성공을 표시할 수 있는가, 알림이 늦어도 예약은 조회되는가가 서로 다른 질문이다.

    2.1 구조·동작 모델과 인터페이스

    모델은 목적에 필요한 사실을 골라 단순화한 표현이다. 구조 모델은 구성요소와 의존을, 동작 모델은 요청 뒤의 협력 순서를 보여 준다. 같은 화살표라도 호출 의존인지 시간 순서인지 밝혀야 서로 다른 그림을 같은 뜻으로 읽지 않는다.

    구조 그림으로는 화면이 저장 통로를 직접 알아야 하는지 묻는다. 동작 그림으로는 저장 결과를 받은 뒤에 성공·실패를 표시하는지 확인한다. 요청·확정·취소 사이의 변화를 나타내는 상태 모델을 더하면 어느 상태에서 취소할 수 있는지도 살필 수 있다. 동작에 등장하는 구성요소가 구조에서 빠지거나 실패 뒤 무조건 확정된다면 모델 사이의 모순이다.

    인터페이스는 경계를 넘을 때 쓸 이름·입력·결과·오류의 약속이다. 화면만을 뜻하지 않는다. 예약 요청이라면 날짜 형식, 인원 범위, 같은 요청의 재전송 의미, 저장 실패 표현까지 정해야 한다. 명시적인 계약은 호출자가 내부 구조를 추측하거나 전역 설정에 몰래 의존하는 일을 줄인다.[1]

    외부 시스템과의 경계도 같은 방식으로 식별한다. 알림 서비스가 실패했을 때 예약 자체를 취소할지, 예약은 남겨 두고 알림만 다시 시도할지 정해야 한다. 외부 사용자를 포함한 시스템 관점과 소프트웨어 내부 관점을 나누되, 하나의 요청이 경계를 지나는 흐름은 연결해서 검토한다.

    2.2 아키텍처 유형

    계층형 구조는 표현·업무 규칙·자료 접근처럼 역할별로 층을 둔다. 화면 문구가 바뀌어도 예약 가능 규칙이 남도록 하는 분리다. 논리 계층은 책임의 구분이고 물리 배포 단위는 실행 위치의 구분이므로 한 프로그램 안에도 여러 계층이 있을 수 있다. 층마다 서버를 따로 둘 필요는 없다.[2]

    단일 배포형은 관련 기능을 함께 배포한다. 내부 모듈 경계를 지킬 수도 있으므로 단일 배포 자체가 나쁜 구조는 아니다. 추적과 초기 배포는 단순하지만 작은 변경에도 전체를 배포할 수 있다. 업무 능력별 마이크로서비스는 독립 개발·배포·확장의 필요가 클 때 대안이 된다. 대신 원격 호출 실패, 버전 차이, 서비스 사이 자료 일관성을 다룰 비용이 생긴다.

    이벤트는 어떤 일이 일어났다는 사실이다. 이벤트 기반 구조에서는 예약 확정 사실을 발행하고 관심 있는 알림·통계 처리자가 반응한다. 발행자는 모든 수신자의 내부 동작을 몰라도 되지만 처리 지연과 메시지 형식에 대한 의존은 남는다. 전달 유실·중복·순서 변화에 어떻게 대응할지도 설계한다.[2]

    계층, 배포 단위, 이벤트는 같은 축의 세 선택지가 아니다. 계층을 가진 단일 프로그램이 이벤트 방식으로 내부 기능을 연결할 수도 있다. 그림의 직접 호출은 응답을 기다리고, 이벤트 흐름은 확정과 후속 작업을 분리한다. 어느 쪽도 ‘예약 저장 성공, 알림 실패’라는 상태를 없애지 않는다. 로컬 메서드 호출과 네트워크 원격 호출의 실패 조건 역시 다르다.

    2.3 품질 속성과 절충

    예약을 받는 것은 기능이고, 변경하기 쉽고 빠르며 일부 실패를 견디는 것은 품질 속성의 질문이다. 유지보수성은 이해·수정의 용이성, 성능은 응답 시간과 처리 능력, 가용성은 필요할 때 이용할 수 있는 정도다. 보안은 허용된 주체의 접근과 자료 보호에 관계한다. 검증을 늘리면 잘못된 입력을 일찍 막지만 처리 비용도 추가된다.

    ‘빠르고 안전하다’보다 ‘휴일 요금 변경 시 화면 코드는 수정하지 않는다’, ‘알림 실패 뒤에도 확정 예약을 조회할 수 있다’처럼 상황과 결과를 적으면 검토 기준이 생긴다. 성능 수치는 입력량·환경을 정하고 시험해야 하며 구조 이름으로 추측하지 않는다.

    예약 기능에서 대안을 비교하는 질문
    원하는 성질도움이 되는 분리함께 검토할 비용
    요금 규칙의 독립 변경화면과 계산 책임 분리입출력 계약 유지와 호출부 시험
    알림 지연의 영향 축소확정과 후속 알림 분리재시도·중복 처리·상태 추적
    독립 배포와 확장업무 능력별 서비스 분리통신 실패·자료 일관성·운영 부담

    각 대안은 장점과 비용을 함께 가진다. 공식 아키텍처 안내도 복잡도와 통신·관리 비용을 함께 비교한다.[2] 작은 업무를 독립 서비스로 쪼개는 것보다 경계를 잘 지킨 모듈들을 한 프로그램에 두는 것이 요구에 더 맞을 수 있다.

    3. 모듈의 책임과 의존

    모듈화는 책임이 분명한 부분과 협력 방식을 정하는 일이다. 요금, 영수증 모양, 저장 형식이 바뀌는 이유는 다르다. 반대로 같은 계산의 중간 단계마다 파일을 나누면 흐름을 읽는 비용만 늘 수 있다. 줄 수보다 변경 이유를 경계의 기준으로 삼는다.

    3.1 결합도와 경계

    결합도는 다른 모듈의 자료와 내부 동작에 의존하는 정도다. 요금 계산이 화면 상자에서 수량을 읽고 전역 할인 설정을 해석하고 영수증까지 출력하면 세 변경이 계산에 들어온다. 계산이 필요한 단가·수량만 받아 금액을 반환하도록 좁히면 화면과 출력 형식을 몰라도 시험할 수 있다.

    구체적으로 기본 단가 1200원, 단가별 10% 할인, 수량 2라면 할인 단가는 1080원이고 결과는 2160원이다. 개선 전에는 계산기가 할인 설정을 읽어 이 단가를 정했다. 개선 후에는 호출자가 같은 할인·반올림 규칙으로 1080원을 정해 amount(1080, 2)에 넘긴다. 이 수치 추적은 단가별 할인 가정이 맞을 때 책임이 어디로 이동하는지 보여 준다. 총수량이나 주문 전체에 따라 할인하는 규칙은 이 계약에 포함하지 않는다.

    전역 설정 의존은 호출자에 남는다. 시스템 전체에서 의존이 사라진 것이 아니라 계산 경계 밖으로 이동했다. 뒤의 amount는 곱셈 계약을 시험하는 코드이며 할인 알고리즘이나 기존 전체 구현과의 동등성을 검증하는 코드는 아니다. 반올림 시점이 달라지면 같은 비율을 써도 결과가 달라질 수 있어 호출자의 조건도 계약에 남겨야 한다.

    다른 모듈의 내부 값을 직접 바꾸거나 여러 곳이 전역 상태를 수정하면 변경 순서를 알아야 한다. 내부 분기를 선택하는 제어 표시나 필요 이상으로 큰 기록을 넘기는 방식도 의존을 늘릴 수 있다. 그렇다고 값을 모두 낱개로 쪼개면 날짜·통화·단위의 의미가 흩어진다. 필요한 자료를 의미 있는 타입과 명시적인 약속에 모으는 것이 중요하다.[1]

    3.2 응집도와 변경 이유

    응집도는 모듈 내부의 일들이 한 목적에 얼마나 관련되는지 묻는다. 수량 검사와 금액 계산은 유효한 금액 산출을 위한 협력일 수 있지만, 로그인 화면의 색 변경과 임시 파일 삭제까지 넣으면 이름 하나로 목적을 설명하기 어렵다. ‘공통 처리’라고 이름 붙인다고 공통 책임이 생기지는 않는다.

    프로그램 시작 때 함께 실행하는 작업도 변경 이유는 다를 수 있다. 글꼴 준비·연결 열기·기록 정리를 한 흐름에서 조정하더라도 각 작업 구현과 순서 조정 책임을 구별할 수 있다. 반면 앞 단계 결과가 다음 입력이 되는 한 계산은 모아 두는 것이 이해에 도움이 된다.

    결합도는 모듈 사이, 응집도는 모듈 안의 질문이다. 외부 호출 수를 줄이려고 모든 기능을 한곳에 모으면 응집도가 떨어질 수 있다. 작은 파일끼리 내부 상태를 공유하면 결합도는 여전히 높다.[3] ‘규칙 하나를 바꾸면 어디를 고치는가’, ‘화면 없이 계산만 시험할 수 있는가’라는 질문으로 두 관점을 함께 점검한다.

    4. 공통 모듈과 재사용

    재사용은 이미 만든 기능이나 설계를 필요한 다른 곳에서도 쓰는 것이다. 화면 주문과 일괄 주문이 같은 금액 규칙을 사용하면 수정 지점을 모을 수 있다. 숫자가 우연히 같다는 이유만으로 다른 업무를 합치면 한쪽의 규칙 변경이 다른 쪽까지 흔든다. 공유할 것은 모양이 아니라 의미와 변경 이유다.[1]

    4.1 공통 계산의 계약

    amount는 0 이상 정수 원 단가와 1 이상 정수 수량을 받아 정수 금액을 반환한다. 불리언과 문자열은 거절한다. 입력·전역 상태를 바꾸거나 화면에 출력하지 않으며 세금·할인·반품·결제는 맡지 않는다. type(x) is int는 Python에서 정수와 관련된 타입인 불리언까지 배제하려는 검사다. raise는 오류를 알리고, try/except는 호출자가 그 오류를 받아 처리한다.

    def amount(unit_price, quantity):
    if type(unit_price) is not int or type(quantity) is not int:
        raise ValueError("integer required")
    if unit_price < 0 or quantity < 1:
        raise ValueError("invalid range")
    return unit_price * quantity

web_total = amount(1200, 2)
batch_total = amount(1200, 3)
print(web_total, batch_total)
print(amount(0, 1))
try:
    amount(1200, 0)
except ValueError as error:
    print(type(error).__name__, str(error))

    2400 3600
0
ValueError invalid range

    CPython 3.11.15에서 두 호출은 2400과 3600을 얻었다. 단가 0은 허용돼 0을 반환했고 수량 0은 ValueError로 거절됐다. 계산 함수는 값을 돌려줄 뿐, 표시한 것은 호출부의 print다. 이 경계 덕분에 출력 형식을 바꿔도 계산 규칙은 그대로 시험할 수 있다. 음수·문자열·불리언도 계약 경계 시험의 대상이다.

    4.2 활용과 비용

    공통 함수를 라이브러리로 배포하면 버전 선택·호환성·변경 통지가 새 책임이 된다. 원격 서비스로 바꾸면 지연과 장애도 추가된다. 저장소 안에서 실행하도록 등록한 프로그램인 저장 프로시저로 재사용할 때는 호출 권한과, 여러 변경을 하나의 확정·취소 단위로 묶는 트랜잭션 조건을 함께 확인한다. 같은 계산 코드라도 실행 경계가 바뀌면 실패 계약이 달라진다.

    모듈 안에서는 예약의 확정·취소 상태를 가진 객체와 가능 여부를 판단하는 역할을 나눌 수 있다. 호출자는 내부 값을 직접 고치기보다 정해진 동작을 요청한다. 아키텍처에서 정한 경계와 선택 이유가 객체 설계에서도 이어져야 책임 분리의 효과를 유지할 수 있다.
