    1. 아키텍처와 모듈

    예약 화면의 문구만 바꾸었는데 요금 계산까지 고장 난다면, 서로 다른 일이 지나치게 얽혀 있을 수 있다. 반대로 모든 처리를 잘게 나누어도 작은 예약 한 건을 위해 여러 프로그램이 서로 기다려야 한다면 이해와 운영이 어려워진다. 소프트웨어 구조는 프로그램을 어떤 부분으로 나누고, 그 부분들이 어떤 약속으로 협력하게 할지를 정한 조직 방식이다. 좋은 구조의 목표는 상자를 많이 만드는 것이 아니라, 필요한 기능을 제공하면서 변경과 실패의 영향을 이해할 수 있게 하는 것이다.

    모듈은 관련된 일을 하나의 책임으로 묶고 다른 부분과 정해진 통로로 협력하는 단위다. 함수 묶음, 클래스 묶음, 라이브러리나 서비스가 설계 관점의 모듈이 될 수 있다. 여기서 함수는 이름을 붙인 처리 묶음이고, 라이브러리는 다른 프로그램이 가져다 쓸 수 있도록 제공한 코드 묶음이다. 언어별로 ‘모듈’이라는 문법이나 파일 형식도 있지만, 파일을 나누었다는 사실만으로 책임까지 잘 나뉜 것은 아니다.

    아키텍처는 개별 함수의 줄 순서보다 큰 수준에서 주요 구성요소, 관계, 제약과 그 선택 이유를 다룬다. 예약 화면, 예약 규칙, 저장 기능을 나누는 일과 무엇이 무엇에 의존할지 정하는 일이 여기에 해당한다. 세부 모듈 설계는 각 부분의 입력·출력·오류와 내부 처리까지 구체화한다.

    2. 설계 모델과 관점

    설계자는 프로그램 전체를 한 장의 그림에 모두 담기보다, 지금 답할 질문에 필요한 사실만 골라 표현한다. 이렇게 목적에 맞게 단순화한 표현이 모델이다. 어떤 부분이 존재하는지를 보여 주는 구조 모델과, 요청이 들어온 뒤 어떤 순서로 협력하는지를 보여 주는 동작 모델은 서로 다른 질문에 답한다. 그림 옆에 화살표의 뜻을 적지 않으면 호출 관계인지 자료 이동인지 구별하기 어렵다.

    구조 그림은 ‘화면이 저장 형식을 직접 알아야 하는가’를 검토하는 데 좋다. 동작 그림은 ‘저장에 실패했는데 성공을 표시하는 경로가 있는가’를 찾는 데 좋다. 상태 모델을 더하면 예약이 요청·확정·취소 중 어디에 있는지, 어느 상태에서 취소를 허용하는지도 표현할 수 있다. 모델은 서로 모순되지 않아야 한다. 동작 그림에 등장하는 저장 통로가 구조 그림에는 없거나, 실패 후에도 무조건 확정 상태로 바뀐다면 설계가 덜 정리된 것이다.

    인터페이스는 경계를 넘는 쪽에서 사용할 수 있는 이름, 입력, 결과와 오류 등의 약속이다. 이 말은 화면만을 뜻하지 않는다. ‘예약 요청을 받는다’만으로는 부족하다. 날짜의 표현, 인원 범위, 중복 요청의 의미, 저장 실패를 알리는 방식까지 정해야 호출자가 내부 사정을 추측하지 않는다. 이러한 명시적 인터페이스와 관심사의 분리는 구성요소가 서로의 내부 구현에 덜 의존하게 한다.[1]

    더 큰 시스템 아키텍처 관점에서는 우리 소프트웨어 밖의 사용자와 외부 시스템도 식별한다. 예약 프로그램이 외부 알림 기능을 이용한다면, 알림 요청·완료·실패를 어느 경계에서 주고받는지 표시한다. 알림 실패가 예약 취소를 뜻하는지, 예약은 유지하고 알림만 다시 시도할지도 결정할 사항이다. 이것이 인터페이스 대상을 식별하는 이유다.

    3. 아키텍처 유형

    계층형 구조는 사용자에게 보이는 표현, 업무 규칙, 자료 접근처럼 역할별로 층을 나눈다. 예약 화면의 표시 방식과 예약 가능 조건을 분리하면 화면을 바꾸는 작업에서 업무 규칙을 덜 건드릴 수 있다. 논리적인 계층은 코드의 책임 구분이고, 물리적인 배포 단위는 실행 위치의 구분이다. 한 프로그램 안에 여러 계층이 있을 수 있으므로 층마다 별도 서버가 있어야 하는 것은 아니다.[2]

    단일 배포형은 관련 기능을 하나의 배포 단위로 묶는 방식이다. 내부 모듈 경계를 잘 지킬 수도, 모두 뒤섞을 수도 있으므로 단일 배포라는 말만으로 설계 품질이 정해지지는 않는다. 같은 실행 과정에서 협력하므로 처음에는 추적과 배포가 비교적 단순하지만 작은 변경에도 전체 배포가 필요할 수 있다. 기능별로 따로 개발·배포·확장해야 할 필요가 커지면 마이크로서비스처럼 업무 능력별 독립 서비스로 나누는 대안을 검토한다. 대신 원격 호출 실패, 버전 차이, 여러 서비스 자료의 일관성을 처리해야 한다.

    이벤트 기반 구조는 어떤 일이 일어났다는 사실을 발행하고, 관심 있는 처리자가 그것에 반응하게 한다. 예약 확정 후 알림과 통계를 각각 갱신하는 경우에 어울린다. 발행자는 모든 소비자의 내부 처리를 알 필요가 줄어들지만, 소비자가 처리하기까지 지연이 생길 수 있다. 같은 알림이 다시 전달되거나 순서가 달라질 때의 처리도 정해야 한다. 메시지를 사이에 넣었다고 의존성이 사라지는 것은 아니다. 메시지의 의미와 형식, 전달 방식에 대한 의존은 남는다.[2]

    첫 그림에서는 알림 호출의 응답을 기다린다. 두 번째에서는 예약 확정 사실과 후속 처리 사이를 분리한다. 어느 쪽에서도 ‘예약 저장은 성공했으나 알림은 실패한 경우’를 설계해야 한다. 전달 보장과 장애 복구 정책은 별도로 정해야 한다. 특히 클래스의 메서드를 호출하는 것과 네트워크를 넘는 서비스를 호출하는 것은 실패 조건이 다르다.

    4. 품질 속성과 절충

    ‘예약을 받는다’가 기능 요구라면, 변경하기 쉬운지, 응답이 빠른지, 일부 실패를 견디는지는 품질 속성에 해당한다. 유지보수성은 수정과 이해의 용이성, 성능은 응답 시간과 처리 능력, 가용성은 필요한 때 서비스를 이용할 수 있는 정도, 보안은 허용된 주체만 자료와 기능에 접근하도록 하는 성질과 관련된다. 이런 목표는 서로 영향을 준다. 검증을 추가하면 오류를 일찍 막을 수 있지만 처리 비용이 들고, 서비스를 더 나누면 독립 배포가 쉬워지는 대신 통신과 운영이 복잡해진다.

    품질 목표는 ‘빠르고 안전하게’보다 관찰 가능한 상황으로 적는 편이 좋다. 예를 들어 ‘휴일 요금 규칙을 바꾸어도 화면 표시 코드는 수정하지 않는다’, ‘알림 처리가 실패해도 확정된 예약은 조회할 수 있다’라고 쓰면 구조를 검토할 기준이 생긴다. 성능 수치는 입력량과 환경을 정하고 실제 시험해야 얻을 수 있다.

    아키텍처 스타일은 특정 기술의 사용 명령이 아니라 반복되는 구조적 선택의 묶음이다. Microsoft의 공식 대안 비교도 복잡도, 비동기 처리, 서비스 간 통신과 관리의 비용을 함께 다룬다. 규모가 작고 변경 요구가 단순하다면, 잘 나뉜 모듈을 한 프로그램으로 배포하는 편이 요구에 더 잘 맞을 수 있다.[2]

    5. 모듈 경계와 결합도

    모듈화는 하나의 문제를 책임이 분명한 부분으로 나누고 부분 사이의 협력 방식을 정하는 일이다. 기준은 줄 수나 파일 수보다 변경 이유다. 요금 규칙, 영수증 모양, 저장 형식은 바뀌는 이유가 다르므로 함께 묶을지 먼저 의심해 볼 수 있다. 반면 하나의 규칙을 계산하는 중간 단계마다 별도 모듈을 만들면 이해를 위해 여러 파일을 오가야 하므로 분리의 이득이 작을 수 있다.

    결합도는 한 모듈이 다른 모듈의 자료, 처리 방식이나 내부 사정에 얼마나 의존하는지를 나타낸다. 요금 계산기가 화면의 입력 상자 이름을 직접 읽고 화면 색까지 바꾼다면 계산 규칙과 화면 변경이 서로 영향을 준다. 필요한 수량과 단가만 받아 금액을 반환하면 화면의 구성 방식은 몰라도 된다. 이를 결합도를 낮추는 방향의 변경이라고 설명할 수 있다.

    의존의 모습도 구분할 수 있다. 다른 모듈의 내부 값을 직접 수정하면 내부 구현에 묶인다. 여러 모듈이 같은 변경 가능한 전역 값을 읽고 쓰면 누가 언제 바꾸었는지 알아야 한다. ‘출력 모드’ 같은 제어 표시를 넘겨 다른 모듈의 여러 일을 선택하게 하면 호출자가 그 내부 분기까지 알아야 할 수 있다. 필요한 필드 하나 때문에 거대한 예약 기록 전체를 넘기면 불필요한 자료 구조에 의존하기 쉽다. 필요한 값과 뜻이 분명한 결과로 좁히는 것은 이러한 의존을 줄이는 방법이다.

    값 몇 개만 전달한다고 언제나 좋은 계약은 아니다. 날짜·통화·단위처럼 함께 이해해야 하는 자료는 의미 있는 하나의 타입으로 묶는 편이 낫다. 같은 함수 이름을 유지하더라도 금액 단위를 바꾸거나 실패 의미를 바꾸면 계약이 깨진다. 의존성을 없애기보다 필요한 의존을 드러내고 안정적인 약속에 모으는 것이 핵심이다. 명시적 의존과 캡슐화가 이런 목표를 뒷받침한다.[1]

    6. 응집도와 변경 책임

    응집도는 한 모듈 안에 있는 일들이 하나의 목적을 위해 얼마나 밀접하게 관련되는지를 나타낸다. 요금 모듈 안에서 수량을 검사하고 금액을 계산하는 일은 ‘유효한 요금 산출’이라는 목적에 기여한다. 여기에 로그인 화면 색 변경과 임시 파일 삭제까지 넣으면 함께 있어야 할 이유가 약해진다. 이 경우 모듈 이름을 ‘공통 처리’로 바꾸어도 책임은 정리되지 않는다.

    함께 실행된다는 이유와 같은 목적이라는 이유는 다르다. 프로그램 시작 때 글꼴을 읽고, 연결을 열고, 오래된 기록을 지운다고 해서 셋이 하나의 업무 책임인 것은 아니다. 순서가 중요하다는 이유로 한 흐름 안에 둘 수는 있지만, 각 작업의 구현과 전체 순서를 조정하는 책임을 구분하면 변경 영향을 더 잘 이해할 수 있다. 반대로 앞 단계 결과가 다음 단계 입력이 되는 작업들은 하나의 계산 목적을 달성하는 과정일 수 있다.

    결합도는 모듈 사이를, 응집도는 모듈 안을 보는 질문이다. 높은 응집도와 낮은 결합도를 함께 지향하면 변경 이유를 찾기 쉬워지지만, 둘은 같은 측정값이 아니다. 모든 일을 한 모듈에 넣어 외부 호출 수를 줄였다고 설계가 좋아지지 않는다. 또 작은 모듈들이 서로의 내부 상태를 많이 공유하면 파일 수가 많아도 결합도는 높다. 책임 분리와 단일 책임 원칙은 이 판단에 사용할 수 있는 설계 지침이다. Microsoft가 보관하는 MSDN 설계 해설도 결합도를 다른 부분과의 연결 정도로, 응집도를 내부 책임·자료·메서드의 관련 정도로 구별한다.[3]

    검토할 때는 ‘규칙 하나가 바뀌면 어떤 모듈을 수정하는가’, ‘다른 모듈 없이 이 계산만 시험할 수 있는가’, ‘이름 하나로 내부 일의 목적을 설명할 수 있는가’를 묻는다. 변경 파일 수나 의존 수를 기록할 수 있지만 맥락 없는 숫자가 품질을 증명하지는 않는다. 다음 예제에서는 전역 상태와 출력 의존을 제거했는지, 두 호출자가 같은 계산 규칙을 쓰는지를 직접 확인한다.

    7. 공통 모듈과 재사용

    재사용은 이미 만든 기능이나 설계 지식을 다른 필요한 곳에서도 쓰는 것이다. 화면 주문과 일괄 주문이 같은 금액 규칙을 써야 한다면 계산을 공통 함수로 두면 규칙의 수정 지점이 모인다. 반면 두 업무의 숫자가 우연히 같다는 이유만으로 묶으면 한쪽의 변경이 다른 쪽까지 흔든다. 공유할 것은 겉모양이 아니라 같은 의미와 같은 변경 이유를 가진 규칙이다.[1]

    공통 금액 규칙은 작은 정수 원 단가와 정수 수량을 곱하는 것이다. 단가는 0 이상, 수량은 1 이상으로 정하고 불리언과 문자열은 받지 않는다. 성공하면 정수 금액을 반환하고, 잘못된 입력에는 ValueError로 실패를 알린다. 입력을 바꾸거나 화면·파일에 출력하지 않는 것도 계약이다. 세금, 할인, 반품과 결제는 이 규칙에 포함하지 않는다. type(x) is int는 이 예제에서 불리언까지 배제하려는 의도적인 검사다.

    def amount(unit_price, quantity):
    if type(unit_price) is not int or type(quantity) is not int:
        raise ValueError("integer required")
    if unit_price < 0 or quantity < 1:
        raise ValueError("invalid range")
    return unit_price * quantity

web_total = amount(1200, 2)
batch_total = amount(1200, 3)
print(web_total, batch_total)
print(amount(0, 1))
try:
    amount(1200, 0)
except ValueError as error:
    print(type(error).__name__, str(error))

    호출자는 출력할 책임을 가지고, 공통 함수는 입력 검증과 금액 산출만 담당한다. web_total과 batch_total은 같은 함수를 사용하는 두 호출의 결과다. 이 코드를 CPython 3.11.15로 실행한 표준 출력은 다음과 같다.

    2400 3600
0
ValueError invalid range

    관측한 것은 같은 계산을 두 호출에서 재사용했고 0 단가는 허용되며 0 수량은 거부되었다는 점이다. 별도 검증에서는 음수·문자열·불리언 입력도 거부되는지 확인했다. 설계를 구현으로 옮길 때는 이처럼 정상 입력뿐 아니라 계약 경계와 실패 경로를 시험해야 한다.

    공통 함수를 라이브러리로 배포한다면 호환성 유지, 버전 선택, 변경 통지의 책임이 생긴다. 원격 공통 서비스로 바꾸면 호출 지연과 서비스 장애도 계약에 추가된다. 모든 중복을 한곳에 모으기보다 실제로 같은 규칙인지 확인하고, 재사용의 편익이 새로운 의존의 비용보다 큰지 판단한다. 저장 프로시저처럼 저장소 안에서 실행되는 재사용 기능은 호출·권한·트랜잭션 조건까지 확인해야 한다.

    8. 모듈과 객체 설계

    모듈의 책임을 정한 뒤에는 그 안에서 상태를 가진 대상과 수행할 일을 나눌 수 있다. 예약 모듈이라면 개별 예약의 확정·취소 상태를 관리하는 객체와 예약 가능 여부를 판단하는 역할을 구분한다. 화면은 모듈이 제공하는 요청 통로를 사용하고, 개별 객체의 내부 상태를 직접 고치기보다 정해진 동작을 요청한다.
