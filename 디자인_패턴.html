    1. 디자인 패턴과 변경 문제

    조건문과 함수로도 코드를 작성할 수 있는데 왜 패턴이 필요할까? 일반 요금만 있던 판매 프로그램에 회원·행사 요금을 추가할 때마다 여러 판매 경로의 계산 분기를 고쳐야 한다면 변경 지점을 모을 이유가 생긴다. 디자인 패턴은 이런 반복되는 문제의 맥락, 책임을 나누는 구조, 적용 결과와 비용을 이름으로 정리한 설계 지식이다. 완성된 코드 파일을 가져오는 것이 아니라 해법을 선택할 경험을 재사용한다.[1]

    반대로 요금이 하나로 고정되어 있고 변경 지점이 이미 함수 하나라면 패턴 계층을 추가할 이유는 약하다. 이름을 먼저 고르기보다 무엇이 자주 바뀌는지, 그때 수정이 어디로 퍼지는지 확인한다. 계산 교체, 맞지 않는 호출 방식, 늘고 줄어드는 알림 대상은 각각 다른 문제이므로 해법도 달라진다.

    라이브러리는 호출할 구현을 제공하고 알고리즘은 결과를 계산하는 절차를 다룬다. 패턴은 주로 구현 사이의 관계와 책임 배분을 설명한다. OOP의 객체·상태·사용 약속은 패턴을 표현할 재료이지만, 객체지향 코드가 반드시 이름 있는 패턴을 써야 하는 것은 아니다. 같은 의도를 함수 조합으로 표현할 수도 있다.[2]

    1.1 생성·구조·행위 패턴

    생성은 필요한 객체를 준비하는 방법, 구조는 기존 객체나 클래스의 연결, 행위는 계산·통지 등 책임과 협력에 초점을 둔다. 개발의 세 단계가 아니라 서로 다른 설계 질문을 묶은 분류이며 함께 사용할 수 있다.[1]

    분류별 중심 질문과 해법의 예
    분류중심 질문대표 구조추가되는 부담
    생성호출자가 구체 클래스를 직접 정하지 않고 필요한 객체를 얻을 수 있는가?Factory Method는 생성 동작의 구현을 하위 클래스가 바꿀 수 있게 한다. Abstract Factory는 관련 객체들을 일관된 조합으로 생성하는 약속을 제공한다.생성 계층과 설정을 찾아가야 하며, 생성할 종류가 고정이면 과할 수 있다.
    구조이미 있는 기능을 필요한 경계와 모양으로 연결할 수 있는가?Adapter는 다른 호출 약속을 맞춘다. Decorator는 감싼 객체와 같은 사용 약속을 유지하며 책임을 더한다.감싸는 계층과 호출 경로가 늘고, 의미가 맞는지 확인해야 한다.
    행위계산이나 알림의 책임을 어떻게 나누는가?Strategy는 교체할 계산을 위임한다. Observer는 등록된 수신자에게 변화를 알린다.계산 선택, 수신자 수명, 실행 순서와 실패 처리를 정해야 한다.

    관련 객체를 일관된 조합으로 준비해야 하면 생성 문제가 중심이다. 기존 기능을 호출자의 약속에 맞추려면 구조 문제이고, 이미 준비한 계산을 바꿔 맡기려면 행위 문제다. 객체를 만드는 함수 하나로 충분한 경우도 많다. 그런 함수를 넓게 팩터리라고 부르더라도 하위 클래스가 생성 구현을 재정의하는 Factory Method나 관련 객체군을 만드는 Abstract Factory를 구현했다고 자동으로 판정하지는 않는다.

    2. 계산의 교체와 전략

    전략(Strategy)은 같은 계약을 지키는 계산들을 별도로 두고 사용하는 쪽이 선택된 계산에 일을 맡기는 패턴이다. 판매 흐름은 유지하되 요금만 바꾸려는 상황이 그 예다. 일반 요금과 회원 요금이 달라도 수량을 검사하고 잔여 표를 줄이는 규칙은 매번 복사할 필요가 없다.

    2.1 판매와 정책의 책임

    매표소는 수량 검사와 재고 변경을, 정책은 수량에 대한 금액 계산을 맡는다. 매표소가 정책 객체를 보유하고 요청하는 관계를 합성, 같은 total(수량) 호출을 여러 구현에 사용할 수 있는 성질을 다형성이라고 한다. 정책의 결과는 0 이상의 정수 원 금액이며 정책은 잔여 수량을 바꾸지 않는다고 계약한다.

    정책을 고르는 조건은 사라지지 않고 구성 코드로 이동한다. 회원 자격을 판단해야 한다면 그 담당 흐름이 올바른 정책을 전달해야 한다. 전략 자체가 인증을 제공하지는 않는다. 새 요금에는 새 계산·선택 코드·시험이 필요하지만, 같은 계약이면 판매의 수량 검사 부분은 유지할 수 있다.

    Java의 Comparator는 정렬에 비교 규칙을 전달하는 실제 API다. 비교기는 일관된 순서 관계 등 계약을 지켜야 한다. 정렬과 비교를 나눠 읽는 것은 전략 관점의 해석이고, 공식 API가 확인해 주는 사실은 비교기의 동작과 계약이다.[3] ‘같은 메서드 이름’만 맞추고 결과를 다른 통화나 문자열로 바꾸면 같은 전략 계약이 아니다.

    2.2 요금 정책 구현과 결과

    일반은 한 장 1000원, 회원은 800원이며 각각 표 3장인 별도 매표소로 시작한다. class는 객체의 동작과 상태를 정의하고, self는 현재 동작을 수행하는 객체다. __init__는 객체 생성 시 초기 상태를 준비한다. class MemberPrice(PricePolicy)는 상속을 나타내며 부모의 total을 다시 정의하는 것이 오버라이딩이다.

    PricePolicy의 기본 total은 NotImplementedError를 낸다. 이는 abc를 이용한 추상 클래스 선언이 아니라 자식에게 구현을 요구하는 간단한 관례다. @property는 remaining을 읽기 속성으로 제공한다. 밑줄 이름은 내부용 관례이지 강제 접근 차단이 아니다.[4] 코드의 raise는 오류를 알리고 try/except는 호출자가 오류를 받아 표시하는 부분이다.

    class PricePolicy:
    def total(self, quantity):
        raise NotImplementedError("provide a price policy")

class StandardPrice(PricePolicy):
    def total(self, quantity):
        return 1000 * quantity

class MemberPrice(PricePolicy):
    def total(self, quantity):
        return 800 * quantity

class TicketDesk:
    def __init__(self, stock, policy):
        if type(stock) is not int or stock < 0:
            raise ValueError("invalid stock")
        self._remaining = stock
        self._policy = policy

    @property
    def remaining(self):
        return self._remaining

    def sell(self, quantity):
        if type(quantity) is not int or quantity <= 0:
            raise ValueError("invalid quantity")
        if quantity > self._remaining:
            raise ValueError("not enough tickets")
        price = self._policy.total(quantity)
        if type(price) is not int or price < 0:
            raise ValueError("invalid policy result")
        self._remaining -= quantity
        return price

morning = TicketDesk(3, StandardPrice())
afternoon = TicketDesk(3, MemberPrice())
print(morning.sell(2), morning.remaining)
print(afternoon.sell(2), afternoon.remaining)
try:
    morning.sell(2)
except ValueError as error:
    print(str(error), morning.remaining)

    2000 1
1600 1
not enough tickets 1

    CPython 3.11.15에서 같은 sell(2)가 일반은 2000, 회원은 1600을 반환했고 각 재고는 1이 됐다. 오전 매표소에 다시 2장을 요청하면 남은 1장보다 많아 거절되며 재고는 1을 유지한다. 핵심 순서는 수량 확인 → 정책 계산 → 결과 확인 → 재고 감소다. 정책이 실패하거나 잘못된 결과를 주면 감소 줄에 도달하지 않는다.

    이 계약은 단일 실행 흐름에서 재고를 바꾸지 않는 정책과 협력할 때의 상태 보존이다. 동시 판매 방지, 결제와 판매의 원자적 처리, 영구 저장이나 권한 검사는 구현하지 않는다. 정책이 외부에 만든 부작용까지 되돌릴 수도 없다. 계산별 시험이 쉬워지는 대신 객체 생성과 연결을 읽는 비용이 늘며, 계산이 단순하면 함수 전달로 같은 목적을 달성할 수 있다.

    3. 경계 변환과 어댑터

    어댑터(Adapter)는 호출자가 원하는 약속과 기존 기능의 약속이 다를 때 경계를 맞춘다. 전략은 같은 계약의 행동 교체이고 어댑터는 다른 계약의 변환이다. 기존 기능을 직접 고칠 수 없거나 호출자가 많아 한꺼번에 바꾸기 어려울 때 변환 책임을 모을 수 있다.

    3.1 호출과 단위의 대응

    보고서는 섭씨를 요구하지만 장치는 화씨를 반환하며 메서드 이름도 다르다고 하자. 보고서마다 변환식을 쓰면 장치 변경의 영향이 퍼진다. 보고서는 celsius()만 알고, 어댑터가 장치의 read_fahrenheit()를 호출한 뒤 (화씨 - 32) × 5 / 9로 변환한다. 호출 이름과 결과 단위를 함께 맞추는 것이다.

    아래 장치는 고정값 68.0을 반환한다. self._sensor는 어댑터가 보유한 장치이며, 보고서의 f 문자열에서 :.1f는 소수 첫째 자리까지 표시하라는 형식이다. 장치·변환·표시의 역할을 나누어 읽으면 된다.

    class LegacySensor:
    def read_fahrenheit(self):
        return 68.0

class CelsiusAdapter:
    def __init__(self, sensor):
        self._sensor = sensor

    def celsius(self):
        fahrenheit = self._sensor.read_fahrenheit()
        return (fahrenheit - 32.0) * 5.0 / 9.0

def report(sensor):
    return f"{sensor.celsius():.1f} C"

print(report(CelsiusAdapter(LegacySensor())))

    3.2 변환 결과와 한계

    20.0 C

    CPython 3.11.15 출력은 20.0 C다. 보고서는 장치 이름이나 화씨 변환식을 몰라도 섭씨 값을 얻었다. 하지만 단위가 맞는 것과 유효한 측정인 것은 다르다. 장치가 오래된 값을 반환하거나 고장을 특정 숫자로 나타낸다면 그 조건도 대응시켜야 한다. 어댑터가 측정하지 않은 정보를 만들어 줄 수는 없다.

    Java InputStreamReader는 바이트를 지정한 문자 인코딩으로 해석해 문자를 제공한다. 다른 입력 약속을 연결한다는 점에서 어댑터 관점으로 읽을 수 있다. 공식 API의 ‘bridge’라는 일반 표현을 GoF Bridge 패턴의 공식 분류로 단정하지 않는다.[5] 인코딩이 틀리면 호출이 성공해도 원하는 문자가 아니듯, 변환에는 이름뿐 아니라 결과·오류·유효 시점·자원 해제의 의미까지 필요하다.

    변환이 한곳에 모이는 대신 계층 하나가 추가되어 시험·유지가 필요하다. 양쪽 인터페이스를 바꿀 수 있고 사용처가 적다면 직접 통일하는 편이 단순할 수 있다.

    4. 변화 통지와 옵서버

    옵서버(Observer)는 변화를 제공하는 객체에 관심 있는 수신자가 등록하고 통지를 받는 관계다. 판매 코드가 화면과 통계의 구체 함수를 직접 호출하면 새 표시를 붙일 때 판매도 고쳐야 한다. 등록된 수신자에게 공통 약속으로 알리면 대상의 증감을 등록 관계로 표현할 수 있다.[6]

    4.1 등록·알림·해제

    제공자는 수신자 목록을 관리하고, 수신자는 더 이상 필요 없을 때 해제한다. 아래 예제는 판매 코드와 별도로 잔여 수량 알림을 실행한다. dict, 여기서는 {}로 만든 사전은 키와 값을 연결한다. object()로 새 등록을 구별할 표식을 만들고 그 키에 수신함수를 둔다. subscribe는 그 표식을 지우는 함수를 반환한다.

    lambda value: ...는 value를 받아 짧은 동작을 하는 이름 없는 함수다. tuple(self._listeners.values())는 발행 시작 시의 수신함수들을 별도 순서열로 모아 이번 통지 목록을 고정한다. pop(token, None)은 표식이 이미 없어도 오류 대신 기본값을 돌려줘 해제를 반복할 수 있게 한다.

    class RemainingEvents:
    def __init__(self):
        self._listeners = {}

    def subscribe(self, listener):
        token = object()
        self._listeners[token] = listener
        def unsubscribe():
            self._listeners.pop(token, None)
        return unsubscribe

    def publish(self, remaining):
        for listener in tuple(self._listeners.values()):
            listener(remaining)

events = RemainingEvents()
stop_screen = events.subscribe(lambda value: print("screen", value))
stop_stats = events.subscribe(lambda value: print("stats", value))
events.publish(1)
stop_screen()
events.publish(0)
stop_stats()

    screen 1
stats 1
stats 0

    CPython 3.11.15에서 첫 publish(1)는 screen과 stats에 모두 전달됐다. stop_screen()으로 화면만 해제한 뒤 publish(0)는 stats에만 갔다. 마지막 stop_stats()는 나머지 구독을 해제한다. 판매의 수량 계산과 등록 수명의 책임이 다르다는 점이 이 흐름에 드러난다.

    4.2 순서와 실패 처리

    이 구현은 사전의 등록 순서를 따라 동기 호출, 즉 한 수신자가 끝난 뒤 다음 수신자를 부른다. tuple로 이미 확보한 목록은 중간에 구독을 해제해도 바뀌지 않아 이번 발행의 수신자는 호출될 수 있다. 수신자가 예외를 내면 예외가 발행 호출자로 전파되고 뒤 수신자는 호출되지 않는다. 이는 예제의 정책이며 옵서버라는 이름이 강제하는 보장은 아니다.

    해제하지 않으면 제공자가 더 이상 필요 없는 대상을 계속 참조할 수 있다. 같은 함수를 두 번 등록하면 별도 표식으로 두 번 통지되고, 수신자가 다시 변화를 발행하면 연쇄 호출도 생긴다. 수명·중복·순서·실패를 함께 설계해야 하는 이유다. 수신자별 오류를 격리할 수 있지만 실패 기록과 재시도 책임이 추가된다. 이 패턴이 비동기·병렬 실행이나 네트워크 전달의 유실·중복 문제까지 자동 해결하는 것은 아니다.

    5. 선택과 비용

    다른 객체를 감싼다는 그림만으로 전략과 어댑터를 구별할 수는 없다. 같은 계약의 계산을 교체하는지, 다른 계약을 번역하는지를 봐야 한다. 변화 통지에서는 계산이나 단위보다 등록 관계와 수신자의 수명이 핵심이다.

    요구가 달라졌을 때 남는 수정과 새로 생기는 책임
    변경 요구검토할 구조그래도 필요한 작업
    요금 정책을 더한다전략: 계산 구현을 선택해 위임새 계산·정책 선택·공통 계약 시험. 회원 자격 판단은 별도다.
    호출 방식이 다른 장치를 붙인다어댑터: 경계의 호출과 값을 변환단위·오류·유효 시점·자원 해제의 의미를 확인한다.
    알림을 받는 화면이 늘고 줄어든다옵서버: 등록된 수신자에게 통지구독 수명·알림 순서·연쇄 호출·실패 처리를 정한다.

    실제 변경을 하나 적고 현재 수정이 퍼지는 곳을 찾은 다음, 계약을 분리했을 때 남는 수정과 새 비용을 비교한다. ‘요금 하나를 추가해도 판매 검사는 유지된다’처럼 확인 가능한 이득이 있어야 한다. 미래의 모든 변경을 예상해 계층을 만들기보다 단순한 함수·조건문으로 해결되는 부분은 단순하게 남겨도 된다.

    5.1 객체 설계와 아키텍처

    객체지향 프로그래밍은 상태·책임·캡슐화·상속·다형성의 기본 의미를 다루고, 패턴은 그 재료를 특정 변경 문제에 배치한다. 둘을 구별해야 클래스를 썼다는 사실과 적절한 패턴을 선택했다는 판단을 혼동하지 않는다.

    소프트웨어 아키텍처와 모듈의 큰 경계에서도 책임 분리는 중요하지만, 로컬 옵서버와 서비스 사이 이벤트 전달의 실패 조건은 다르다. 정렬 비교기를 교체하는 구조와 실제 정렬의 비용도 다른 질문이다. 비용은 자료구조와 알고리즘에서 다룬다. 패턴 이름은 팀의 공통 언어가 되되 입력·결과·오류 계약을 대신하지 않는다.
