    1. 반복되는 설계 문제

    처음에는 일반 요금만 계산하던 판매 프로그램에 회원 요금과 행사 요금이 추가되었다고 하자. 판매 동작마다 요금 종류를 확인하는 조건문을 넣으면 새 요금을 도입할 때 여러 곳을 수정해야 한다. 다른 프로그램에서도 정렬 기준, 파일 출력 형식, 이동 방식처럼 ‘처리 흐름은 유지하면서 일부 계산을 바꾸고 싶다’는 요구가 나타난다. 업무 내용은 달라도 변경이 번지는 모양은 닮아 있다.

    디자인 패턴, 또는 설계 패턴은 반복되는 문제의 맥락과 그 문제를 풀기 위한 재사용 가능한 설계 구조를 이름으로 정리한 것이다. 어떤 역할을 나누고 누가 누구에게 요청할지, 그 결과 어떤 변경이 쉬워지고 어떤 비용이 생길지를 함께 설명한다. 재사용하는 것은 완성된 소스 파일이 아니라 설계 경험이다. 같은 전략 패턴도 언어와 요구에 따라 클래스, 함수, 인터페이스를 조합하는 모양이 달라질 수 있다.[1]

    패턴을 읽을 때는 이름보다 먼저 문제와 조건을 확인한다. 계산 종류를 교체해야 하는가, 이미 있는 기능의 호출 방식이 맞지 않는가, 사건을 받아야 할 대상이 늘어나는가에 따라 적합한 구조가 다르다. 해법을 적용한 뒤에는 기존 책임이 어디로 이동했는지와 새로 생긴 책임이 무엇인지 확인한다. 이름만 붙이고 조건문을 다른 파일로 옮겼다면 수정 범위가 실제로 줄었는지는 별도로 따져야 한다.

    라이브러리는 호출해서 쓰는 구현을 제공하고, 알고리즘은 어떤 결과를 계산하는 절차를 다루며, 패턴은 주로 구현들이 맺는 관계와 책임 배분을 설명한다. OOP가 객체·상태·사용 약속이라는 기본 재료를 제공한다면 패턴은 특정 변경 문제에 그 재료를 배치하는 방법이다. 따라서 패턴을 적용하지 않아도 객체지향 프로그램일 수 있고, 패턴의 의도를 클래스 없이 함수 조합으로 표현할 수도 있다.[2]

    2. 생성·구조·행위

    대표적인 객체지향 설계 패턴은 생성, 구조, 행위의 세 관점으로 분류한다. 생성은 어떤 객체를 어떻게 준비할지, 구조는 기존 객체나 클래스를 어떻게 연결할지, 행위는 누가 어떤 일을 맡고 요청을 주고받을지를 중심으로 보는 구분이다. 프로그램의 개발 순서를 세 단계로 나눈 것이 아니며, 한 프로그램에서 여러 분류의 패턴이 함께 쓰일 수 있다.[1]

    분류별 중심 질문과 해법의 예
    분류중심 질문대표 구조추가되는 부담
    생성호출자가 구체 클래스를 직접 정하지 않고 필요한 객체를 얻을 수 있는가?Factory Method는 생성 동작의 구현을 하위 클래스가 바꿀 수 있게 한다. Abstract Factory는 관련 객체들을 일관된 조합으로 생성하는 약속을 제공한다.생성 계층과 설정을 찾아가야 하며, 생성할 종류가 고정이면 과할 수 있다.
    구조이미 있는 기능을 필요한 경계와 모양으로 연결할 수 있는가?Adapter는 다른 호출 약속을 맞춘다. Decorator는 감싼 객체와 같은 사용 약속을 유지하며 책임을 더한다.감싸는 계층과 호출 경로가 늘고, 의미가 맞는지 확인해야 한다.
    행위계산이나 알림의 책임을 어떻게 나누는가?Strategy는 교체할 계산을 위임한다. Observer는 등록된 수신자에게 변화를 알린다.계산 선택, 수신자 수명, 실행 순서와 실패 처리를 정해야 한다.

    예를 들어 화면 모양에 맞춰 버튼과 메뉴를 함께 만들어야 한다면 생성의 일관성이 문제다. 파일 입력을 기존 파서가 기대하는 형식으로 제공해야 한다면 연결 경계가 문제다. 이미 준비된 요금 계산들 중 하나를 선택해 판매에 적용한다면 행동의 교체가 문제다. 먼저 바뀌는 부분을 구체적으로 적으면 분류가 암기 목록이 아니라 설계 대안을 찾는 출발점이 된다.

    생성을 함수 하나에 모으는 것만으로도 중복을 줄일 수 있다. 이런 함수를 넓게 ‘팩터리’라고 부르기도 하지만, 생성 함수 하나가 있다는 이유만으로 Factory Method나 Abstract Factory의 구조를 구현했다고 하지는 않는다. 단순한 분리로 충분한지, 하위 클래스별 생성 변화나 관련 객체 묶음의 일관성까지 필요한지에 따라 선택한다.

    3. 전략 패턴

    전략(Strategy)은 바꿔 끼울 계산이나 처리 방식을 별도 구현으로 만들고, 사용하는 쪽이 같은 약속으로 선택된 구현에 일을 맡기는 패턴이다. 요금이 하나일 때는 판매 동작 안에서 금액을 계산해도 간단하다. 회원·행사 정책을 여러 판매 경로에 적용하게 되면 잔여 수량을 관리하는 일과 금액을 계산하는 일을 분리할 이유가 생긴다.

    매표소는 요청 수량과 잔여 표를 검사하고, 정책은 수량에 대한 금액을 계산한다. 매표소는 정책 객체를 보유하며 total(수량)을 호출한다. 일반 정책과 회원 정책은 같은 입력과 결과 약속을 지키되 계산을 달리한다. 객체가 다른 객체를 가지고 일을 맡기는 합성과, 같은 호출로 여러 구현을 사용하는 다형성이 여기서 함께 쓰인다.

    정책을 선택하는 판단이 없어지는 것은 아니다. 예제에서는 객체를 만드는 코드가 일반 정책과 회원 정책을 직접 선택한다. 실제 회원 자격 판정이 필요하면 그 판단을 맡은 흐름이 올바른 정책을 전달해야 한다. 전략은 회원 인증을 대신하지 않는다. 새 정책을 추가할 때 매표소의 판매 규칙은 유지할 수 있지만, 정책 구현과 선택 코드 및 시험은 필요하다.

    정책의 계약은 ‘양의 정수 수량을 받아 0 이상의 정수 원화 금액을 반환하며 잔여 수량을 바꾸지 않는다’로 정한다. 세금이나 통화 변환이 없는 설명용 가격이다. 메서드 이름이 같아도 문자열이나 다른 통화 단위로 결과를 주면 같은 계약이 아니다. 인터페이스를 공유한다는 말에는 자료형뿐 아니라 값의 뜻과 부작용 조건도 포함된다.

    실제 API에서 비교 규칙을 전달하는 사례로 Java의 Comparator를 볼 수 있다. 정렬 메서드는 비교기를 받아 어느 항목을 앞에 놓을지 결정하며, 비교기는 일관된 순서 관계 등 계약을 지켜야 한다. 이를 전략 관점으로 해석하면 정렬 처리와 비교 규칙의 책임이 나뉜다. 공식 API가 확인해 주는 것은 비교기의 동작과 계약이며, 패턴 관점의 설명은 그 동작을 읽는 해석이다.[3]

    교체 지점을 분리하면 계산별 시험이 쉬워지고 판매 코드의 정책별 분기를 줄일 수 있다. 그 대신 클래스와 생성·연결 과정이 늘어난다. 계산이 단순하면 함수를 인수로 전달해 같은 목적을 달성할 수 있고, 정책 하나가 고정이라면 함수 하나를 유지해도 된다. 상속 계층을 많이 만드는 것이 전략의 목적은 아니다.

    4. 매표소의 정책 교체

    일반 표는 한 장에 1000원, 회원 표는 한 장에 800원으로 가정한다. 각각 표 3장으로 시작하는 매표소를 별도로 만든다. PricePolicy의 기본 메서드는 계산을 제공하지 않고 NotImplementedError를 발생시킨다. 이는 Python의 추상 클래스 선언 기능이 아니라 자식이 구현해야 할 약속을 간단히 나타낸 코드다. 두 정책은 total을 오버라이딩한다.

    class PricePolicy:
    def total(self, quantity):
        raise NotImplementedError("provide a price policy")

class StandardPrice(PricePolicy):
    def total(self, quantity):
        return 1000 * quantity

class MemberPrice(PricePolicy):
    def total(self, quantity):
        return 800 * quantity

class TicketDesk:
    def __init__(self, stock, policy):
        if type(stock) is not int or stock < 0:
            raise ValueError("invalid stock")
        self._remaining = stock
        self._policy = policy

    @property
    def remaining(self):
        return self._remaining

    def sell(self, quantity):
        if type(quantity) is not int or quantity <= 0:
            raise ValueError("invalid quantity")
        if quantity > self._remaining:
            raise ValueError("not enough tickets")
        price = self._policy.total(quantity)
        if type(price) is not int or price < 0:
            raise ValueError("invalid policy result")
        self._remaining -= quantity
        return price

morning = TicketDesk(3, StandardPrice())
afternoon = TicketDesk(3, MemberPrice())
print(morning.sell(2), morning.remaining)
print(afternoon.sell(2), afternoon.remaining)
try:
    morning.sell(2)
except ValueError as error:
    print(str(error), morning.remaining)

    TicketDesk는 PricePolicy를 상속하지 않고 정책 객체를 가진다. 일반·회원 정책은 PricePolicy를 상속한다. 판매 동작은 수량을 검사한 뒤 정책을 호출하고, 반환값을 검사한 다음 잔여 표를 줄인다. 이 순서 덕분에 정책 계산이 실패하거나 잘못된 값을 돌려주면 수량 감소까지 진행하지 않는다. remaining은 읽기 속성이고 _remaining의 밑줄은 내부용 관례일 뿐 접근 금지는 아니다.[4]

    최종 본문에서 추출한 코드를 CPython 3.11.15로 실행한 표준 출력은 다음과 같다.

    2000 1
1600 1
not enough tickets 1

    같은 sell(2) 호출에 일반·회원 정책이 서로 다른 금액을 계산하고 각 객체의 수량은 따로 줄었다. 마지막 요청은 오전 매표소의 잔여 1장보다 많은 2장이므로 거부했으며 잔여 값은 1로 유지되었다. 별도 검증에서도 잘못된 수량, 잘못된 정책 반환값과 정책 예외가 잔여 수량을 바꾸지 않는지 확인했다.

    이 코드는 단일 실행 흐름에서 부작용 없이 금액을 계산하는 정책과 협력한다. 여러 요청의 동시 판매 방지, 결제와 판매의 원자적 처리, 영구 저장, 사용자 권한은 구현하지 않았다. 정책이 외부에서 수행한 작업까지 되돌리는 코드도 없다. 상태 변경을 메서드에 모은 것과 거래 전체의 안전성을 보장하는 것은 다른 문제다.

    5. 어댑터 패턴

    어댑터(Adapter)는 호출자가 원하는 사용 약속과 기존 기능의 약속이 다를 때 그 경계를 맞추는 구조다. 전략이 같은 계약의 계산을 교체하는 문제라면 어댑터는 이미 있는 기능을 그 계약에 맞게 연결하는 문제다. 기존 코드를 직접 고칠 수 없거나 여러 호출자를 한꺼번에 바꾸기 어렵다면 변환 책임을 한곳에 두는 것이 유용하다.

    보고서가 센서의 온도를 섭씨 값으로 읽는데, 교체한 장치의 기존 API는 화씨 값과 다른 메서드 이름을 제공한다고 하자. 보고서마다 이름과 단위를 바꾸는 코드를 넣으면 장치 차이가 여러 곳에 퍼진다. 보고서는 계속 celsius()를 호출하고, 어댑터가 장치의 read_fahrenheit() 결과를 섭씨로 바꾸게 한다. 이 사례의 온도는 실제 장치 측정값이 아닌 고정 시험값이다.

    class LegacySensor:
    def read_fahrenheit(self):
        return 68.0

class CelsiusAdapter:
    def __init__(self, sensor):
        self._sensor = sensor

    def celsius(self):
        fahrenheit = self._sensor.read_fahrenheit()
        return (fahrenheit - 32.0) * 5.0 / 9.0

def report(sensor):
    return f"{sensor.celsius():.1f} C"

print(report(CelsiusAdapter(LegacySensor())))

    CPython 3.11.15에서 최종 본문 코드를 실행한 표준 출력은 다음과 같다.

    20.0 C

    보고서는 장치의 메서드 이름이나 변환식을 몰라도 섭씨 결과를 얻는다. 어댑터에 보조 기능을 더할 수는 있지만, 장치가 측정하지 않은 정보를 단위 변환만으로 얻을 수는 없다. 장치가 오래된 측정값을 반환하는지, 고장을 숫자나 예외로 나타내는지까지 확인해야 같은 의미의 온도를 제공할 수 있다. 예제의 기존 장치는 정상적인 수치만 반환하며 실제 장치의 오류·누락·유효 시각 검증은 포함하지 않았다.

    Java의 InputStreamReader도 바이트 입력을 지정한 문자 인코딩에 따라 문자로 읽는 경계를 제공한다. 바이트를 읽는 기능과 문자를 원하는 호출자 사이를 맞춘다는 점을 어댑터 관점에서 볼 수 있다. 인코딩 선택을 잘못하면 메서드가 호출된다는 사실만으로 의도한 문자를 얻을 수 없다. 공식 API의 ‘bridge’라는 일반 표현을 별도의 GoF Bridge 패턴 분류로 단정하지 않는다.[5]

    어댑터를 고를 때는 메서드 이름뿐 아니라 단위·결과·오류·자원 해제의 약속까지 대응시킨다. 기존 기능의 차이가 한곳에 모이는 이득이 있지만, 변환 계층이 추가되고 그 계층도 시험·유지해야 한다. 두 인터페이스를 함께 바꿀 수 있고 사용처가 적다면 직접 통일하는 편이 더 단순할 수 있다.

    6. 옵서버 패턴

    옵서버(Observer)는 변화를 제공하는 객체에 관심 있는 수신자들이 등록하고 알림을 받는 관계다. 잔여 표가 바뀌면 화면과 통계 표시를 갱신한다고 하자. 판매 코드가 각 화면의 구체 메서드를 직접 호출하면 새 표시를 추가할 때 판매 코드를 고쳐야 한다. 제공자가 등록된 수신자의 공통 알림 동작을 호출하게 바꾸면 수신자 추가·제거를 등록 관계로 표현할 수 있다.[6]

    알림 제공자와 수신자는 상태값을 담은 같은 메시지 약속으로 연결된다. 누가 등록하고 언제 해제할지는 여전히 결정해야 한다. 아래에서는 호출 가능한 함수도 수신자로 사용한다. subscribe는 구독 해제 함수를 돌려주고, 수신자는 더 이상 알림이 필요 없을 때 그 함수를 호출한다. 판매 예제에 이 코드를 연결하지는 않았으며, 같은 잔여 수량이라는 값으로 알림 관계만 따로 실행한다.

    class RemainingEvents:
    def __init__(self):
        self._listeners = {}

    def subscribe(self, listener):
        token = object()
        self._listeners[token] = listener
        def unsubscribe():
            self._listeners.pop(token, None)
        return unsubscribe

    def publish(self, remaining):
        for listener in tuple(self._listeners.values()):
            listener(remaining)

events = RemainingEvents()
stop_screen = events.subscribe(lambda value: print("screen", value))
stop_stats = events.subscribe(lambda value: print("stats", value))
events.publish(1)
stop_screen()
events.publish(0)
stop_stats()

    CPython 3.11.15에서 최종 본문 코드를 실행한 표준 출력은 다음과 같다.

    screen 1
stats 1
stats 0

    첫 변화는 화면과 통계가 함께 받고, 화면을 해제한 뒤의 변화는 통계만 받았다. 이 구현은 등록 순서로 동기 호출하며 발행을 시작할 때 수신자 목록을 복사한다. 따라서 알림 도중 구독을 해제해도 이미 복사한 이번 발행의 수신자는 호출될 수 있다. 수신자 하나가 예외를 내면 그 예외가 호출자에게 전파되고 뒤의 수신자는 호출되지 않는다. 순서와 실패 처리의 선택을 코드가 드러내는 것이지 옵서버라는 이름이 이 방식을 강제하는 것은 아니다.

    수신자가 오래 등록된 채로 남으면 제공자가 불필요한 객체를 계속 참조할 수 있다. 또 수신자가 다시 변화를 일으키면 연쇄 호출이나 반복 알림이 생길 수 있다. 해제 시점, 중복 등록, 순서, 예외 전파를 설계해야 하는 이유다. 오류를 수신자별로 격리할 수도 있지만 그때는 실패를 기록하고 재시도할지 등의 책임이 추가된다. 옵서버는 비동기·병렬 실행이나 네트워크 전달을 보장하지 않으며, 분산 이벤트 전달의 유실·중복 처리까지 자동으로 해결하지 않는다.

    7. 선택과 비용

    같은 클래스 그림처럼 보여도 패턴의 의도가 다를 수 있다. 기존 장치의 인터페이스를 맞추는 객체와 요금 계산을 갈아 끼우는 객체는 모두 다른 객체를 감쌀 수 있지만, 전자는 계약 차이를 번역하고 후자는 같은 계약의 행동을 교체한다. 이름을 판단할 때는 그림의 상자 수보다 해결하려는 변경 문제를 읽어야 한다.

    요구가 달라졌을 때 남는 수정과 새로 생기는 책임
    변경 요구검토할 구조그래도 필요한 작업
    요금 정책을 더한다전략: 계산 구현을 선택해 위임새 계산·정책 선택·공통 계약 시험. 회원 자격 판단은 별도다.
    호출 방식이 다른 장치를 붙인다어댑터: 경계의 호출과 값을 변환단위·오류·유효 시점·자원 해제의 의미를 확인한다.
    알림을 받는 화면이 늘고 줄어든다옵서버: 등록된 수신자에게 통지구독 수명·알림 순서·연쇄 호출·실패 처리를 정한다.

    선택 순서는 실제 변경을 하나 적고, 현재 수정이 퍼지는 지점을 찾고, 분리할 계약을 정한 다음, 작은 해법과 패턴 구조의 비용을 비교하는 것이다. ‘새 정책 하나를 넣어도 판매 검사 코드는 유지된다’처럼 확인 가능한 이득이 있어야 한다. 미래의 모든 변화를 예상해 계층부터 늘리기보다는 지금 반복되는 변경이나 충분히 구체적인 요구에 대응하는 편이 낫다.

    패턴의 가치는 공통 언어에도 있다. ‘전략을 사용한다’는 말은 계산 교체 지점과 선택 책임을 논의하게 하고, ‘어댑터가 필요하다’는 말은 계약 차이의 번역을 검토하게 한다. 그러나 팀원이 모르는 이름을 나열하는 것보다 실제 입력·책임·오류 조건을 함께 적는 설명이 더 유용하다. 단순한 함수나 조건문으로 요구와 변경 지점이 충분히 드러난다면 그대로 두는 것도 설계 판단이다.

    8. 객체와 구조의 연결

    객체지향 프로그래밍은 상태의 변경 책임, 캡슐화, 상속과 다형성의 기본 의미를 설명한다. 전략·어댑터·옵서버는 그 재료를 특정 문제에 배치한 설계다. 구현의 기본 원리와 패턴 선택의 이유를 구분하면 ‘클래스를 썼으니 패턴을 적용했다’는 판단을 피할 수 있다.

    소프트웨어 구조와 모듈이 다루는 더 큰 구성요소의 경계에서도 책임 분리는 중요하다. 다만 한 프로세스 안의 옵서버 관계를 서비스 사이의 이벤트 전달과 같은 보장으로 해석하지는 않는다. 정렬 비교 규칙을 교체하는 구조와 정렬 연산의 비용 역시 다른 질문이며, 후자는 자료구조와 알고리즘 선택으로 연결된다.
