    1. 데이터가 코드가 되는 취약점

    댓글은 다른 사람이 쓴 글을 읽는 기능이다. 그런데 댓글에 들어온 신뢰할 수 없는 입력을 웹페이지가 안전하게 구분하지 못해 브라우저가 코드로 해석한다면, 글을 읽는 사람의 브라우저에서 공격자가 넣은 스크립트가 실행될 수 있다. 이런 취약점과 이를 이용한 공격을 XSS(Cross-Site Scripting, 크로스사이트 스크립팅)라고 한다.[1]

    브라우저는 HTML로 문서 구조를 만들고 JavaScript로 동작을 수행한다. XSS는 원래 데이터로 다뤄야 할 값이 이 실행 과정에 끼어드는 문제다. 공격자는 댓글 작성자일 수 있고, 피해자는 그 댓글을 보는 다른 이용자일 수 있다. 공격 스크립트는 취약한 페이지의 출처에서 실행되므로 화면 내용을 바꾸거나, 페이지가 접근할 수 있는 정보를 읽거나, 로그인한 이용자 권한으로 요청을 보낼 수 있다. 실제 영향은 그 페이지의 권한과 브라우저의 보안 제한에 따라 달라진다.

    2. 입력에서 실행까지

    가상 문구점의 상품 후기를 생각해 보자. 작성자의 입력이 저장되고, 서버가 다른 이용자에게 후기를 보내며, 브라우저가 이를 화면에 넣는다. 이때 입력을 단순 글자로 표시하지 않고 문서 구조나 코드의 일부로 해석하게 만들면 공격이 성립할 수 있다. 서버가 보낸 값이나 저장소에서 읽은 값이라는 사실만으로 신뢰할 수 있는 것은 아니다.

    저장형 XSS
    후기처럼 저장된 입력이 나중에 다른 이용자에게 표시되는 경로에서 발생한다.
    반사형 XSS
    검색어처럼 요청에 들어온 입력이 그 요청의 응답에 반영되는 경로에서 발생한다.
    DOM 기반 XSS
    브라우저의 페이지 프로그램이 신뢰할 수 없는 값을 읽어 위험한 방식으로 화면에 넣거나 실행할 때 발생한다. DOM은 프로그램이 문서의 구조와 내용을 다루는 객체 모델이다. 문제의 값이 반드시 서버 응답에 포함되어야 하는 것은 아니다.

    저장형·반사형은 입력이 전달되는 경로를, DOM 기반은 브라우저 쪽의 처리 원인을 강조하는 구분이다. 따라서 서로 완전히 배타적인 세 상자로 보지 않는다.[2]

    3. 글자와 서식을 구별하는 출력

    일반 댓글은 입력을 텍스트로 출력하면 된다. 예를 들어 DOM의 textContent는 값을 HTML로 해석하지 않고 글자로 넣는 데 쓴다. 서버의 문서 템플릿에서는 프레임워크의 자동 이스케이프를 활용한다. 출력 인코딩은 특수문자가 해당 위치에서 문법으로 해석되지 않도록 표현을 바꾸는 것이며 암호화와는 다르다. HTML 본문·속성·URL은 해석 규칙이 다르므로 한 가지 변환을 모든 위치에 적용할 수 없다. 실행 코드를 구성하는 자리에 외부 값을 직접 섞는 설계는 피한다.[3]

    서식이 필요할 때 사용하는 HTML 정화(sanitization)는 허용 정책에 맞지 않는 요소나 속성을 걸러 내는 처리다. 정화한 결과를 나중에 위험한 방식으로 다시 조합하면 보호가 깨질 수 있다. 정화 라이브러리와 프레임워크는 보안 업데이트를 적용하고, 자동 보호를 해제하는 기능은 별도로 검토해야 한다.

    4. 다른 보호 수단의 한계

    입력 검증은 값의 길이와 형식 등 업무 규칙을 확인하지만 안전한 출력 처리를 대신하지 않는다. 특수문자를 무조건 삭제하면 정상적인 글을 훼손하면서도 다른 해석 위치의 위험을 놓칠 수 있다. CSP(Content Security Policy)는 브라우저가 실행하거나 불러올 콘텐츠를 제한하는 추가 방어 정책이지, 취약한 출력 코드를 그대로 두어도 된다는 보장이 아니다.

    HTTPS는 통신 중 내용을 보호한다. 전달된 내용을 페이지가 잘못 해석하는 XSS까지 없애지는 않는다. 쿠키의 HttpOnly도 스크립트의 쿠키 직접 접근을 제한할 뿐, 공격 스크립트가 화면을 바꾸거나 이용자 권한으로 요청하는 모든 동작을 막지는 않는다. 요청·응답과 브라우저의 해석 단계는 HTTP와 웹 요청에서 이어 볼 수 있다.
