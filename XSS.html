    1. XSS의 원인과 영향

    댓글을 읽었을 뿐인데 왜 다른 사람이 넣은 프로그램이 실행될까? 페이지가 외부 입력을 글자 데이터와 실행할 코드로 안전하게 구분하지 못하면 이런 일이 생긴다. 이를 XSS(Cross-Site Scripting, 크로스사이트 스크립팅) 취약점이라 하며 이를 이용한 공격도 같은 이름으로 부른다. 방어 기술의 이름이 아니라, 신뢰할 수 없는 값이 브라우저에서 코드로 해석되는 문제의 이름이다.[1]

    HTML은 제목·문단 등 웹 문서의 구조를, JavaScript는 페이지의 동작을 표현한다. 댓글 작성자가 넣은 값이 코드로 해석되면 그 댓글을 보는 다른 이용자가 영향을 받을 수 있다. HTTP·HTTPS 페이지의 출처는 접근 방식인 스킴, 도메인 이름이나 IP 주소인 호스트, 접속 번호인 포트의 조합이다. XSS로 실행된 스크립트는 취약한 페이지의 출처에서 동작하므로 화면을 바꾸거나 페이지가 접근 가능한 정보를 읽거나 로그인한 이용자의 권한으로 요청할 수 있다. 가능한 영향은 페이지 권한과 브라우저의 제한에 따라 달라진다.

    2. 입력의 전달과 실행 경로

    2.1 저장형과 반사형

    상품 후기의 경로를 따라가 보자. 작성자가 값을 입력하고 서버가 저장한다. 다음에 열람자가 상품을 열면 서버가 저장된 후기를 보내고 브라우저가 화면에 배치한다. 저장 단계가 성공했다고 마지막 해석까지 안전해지는 것은 아니다. 후기를 실행 가능한 문법으로 섞어 출력하면 작성자의 값이 열람자의 브라우저 동작을 바꾸는 통로가 된다.

    저장형은 저장된 입력이 나중에 표시되는 경로를 말한다. 반사형은 검색어처럼 요청에 들어온 값이 그 요청의 응답에 반영되는 경로를 말한다. 반사형은 데이터베이스에 저장하지 않아도 생길 수 있다. 두 경우 모두 입력의 출처와 최종 출력 위치를 추적해야 하며, 서버를 거쳐 왔다는 사실만으로 외부 입력이 신뢰된 데이터가 되지는 않는다.

    2.2 DOM 기반 처리

    DOM은 프로그램이 문서 구조와 내용을 다루는 객체 모델이다. 브라우저 프로그램은 주소의 프래그먼트나 입력칸의 값을 읽어 문서를 바꿀 수 있다. 그 값을 위험한 방식으로 HTML에 넣거나 실행하는 과정에서 생기는 문제가 DOM 기반 XSS다. 값이 서버가 만든 HTML 응답에 처음부터 포함되어 있어야만 발생하는 것은 아니다.

    저장형·반사형은 값이 전달되는 경로를, DOM 기반은 브라우저 처리 원인을 강조한다. 예를 들어 저장된 후기를 받아 브라우저 프로그램이 안전하지 않게 삽입하면 저장 경로와 클라이언트 처리 문제가 함께 존재한다. 따라서 세 이름을 서로 겹치지 않는 분류로 외우기보다 ‘어디에서 왔고 어디에서 코드로 해석되는가’를 확인한다.[2]

    3. 출력 위치에 맞는 방어

    3.1 텍스트 출력과 인코딩

    먼저 댓글 기능의 목적을 정한다. 글자를 보여 주는 일반 댓글이라면 HTML로 해석할 이유가 없다. DOM의 textContent는 일반 요소의 텍스트 내용으로 값을 넣으므로 <b>안녕</b>를 넣어도 굵은 글씨 요소를 만들지 않고 꺾쇠까지 글자로 보여 준다. 같은 값을 HTML로 해석하는 삽입 방식에 전달하면 요소가 만들어진다. 저장한 값 자체보다 마지막 삽입 방식이 해석을 바꾸는 것이다.

    서버의 문서 템플릿, 즉 데이터가 들어갈 자리를 둔 HTML 틀에서는 자동 이스케이프가 도움이 된다. 이는 특수문자를 문법 대신 글자로 읽도록 안전한 표현으로 바꾸는 기능이다. 이와 같은 출력 인코딩은 암호화가 아니며, 적용 위치에 맞아야 한다. HTML 본문·속성·URL은 서로 다른 규칙으로 해석된다. HTML 본문용 변환 하나를 모든 위치에 재사용하거나 실행 코드 자리에 외부 값을 직접 섞는 설계는 피한다.[3]

    입력 단계에서 꺾쇠를 모두 지우는 방법은 정상적인 인용문까지 훼손한다. 반면 출력 위치를 정하고 알맞은 텍스트 API나 인코딩을 사용하면 원래 글자를 보존하면서 문법으로 해석되는 것을 막을 수 있다. 단, 실행 코드를 담는 요소 등 위험한 위치를 일반 텍스트 요소와 같은 조건으로 취급해서는 안 된다.

    3.2 서식 허용과 HTML 정화

    편집기가 굵은 글씨를 허용해야 한다면 모든 입력을 텍스트로 만드는 것만으로 기능을 만족시킬 수 없다. 이때 HTML 정화(sanitization)로 허용 정책에 맞는 요소·속성만 남긴다. 위 입력에서 굵은 글씨 요소를 허용했다면 ‘안녕’을 굵게 표시할 수 있다. 이것은 입력 전체를 신뢰하는 처리가 아니라 허용할 문서 구조를 제한하는 처리다. 단순 문자열 치환으로 정화기를 직접 만드는 대신 검증된 라이브러리를 사용한다.

    서식을 허용하는 대가로 허용 목록과 라이브러리의 보안 업데이트를 관리해야 한다. 정화한 결과에 외부 문자열을 다시 덧붙이거나 다른 코드 문맥으로 옮기면 앞선 보호가 깨질 수 있다. 따라서 최종 삽입 경로까지 확인하고 프레임워크의 자동 보호를 해제하는 기능은 별도로 검토한다. 일반 댓글에 필요 없는 서식 기능을 추가하면 이러한 관리 비용도 함께 늘어난다.

    4. 보호 수단과 한계

    입력 검증은 길이·형식 같은 업무 규칙을 검사하고 출력 처리는 브라우저가 값을 어떻게 해석할지 통제한다. 두 역할을 바꾸어 생각하면 정상 입력도 다른 출력 위치에서 위험해질 수 있다. CSP(Content Security Policy)는 브라우저가 실행하거나 불러올 콘텐츠를 제한하는 추가 정책이다. 취약한 출력 코드를 그대로 둔 채 CSP만으로 해결하려 하기보다 안전한 출력에 방어층을 더하는 방식으로 사용한다.

    HTTPS는 전송 중 내용을 보호하지만 도착한 값을 페이지가 코드로 잘못 해석하는 문제는 고치지 않는다. 쿠키의 HttpOnly도 스크립트가 쿠키 값을 직접 읽는 것을 제한할 뿐 화면 변경이나 이용자 권한의 요청을 모두 차단하지는 않는다. 따라서 대응의 출발점은 입력의 경로와 출력 위치를 찾는 일이다. 일반 텍스트인지 허용 서식인지 계약을 정하고 그 계약에 맞게 삽입한 뒤, 추가 정책과 업데이트로 남는 위험을 줄인다.
